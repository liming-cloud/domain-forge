# ADR-0006：显式资源映射与读写一致的数据范围执行

- 状态：Proposed（待讨论）；日期：2026-09-19
- 决策负责人：用户；整理：AI；评审：R2 / Q05
- 需求：C08–C10、C14；验证：D01–D15

## 背景

框架不知道某个业务表的“本人”是创建者、负责人还是记录主体，也不知道无部门记录应该如何处理。只在列表 SQL 上增加过滤不能保护详情、更新和归属变更。

## 推荐决定

应用用例声明固定权限点；受保护资源登记部门/本人字段及支持的操作/SQL 形态。IAM 产生范围值，消费方将范围映射到资源谓词。多角色合并算法只在[安全模型](../design/03-iam-domain-security.md)维护。

查询候选使用 MyBatis-Plus DataPermissionInterceptor；实际支持以未来 SQL 用例验证为准。写入由应用规则与仓储条件写入共同约束：已有记录的范围、目标归属、版本和影响行数都检查；创建记录也必须验证目标归属。不能把插件选型当作所有写操作自动受保护的证明。

受保护资源访问没有映射、上下文或可信权限点时拒绝执行。系统认证查询采用内部可审计白名单，限定具体 Mapper/用例；禁止外部请求设置 bypass，禁止对整个服务关闭数据权限。未登记的新 Mapper 触达已保护资源时由覆盖检查阻断，不能靠“没有注解”获得例外。

首批支持受验证的简单查询、分页/计数、详情及有界联表。子查询、UNION、批量写入等只有明确用例和测试后才加入支持清单；否则拒绝或改写成已支持的显式安全查询，不承诺通用 SQL 重写。

## 备选与代价

- 全部手写范围条件：透明但容易遗漏，需额外覆盖检查；作为少量特殊查询的显式方案可接受。
- 全局自动猜字段并拦截全部 SQL：接入表面简单，但混淆资源语义和系统查询，拒绝采用。
- 仅在网关或 Controller 检查角色：不能保证资源级读写边界，无法满足 C09。

## 后果与重评条件

每个业务资源必须说明归属和支持范围，这是一项接入成本。ES 查询和 S3 对象不能直接继承 SQL 约束，未来需分别建立等价授权边界。引入多租户、行级共享或复杂组织后，先重评模型，再修改执行器。
