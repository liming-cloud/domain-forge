# 平台研发流程

平台维护者（含 AI 编码工具）开发本仓库时的入口。业务项目复制仓库后删除 `docs/platform/`（见[业务仓库起步清单](../reference/业务仓库起步清单.md)），业务研发只用[开发流程](../workflow/01-开发流程.md)。平台资产仍在本仓库维护，不因标注“业务项目可删除”而失去维护。

## 开工前

1. 任务来自 GitHub「首版」里程碑中 `status/ready`、且依赖（blocked by）已全部关闭的任务 issue，编号小的优先。issue 描述是唯一依据。没有就绪的任务时，先把未决问题写进对应 issue，不凭路线图自行开工。
2. 读[产品定义](产品定义.md)中与任务相关的小节（任务与验收场景的对应见[路线图](路线图.md#首版跟踪)），确认任务在范围内。
3. 之后按 [AGENTS.md](../../AGENTS.md) 路由到规则卡与参考页。
4. 每个会话只做一个任务；跨会话的进度写在置顶的路线 issue 中，不写进仓库文件。

## 任务与 issue

2026-11-05 起，issue 采用扁平结构：一个任务对应一个 issue，不再设跟踪层；产品验收场景到任务的对应关系记在[路线图](路线图.md#首版跟踪)中。此前的跟踪 issue（`kind/capability`）都已关闭，作为历史保留。

| 层级 | 何时关闭 |
|---|---|
| 里程碑「首版」：首版剩余的全部任务 issue | 全部任务关闭 |
| 任务 issue（`kind/slice`、`kind/chore`、`kind/bug`、`kind/flake`） | 对应 PR 合并（PR 描述写 `Closes #任务`）；一个任务需要多个 PR 时，由最后一个 PR 关闭 |

- **未决问题**：人的答复写在任务 issue 中，并写成 [ADR](../decisions/README.md)；全部答复后 `status/needs-decision` 改为 `status/ready`。
- **度量**：合并后返工的 PR 加 `rework`；门禁与评审都没拦住、合并后才发现的缺陷加 `escaped-defect`，供研发度量统计（[#103](https://github.com/liming-cloud/domain-forge/issues/103)）。2026-11-03 决定：
  - 字段都从 GitHub 现有数据取得，不另填表：PR 从创建到合并的耗时、评审轮次与评审意见数、是否返工（`rework`）；合并后发现的缺陷在缺陷 issue 上加 `escaped-defect`，并链接引入它的 PR。
  - 每个里程碑统计一次：运行 [`scripts/dev_metrics.py`](../../scripts/dev_metrics.py)（`--milestone <名称> -o docs/platform/度量报告/<名称>.md`，先跑一遍 `domain-forge-build-rules` 的测试以取得反例检出结果），用 `gh` 从 GitHub 拉取，生成的 Markdown 报告提交到[度量报告](度量报告/首版.md)。
- **漏洞告警**：依赖漏洞由 Dependabot 提示（[W-10](../workflow/01-开发流程.md#w-10-漏洞告警只提示不阻断)）；暂不处理的，在[路线图](路线图.md#已知风险)的已知风险中记录。

## 合并条件

`main` 的分支保护要求五项检查：mvn verify、服务模板、部署参考、MVP 闭环、文档链接；未通过无法合并。检查按 CI 任务名称匹配，修改 `.github/workflows/ci.yml` 中的任务名称时须同步修改分支保护。

人工读过 PR 并开启自动合并（Enable auto-merge）；CI 全绿后由 GitHub 合并并删除分支。不设审批人数：PR 由同一账号开出，作者不能批准自己的 PR。

## 平台资产

下列内容只服务平台研发，业务项目可以删除：

| 位置 | 内容 |
|---|---|
| `docs/platform/` | 产品定义、路线图、质量模型与北极星、性能基线、本页 |
| `.github/ISSUE_TEMPLATE/`、`.github/pull_request_template.md` | 平台的 issue 与 PR 模板；业务项目按自己的流程改写 |

修改平台资产也要保持文档链接检查通过。平台文档不能被其余文档以链接依赖（业务项目删除后链接会失效）；其余文档需要提到平台文档时只写路径，不加链接。

## 向业务仓库同步平台修复

业务仓库以 git 上游合并同步平台升级（[平台升级同步](../reference/平台升级同步.md)）。平台侧的约定：

- 修复尽量集中在平台目录（`platform/`、`deploy/`、`scripts/`、`docs/`），不顺带改动业务可能已改写的文件。
- 改动模板生成的内容（`platform/templates/`）时，在 PR 中说明已生成的服务是否需要手工同步；模板升级不覆盖已有服务。
- 对部署覆盖文件、Nacos 种子、AGENTS.md 的结构性改动，在 PR 描述中单独列出，便于业务仓库合并时评估冲突。
