# 性能基线

首版按预先确定的资源、场景、数据与门槛做一次真实压测，结果与复现说明进入仓库；不替代业务项目自己的性能验收。产品要求见[性能验收边界](../platform/产品定义.md#性能验收边界)，规则卡见[测试与验证 T-10](../rules/10-测试与验证.md#t-10-性能结论绑定条件)，跟踪见 [#112](https://github.com/liming-cloud/domain-forge/issues/112)。

决定记录：[ADR 0021](../decisions/0021-性能基线的取舍.md)。服务启动耗时的基线见[启动](#启动)。

## 口径

| 项 | 内容 |
|---|---|
| 部署形态 | 部署参考（`deploy/compose.yml`）加模板生成的 `order-service`（`--with-example`）与调用它的 `board-service`（`--call-example`、`--consume-example`），与 MVP 闭环验证相同；请求经 Nginx → 网关 → 服务 |
| 资源 | 常驻容器合计 4 核、8064m，见下表。内存配额在启动时设置；CPU 配额在启动与灌数完成后、压测前用 `docker update` 施加（逐容器的静态配额下 PowerJob 等 JVM 启动超过健康检查时限，而真实单机启动时各容器共享 CPU；灌数受 IAM 密码计算速度限制，在配额下要一小时以上；二者都不计量）。JVM 加 `-XX:ActiveProcessorCount=1`，与施加 CPU 配额后会检测到的处理器数一致。一次性初始化任务在压测前已退出，不计入 |
| 数据 | 1 万个账号（`perf00001`…，同一密码，订单角色：订单读写、本人范围），每个账号 10 张草稿订单，共 10 万张；全部经公开接口灌入，不直接写库。按每秒 12 个账号的固定速率灌入（每个账号注册、登录各一次密码计算；IAM 的密码计算池只有 2 个线程加 8 个排队位，失败的登录还计入账号失败次数），约 15 分钟 |
| 负载 | k6 `constant-arrival-rate`（开放模型，按固定速率发起，不因响应变慢而降速），默认每秒 200 次迭代：预热 2 分钟，计量 3 分钟，只统计计量阶段。每次运行只压一个场景 |
| 客户端 | k6 在只接入 Nginx 的压测网络中绑定 480 个源地址，最多 480 个虚拟用户，每个虚拟用户固定一个源地址；每次迭代至少持续 0.95 × 虚拟用户数 ÷ 速率（每秒 200 次时约 2.3 秒，不足部分休眠、不计入耗时），同时在用的源地址约 456 个，每个地址每分钟约 26 次。按地址的登录保护（每地址每分钟 30 次）与网关限流（每地址每秒 20 次）按真实客户端分布生效，不放宽任何产品配置。迭代耗时超过节拍（服务已饱和）时虚拟用户不够，未发出的迭代单独列出 |
| 结果口径 | 按接口统计：吞吐（计量阶段请求数 ÷ 计量时长）、P50/P95/P99 延迟、错误率（非 2xx/3xx 及连接失败）、主要状态码计数；计量期间每 15 秒采样各容器 CPU 与内存 |

| 容器 | CPU（核） | 内存 |
|---|---|---|
| postgres | 0.8 | 1408m |
| iam | 0.8 | 1024m |
| gateway | 0.6 | 768m |
| order-service | 0.6 | 768m |
| board-service | 0.2 | 640m |
| nginx | 0.2 | 128m |
| redis | 0.2 | 384m |
| nacos | 0.2 | 768m |
| rocketmq-broker | 0.2 | 1024m |
| rocketmq-namesrv | 0.1 | 512m |
| powerjob-server | 0.1 | 640m |
| 合计 | 4.0 | 8064m |

### 场景

| 场景 | 迭代内容 | 计量的接口 |
|---|---|---|
| `login` | 随机一个账号登录 | `login`：`POST /api/auth/login` |
| `query` | 带数据范围的订单查询（本人范围，每个账号 10 张） | `query`：`GET /api/orders?limit=20` |
| `submit` | 新建一张草稿订单，再带 `Idempotency-Key` 提交（同事务写 Outbox，board-service 消费） | `create`：`POST /api/orders`；`submit`：`POST /api/orders/{id}/submit`。每次迭代两次请求，服务收到的请求是速率的两倍 |
| `digest` | 跨服务读取订单摘要：board-service 以同一用户身份调用 order-service | `digest`：`GET /api/board/order-digest` |

按 `query`、`submit`、`digest`、`login` 的顺序执行。登录放在最后：速率超过密码计算能力时，失败的登录会计入账号失败次数，部分账号被锁 10 分钟，影响其后场景取令牌。

除 `login` 外，第 i 个虚拟用户固定使用第 i 个账号，令牌取自灌数时该账号的登录（会话 8 小时；令牌只写入临时工作目录，不进入结果目录），压测时不再登录，免得与负载争用 IAM 的密码计算；没有令牌的迭代单独计数，算未达标。

## 复现

前提：Docker（本机虚拟机至少 8 核 8G，k6 与被测服务共用宿主机，见“限制”）、JDK 21、Python 3。

```bash
scripts/perf/run_baseline.sh <结果目录>              # 全部场景，约 1 小时
scripts/perf/run_baseline.sh <结果目录> query digest  # 只压部分场景（仍会重新构建与灌数）
RATE=100 DURATION=5m scripts/perf/run_baseline.sh <结果目录> login
```

脚本在仓库的干净副本中生成两个服务、构建、按上面的配额启动，初始化管理员与订单角色，用 `scripts/perf/seed.js` 灌数，再用 `scripts/perf/load.js` 依次压各场景，最后拆除环境。可调的环境变量：`RATE`、`WARMUP`、`DURATION`、`VUS`、`ACCOUNTS`、`ORDERS_PER_ACCOUNT`、`SEED_RATE`；`KEEP=1` 时保留环境供排查。结果目录中：

| 文件 | 内容 |
|---|---|
| `report.md` | 结果表与计量期间各容器的 CPU 峰值 |
| `<场景>.json`、`seed.json` | k6 汇总（`--summary-export`） |
| `stats-<场景>.txt` | 每 15 秒的 `docker stats` 采样 |
| `environment.txt` | 版本、日期、机器、各容器实际配额、灌数耗时与数据量 |

k6 的门槛（默认 P95 < 200ms、错误率 < 0.1%，可用 `P95_MS`、`ERROR_RATE` 调整）只用于在输出中标出是否越线，越线时脚本照常记录结果。

## 结果

### 2026-11-10 首轮基线

版本 `e382c05`；Apple M3，Docker 29.2.1（虚拟机 8 核、8 GiB），k6 2.3.0。灌数约 14.5 分钟，数据量为 1 万个账号（另有管理员）、10 万张订单。原始结果在 [2026-11-10](性能基线/2026-11-10/)（`200/`、`50/` 两次运行）。

每秒 200 次（门槛参考值的速率）：

| 接口 | 吞吐（次/秒） | P50（ms） | P95（ms） | P99（ms） | 错误率 | 说明 |
|---|---|---|---|---|---|---|
| query | 200.0 | 4 | 6 | 8 | 0.00% | |
| create | 147.2 | 1471 | 2698 | 3351 | 0.03% | 虚拟用户不够，26% 的迭代未发出 |
| submit | 147.2 | 1435 | 2615 | 3300 | 0.03% | 同上 |
| digest | 68.1 | 6288 | 12254 | 15002 | 1.55% | 504 为主；66% 的迭代未发出 |
| login | 200.0 | 46 | 625 | 784 | 92.17% | 429（密码计算繁忙），成功约 15.7 次/秒 |

每秒 50 次（对照）：

| 接口 | 吞吐（次/秒） | P50（ms） | P95（ms） | P99（ms） | 错误率 | 说明 |
|---|---|---|---|---|---|---|
| query | 50.0 | 5 | 8 | 10 | 0.00% | |
| create | 50.0 | 4 | 6 | 12 | 0.00% | |
| submit | 50.0 | 4 | 7 | 11 | 0.00% | |
| digest | 50.0 | 467 | 1240 | 1840 | 0.00% | |
| login | 50.0 | 97 | 539 | 621 | 57.40% | 429，成功约 21.3 次/秒 |

计量期间的 CPU 峰值（1.0 为 1 核；括号内为配额，接近或达到配额即为瓶颈）：

| 场景（速率） | gateway（0.6） | iam（0.8） | order-service（0.6） | board-service（0.2） | postgres（0.8） |
|---|---|---|---|---|---|
| query（200） | 0.25 | 0.37 | 0.60 | 0.02 | 0.26 |
| submit（200） | 0.52 | 0.53 | 0.63 | 0.14 | 0.63 |
| digest（200） | 0.17 | 0.26 | 0.23 | 0.21 | 0.23 |
| login（200） | 0.28 | 0.84 | 0.04 | 0.20 | 0.21 |

观察：

- **带范围的订单查询**在每秒 200 次时 P95 6ms、无错误；order-service 已用满 0.6 核配额，再往上会先在这里饱和。
- **提交订单**每秒约 147 次后饱和（order-service 与 PostgreSQL 用满配额），排队使延迟升到秒级；每秒 50 次时 P95 7ms。
- **跨服务读取订单摘要**受 board-service 的 0.2 核配额限制：每秒 50 次时 P95 已达 1.2 秒，每秒 200 次时大量 504。该配额是本轮的分配，并非产品默认值。
- **登录**受 Argon2id（m=19456KiB、t=2）与 2 个计算线程限制，0.8 核下每秒成功约 16—21 次，超出部分以 429 快速拒绝（P95 约 0.6 秒），符合设计的过载保护。

## 启动

服务在真实部署方式下的启动耗时与耗时分布，作为启动提速（[#157](https://github.com/liming-cloud/domain-forge/issues/157)：Java 25＋AOT 缓存）的基线；跟踪见 [#156](https://github.com/liming-cloud/domain-forge/issues/156)。只度量，不改服务、镜像与部署配置。

### 口径

| 项 | 内容 |
|---|---|
| 部署形态 | 部署参考（`deploy/compose.yml`）加模板生成的 `order-service`（`--with-example`），不加压测覆盖文件：不设内存配额，JVM 参数与运行镜像一致。整套服务健康、管理员初始化后，依赖（PostgreSQL、Redis、Nacos、RocketMQ、PowerJob、网关、Nginx）保持运行 |
| 被测服务 | IAM 与 order-service，逐个重启：`docker compose stop`（正常停止，注销 Nacos 实例）→ `docker update --cpus` 设 1 核或 2 核 → `docker start`。被测服务之外的容器不限 CPU |
| 次数 | 每个服务、每种配额连续 5 次，取中位数 |
| 容器启动到就绪 | 从执行 `docker start` 到容器内 `curl /actuator/health/readiness` 成功，每 0.2 秒探测一次（误差约 0.3 秒），含容器启动、JVM 启动、Spring 上下文、就绪前的启动任务 |
| Started | 本次启动日志中 `Started … in X seconds` 的 X：Spring Boot 从 `SpringApplication.run` 开始到上下文刷新完成，不含 JVM 启动与 Boot 启动器 |
| 首个请求 | 就绪后立即经 Nginx → 网关发出的第一个成功请求的耗时：IAM 为 `GET /api/roles`（管理员令牌，含权限判定与数据库），order-service 为 `GET /api/me/orders`（只需登录，查本服务库，不调 IAM）。网关尚未发现刚注册的实例时返回 503，脚本每 0.2 秒重试，等待时间另记为 `route_wait_ms`，不计入首个请求 |
| 剖析 | 计时之后，每个服务在 1 核下带 JFR 再启动一次（`settings=profile`，CPU 采样周期 1ms，调用栈 512 帧）。两种视角：日志时间线取 main 线程相邻两条日志之间的墙钟间隔，最长的 10 段；JFR 取到就绪为止全部 Java 线程的 CPU 样本，按组件归类（调用栈根端起第一个不属于 JDK、Spring 与 `main` 入口的帧），另计 GC 次数与停顿、已加载类数。JFR 只采样执行 Java 代码的线程，且每个周期只取少数线程，一次启动约 500—700 个样本，占比只表示 Java 代码中的相对分布；JIT 编译、GC 与 JVM 内部的类链接不在其中。带 JFR 的启动比计时慢约 1 秒，只用于看分布 |

### 结果：2026-11-12

版本 `1602f75`；Apple M3，Docker 29.2.1（虚拟机 8 核、8 GiB），运行镜像 Temurin 21 JRE；本机另有 4 个无关容器在运行（空闲）。同一台机器连续跑两轮，原始结果在 [2026-11-12-启动](性能基线/2026-11-12-启动/)（`round1/`、`round2/`，不含 JFR 与日志）。

第一轮中位数：

| 服务 | CPU（核） | 容器启动到就绪（秒） | Started（秒） | 首个请求（ms） |
|---|---|---|---|---|
| iam | 1 | 11.5 | 9.9 | 130 |
| iam | 2 | 6.0 | 5.0 | 87 |
| order-service | 1 | 12.3 | 10.5 | 290 |
| order-service | 2 | 6.3 | 5.3 | 127 |

两轮中位数差异（第二轮相对第一轮）：

| 服务 | CPU（核） | 容器启动到就绪 | Started | 首个请求 |
|---|---|---|---|---|
| iam | 1 | +0.8% | +0.1% | −5.4% |
| iam | 2 | +0.7% | −0.1% | 0.0% |
| order-service | 1 | −0.9% | −1.3% | −20.3% |
| order-service | 2 | −1.3% | −1.3% | −3.9% |

- 容器启动到就绪与 `Started` 两轮差异都在 ±1.5% 内，同组 5 次的极差约 5%—10%。
- **首个请求**在 order-service 1 核下不稳定：10 次分成约 170—230ms 与约 290—300ms 两档，5 次的中位数落在哪一档有随机性，两轮差 20%，未达到“差异 < 10%”。推断是就绪后仍在进行的后台初始化（JIT 编译、PowerJob 与 Nacos 的后续任务）在 1 核下与请求争 CPU；比较首个请求时应多跑几次或看两档各自的值。
- 2 核时约一半的启动出现约 230ms 的路由等待（网关在服务就绪后约 0.2 秒才发现新实例），1 核时没有出现。

### 剖析：耗时分布

两个服务的分布相近（[IAM](性能基线/2026-11-12-启动/round1/profile-iam.md)、[order-service](性能基线/2026-11-12-启动/round1/profile-order-service.md)）。1 核下最耗时的前 10 项（日志时间线为墙钟，JFR 为 CPU 占比）：

| # | 项 | IAM | order-service | 依据 |
|---|---|---|---|---|
| 1 | JVM 启动、Boot 启动器、日志初始化（容器启动到第一条日志） | 3.2 秒 | 3.5 秒 | 时间线（带 JFR，不带时约少 1 秒：日志中 `process running for` 比 `Started` 多约 1.3 秒） |
| 2 | 类加载与读 jar | Java 样本的 70% 以上 | 同左 | JFR：各组件样本中在类加载器、解压与读嵌套 jar 中的部分合计 |
| 3 | Bean 创建：Redisson 客户端之后到 MyBatis-Plus 就绪（Mapper、仓储、应用服务、Sa-Token 等） | 1.6 秒 | 1.6 秒 | 时间线 |
| 4 | 配置加载之后到仓储扫描（读 Nacos 配置后的环境准备、自动配置条件评估） | 1.3 秒 | 1.4 秒 | 时间线 |
| 5 | Web 上下文就绪到数据源启动（过滤器、安全、观测等 Bean） | 1.3 秒 | 0.6 秒 | 时间线 |
| 6 | Bean 定义注册到 Tomcat 初始化 | 0.9 秒 | 0.9 秒 | 时间线 |
| 7 | GC（1 核时 JVM 自动选 Serial GC） | 69 次，0.7 秒 | 83 次，0.6 秒 | JFR，另建 [#167](https://github.com/liming-cloud/domain-forge/issues/167) |
| 8 | PowerJob worker 初始化（含 Vert.x、内存 H2、网卡探测） | 0.4＋0.4 秒 | 1.0＋0.4 秒 | 时间线；JFR 5—6% |
| 9 | Flyway 校验到 Redisson 连接 | 0.5 秒 | 0.5 秒 | 时间线 |
| 10 | `Started` 之后到就绪（启动任务、PowerJob 鉴权、Nacos 监听） | 0.4＋0.5 秒 | 0.4＋0.5 秒 | 时间线 |

按组件的 CPU 样本：Spring 自身（扫描、解析、代理、Bean 装配）约 50%，Nacos 12%，Tomcat 8—16%，平台与服务代码 8—9%，PowerJob 5—6%，Redisson 1—5%；Flyway、Hikari、MyBatis 都在 3% 以下。数据库迁移校验与连接池启动合计不到 0.2 秒，不是瓶颈。

结论：启动受 CPU 限制（1 核到 2 核时间几乎减半），大头是 JVM 加载、链接约 2.2 万个类和 Spring 的装配，没有单个外部依赖（Nacos、Redis、PostgreSQL）的等待超过 0.5 秒。这正是 AOT 缓存（预先加载、链接类并记录方法画像）针对的部分。

### 目标数字的建议

由人在 #157 定。建议以 1 核 `Started` 为主指标、容器启动到就绪为辅，首个请求只要求不变差：

| 指标 | 基线（1 核／2 核） | 建议目标（1 核／2 核） |
|---|---|---|
| IAM `Started` | 9.9／5.0 秒 | ≤ 6.0／3.0 秒（约 −40%） |
| order-service `Started` | 10.5／5.3 秒 | ≤ 6.3／3.2 秒（约 −40%） |
| 容器启动到就绪 | 11.5—12.3／6.0—6.3 秒 | ≤ 7.5／4.0 秒 |
| 首个请求 | 130—290／87—127ms | 不高于基线 |

依据：JEP 483 中 Spring PetClinic（约 2.1 万个类，与本仓库相近）启动从 4.486 秒降到 2.604 秒（−42%）；其他公开实测在 −30% 到 −53% 之间（如 [ankurm.com 的 JDK 25 实测](https://ankurm.com/spring-boot-jdk-aot-cache-jep-514-515-startup-benchmarks/)，就绪 3.9 → 2.0 秒）。本仓库类加载与装配占比高，−40% 是保守取值。

## 限制

- 结果只对上述配额有效（T-10）。k6 与被测服务在同一台宿主机上，k6 不受配额限制，占用的是配额之外的 CPU；宿主机为 Docker 虚拟机分配的 8 核中，被测服务最多使用 4 核。
- 各容器的配额是静态切分，空闲容器的 CPU 不能借给繁忙容器；真实 4 核单机上同一负载的上限可能更高。
- 只有单实例；未压文件上传；数据库在压测前刚灌完数，缓存与统计信息是新的。
- 源地址数受 Nginx 网络命名空间的邻居表限制（表项超过约 512 个时内核频繁回收，已建立连接上的响应会丢失，表现为 k6 的状态 0），所以只用 480 个；虚拟用户数随之受限，服务饱和时先表现为“未发出的迭代”。
- 启动耗时：只在一台 Apple M3 上测过，被测服务之外的容器不限 CPU、与其他无关容器共用宿主机；数字对 1 核、2 核配额与该机器有效（T-10）。被测服务是重启而不是首次部署：镜像、数据库结构与 Nacos 配置都已就绪，Flyway 只做校验。
