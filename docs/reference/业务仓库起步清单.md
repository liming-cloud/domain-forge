# 业务仓库起步清单

团队复制整个仓库作为业务项目的起点：单仓库，平台资产与业务资产分开，平台升级以 git 上游合并同步（[平台升级同步](平台升级同步.md)）。原则：**平台的目录、模块名、`org.domainforge` 坐标与包名都不改**，业务只新增自己的服务与文档，否则每次升级都会冲突。

## 资产划分

| 类别 | 位置 | 处理 |
|---|---|---|
| 平台专有资产 | `docs/platform/`（产品定义、路线图、平台研发流程、质量模型、性能基线） | 删除 |
| 平台代码与文档 | `platform/`（bom、build-rules、shared、framework、services/iam、services/gateway、templates）、`deploy/`、`scripts/`、`docs/` 下的 rules、reference、explanation、decisions、workflow、`AGENTS.md` | 保留，不改名，随上游同步 |
| 需要改写 | `README.md`、`.github/ISSUE_TEMPLATE/`、`.github/pull_request_template.md` | 改成业务项目自己的说明与模板；保留 CI 与 `dependabot.yml` |
| 业务资产（新增） | `platform/services/<业务服务>`、`deploy/services/<业务服务>.compose.yml`、`deploy/nacos/config/<业务服务>.yaml`、业务自己的决定记录 | 由模板生成或自己新增，上游不会修改 |

仓库中没有示例业务服务；模板的 `--with-example` 示例只在生成时附带，不需要时不加该参数，或直接删除生成出的 `order` 相关包、迁移、Mapper 与测试。

## 步骤

1. **复制并建立上游**：克隆平台仓库，把原远端改名为 `upstream`，再添加业务仓库为 `origin`。

   ```bash
   git clone <平台仓库地址> <业务仓库目录> && cd <业务仓库目录>
   git remote rename origin upstream
   git remote add origin <业务仓库地址>
   ```

2. **删除平台专有资产**：`git rm -r docs/platform`。其余文档提到这些文件时只写路径、不加链接，删除后文档链接检查仍通过。
3. **改写 `README.md`**：写业务项目的目标、负责人与联系方式；删除“平台维护者”一行。
4. **改写 GitHub 模板**：按业务团队的流程调整 issue 与 PR 模板；CI 的必需检查按分支保护设置。
5. **生成第一个业务服务**：见[服务模板使用说明](../../platform/templates/ddd-service/01-使用说明.md)；包名用业务自己的（`--package`），不改平台包名。
6. **业务决定记录**：写在 `docs/decisions/`，文件名加 `业务-` 前缀（如 `业务-0001-订单拆分.md`），避免与上游后续新增的编号冲突。
7. **业务内容放在新增位置**：`AGENTS.md` 需要补充业务约定时，追加到末尾的 `## 本项目补充`；不改动平台文档的既有段落。
8. **验证**：

   ```bash
   platform/mvnw -f platform/pom.xml verify
   python3 scripts/check_doc_links.py
   ```

步骤 2 之后的状态由 `scripts/verify_starter.sh` 在仓库的干净副本中演练：删除平台专有资产，检查 `AGENTS.md` 不再引用平台研发流程，运行文档链接检查，再运行 `mvn verify`（可带 Maven 参数；`--docs-only` 只做前两项检查，已进入 CI 的文档链接作业）。
