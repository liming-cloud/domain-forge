# 平台升级同步

业务仓库用 git 把平台仓库（上游）的修复与升级合并进来；不提供自动升级工具。起点见[业务仓库起步清单](业务仓库起步清单.md)。

## 步骤

1. **拉取并查看变化**（添加 `upstream` 的做法见起步清单）：

   ```bash
   git fetch upstream
   git log --oneline HEAD..upstream/main          # 上游有哪些新提交
   git diff --stat HEAD...upstream/main           # 改了哪些文件
   ```

2. **在业务仓库新建分支并合并**，用 merge，不用 rebase：

   ```bash
   git switch -c chore/sync-platform-<日期> origin/main
   git merge upstream/main
   ```

3. **解决冲突**，按下表处理；合并后运行 `platform/mvnw -f platform/pom.xml verify` 与 `python3 scripts/check_doc_links.py`。
4. **用合并提交（merge commit）合并这个同步 PR，不要 squash**。squash 会丢掉上游提交的祖先关系，下一次合并时已解决的冲突会再来一遍。
5. 合并后 `git diff --stat <合并前> <合并后>` 核对：上游改名或删除的文件没有被带回，业务已删除的平台专有资产（`docs/platform/`）没有复活。

## 容易冲突的位置

| 位置 | 为什么冲突 | 处理 |
|---|---|---|
| `platform/services/pom.xml` | 生成服务时在 `modules` 追加了业务模块 | 保留双方的 `<module>` 行 |
| `deploy/nacos/config/gateway.yaml`、`deploy/rocketmq/topics.conf`、`deploy/powerjob/apps.conf` | 生成服务时追加了业务路由、主题与应用 | 保留双方追加的条目 |
| `deploy/services/<业务服务>.compose.yml`、`deploy/nacos/config/<业务服务>.yaml` | 业务自己的部署覆盖与配置种子 | 保留业务版本；上游若调整了生成的内容，对照上游模板资产（`platform/templates/ddd-service/assets/`）手工合入 |
| 模板生成的服务（`platform/services/<业务服务>`） | 生成后归业务维护，模板升级不覆盖 | 上游改了模板时，对照上游变更手工同步需要的部分 |
| `deploy/compose.yml`、`deploy/env.example` | 业务调整过镜像、端口或 `COMPOSE_FILE` | 以上游为基础，重新套用业务的改动；镜像摘要以上游为准 |
| `AGENTS.md` | 业务在末尾追加了“本项目补充” | 保留上游正文与业务补充两部分 |
| `docs/platform/` | 业务已删除，上游又修改了其中的文件 | 解决为删除（`git rm`） |
| `README.md`、`.github/` 模板 | 业务已改写 | 保留业务版本 |

处理原则：平台目录以上游为准；业务追加或改写的内容保留；冲突无法判断归属时，保留上游的结构，再把业务的差异补回。

## 提给上游的修复

在业务仓库发现的平台缺陷，在上游仓库开 issue 或 PR，修复合并后再按上述步骤同步；不在业务仓库里直接改平台目录，否则下次合并必然冲突。
