# 0003 组件耦合的度量与硬规则

- 状态：已接受（2026-11-05）
- 关联 issue：[#93](https://github.com/liming-cloud/domain-forge/issues/93)、[#104](https://github.com/liming-cloud/domain-forge/issues/104)

## 背景

Martin 的组件原则给出了无环、稳定依赖和主序列距离等度量，需要决定哪些作为门槛。2026-11-05 用 ArchUnit 1.5.1 的 `ArchitectureMetrics` 对 `shared`、12 个组件、IAM 和网关的生产代码测量（基线见质量模型与北极星（平台仓库 `docs/platform/质量模型与北极星.md`））。

## 决定

- 用 ArchUnit 度量，粒度分 Maven 模块级和组件内 api/internal 级。
- 无环和稳定依赖作硬规则（[S-24](../rules/02-系统设计.md#s-24-组件之间无环依赖指向更稳定的一方)）。
- 主序列距离 D 和 Lakos NCCD 只作报表，看趋势，不作门槛；“api 不放具体实现”改用结构规则检查（[S-06](../rules/02-系统设计.md#s-06-用包划分边界跨边界只经公开合同)）。

## 后果

D 值不作门槛的原因：Martin 的抽象度只把接口和抽象类算作抽象。由 record 和异常组成的 api 包会显得“又稳定又具体”，例如 `files.api` 的 D 是 0.88，`notification.api` 是 0.78，其实这是正常的值类型合同。反过来，`persistence.api` 在 api 包里构建连接池，这正是要发现的问题，但同包有注解，它的 D 是 0.00。D 对我们关心的问题既误报又漏报。

规则由 [#104](https://github.com/liming-cloud/domain-forge/issues/104) 实现。
