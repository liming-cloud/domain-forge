# 业务-0001 年假账户聚合：余额与本人申请同在一个聚合

- 状态：提议（2026-11-17，业务规则由人在 #177 确认，本文其余取舍随 PR 评审确认）
- 关联 issue：#177

## 背景

请假审批的业务规则已由人确认（#177，2026-11-13）：

1. 年假余额在申请通过时扣减，撤回或驳回已扣减的申请时退回；并发下不超扣。
2. 同一人的请假时段不能重叠，只计未结束流程与已通过的申请。
3. 状态机：草稿 → 待审 → 通过／驳回；申请人可在审批前撤回。
4. 审批人只能审批自己数据范围（IAM 部门范围）内的申请。

“通过”同时改变申请状态与余额，必须一起生效；平台要求一个事务只修改一个聚合（[S-11](../rules/02-系统设计.md#s-11-一个事务只修改一个聚合)，自动检查），并发约束由数据库保证（[P-09](../rules/05-持久化.md#p-09-并发约束由数据库保证)）。

## 决定

- **聚合**：一名员工一个年假账户 `LeaveLedger`（聚合根，身份为 IAM 账号 ID），包含剩余天数与本人的全部申请 `LeaveRequest`（子实体）。规则 1、2 都跨越同一人的多份申请，由这一个聚合维护；通过一份申请在同一次保存中改状态并扣余额，满足 S-11。
- **并发**：不加锁。保存时以读取到的账户版本为条件更新，同一人的并发修改（两份申请同时通过、两份重叠申请同时起草）只有一个成功，其余返回 409 `VERSION_CONFLICT`；余额另有 `remaining_days >= 0` 检查约束兜底。`LeaveServiceIT` 让两个请求读到同一版本后卡在账户行锁上再放行，验证只有一个写入。
- **客户端不携带版本**：申请提交后内容不再变化，审批人看到的就是将被通过的内容；状态迁移由状态机判断，重复的迁移得到 409 `LEAVE_STATE_CONFLICT`。账户版本会因本人其他申请而变化，要求审批人携带账户版本只会制造无意义的冲突。这是对 P-09 “读取时核对客户端提交的版本”的有意偏离，理由如上。
- **退回**：按规则 3，撤回只能发生在审批前，驳回只针对待审申请，二者都没有扣减过余额，因此不存在需要退回的申请，账户不提供退回操作。规则 1 的退回条款按此理解为不会触发；若以后允许撤销已通过的申请，再增加退回。
- **天数**：按自然日计，含起止两天，单次最多 366 天；不扣除周末与节假日（没有工作日历的需求与数据来源）。余额不分年度。
- **部门与授权**：申请起草时挂靠一个部门，该部门须在申请人 `leave:request:apply` 的范围内（通常授予“本部门”）；审批人用 `leave:request:approve` 的部门范围，范围外的申请与不存在一样返回 404 `LEAVE_REQUEST_NOT_FOUND`，不暴露他人申请。提交与撤回只能由申请人本人操作（按本人账户加载）。
- **余额来源**：增加发放命令 `POST /api/leave-balances/{accountId}/grants`，权限 `leave:balance:grant` 且须为 ALL 范围（部门范围无法判断员工归属）。确认的规则没有说明余额从哪里来，没有它就无法验证扣减。

不采用：

- 申请与余额各为一个聚合、同一事务修改两者：违反 S-11，自动检查拒绝。
- 申请与余额各为一个聚合、通过后经事件异步扣减：扣减晚于通过，余额不足时已通过的申请无法收回，违反“并发下不超扣”。
- 起草或提交时预占余额：与“通过时扣减”的确认规则不符。

## 后果

- 账户随员工的申请数增长，每次修改读取并写回本人全部申请；单人每年的申请量很小，可以接受。需要时再按年度或状态归档。
- 同一人的任意两次修改互相冲突（例如起草新申请与审批旧申请同时发生），被拒的一方刷新后重试即可。
- 待确认：是否禁止审批人审批本人的申请（当前审批人的部门范围包含本人部门时可以审批自己的申请；确认的规则没有限制）。
