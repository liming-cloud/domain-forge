# 开发流程

人和 AI 编码工具使用同一套流程：在任务 issue 中答复未决问题 → 分支开发 → `mvn verify` → PR（关闭任务）→ CI → 人工阅读并开启自动合并 → CI 全绿后 GitHub 自动合并。

## 任务与 issue

研发按产品验收组织，不按技术组件组织：每一份工作都要能说出它闭合了哪条验收场景。只做出组件、却没有使用方和端到端验证的“横向切片”，不算完成。

一个任务对应一个 issue。issue 是一项完整、可验证的工作：产品任务 `kind/slice`，杂务 `kind/chore`，缺陷 `kind/bug`，不稳定测试 `kind/flake`。描述是唯一事实来源，包括背景、已确认的决定、未决问题、验收场景（各自对应的自动化验证）、改动范围、依赖与风险。对应 PR 合并时关闭（PR 描述写 `Closes #任务`）；一个任务需要多个 PR 时，由最后一个 PR 关闭。

- **未决问题前置**：开工前，把需要人决定的问题（见[需要人工决定的事项](#需要人工决定的事项)）写进任务 issue 的“未决问题”，并加 `status/needs-decision`。人在 issue 中答复，全部答复后改为 `status/ready`。答复写成 [ADR](../decisions/README.md)，issue 只链接过去。不在开工后才在对话中临时提问。
- **推进顺序**：取 `status/ready`、且依赖（blocked by）已全部关闭的任务，编号小的优先。遇到未决问题时，把问题写进对应 issue，转去做其他已就绪的任务。
- **issue 描述保持最新**：进度、决定与实施历史都更新在描述中，不让读者翻评论才知道当前状态。
- **完成定义**：验收场景全部打勾，且每条都有在 CI 中执行的自动化验证（确实只能手动的，写明执行人、时间与结果记录位置）。没做完的部分转成范围清楚、写明理由的后续 issue，并经人同意；设计文档与部署说明已更新。

## 不稳定测试

同一代码时而通过、时而失败的测试按缺陷处理，不能靠反复重跑掩盖：

1. 首次出现：确认与当前 PR 的改动无关后可以重跑一次；同时搜索已有 `kind/flake` issue，有则追加本次运行链接与完整日志，没有则新建，标题为 `[Flaky test] <测试名>`。
2. 再次出现且尚未修复：先隔离该测试（禁用并在注释中链接 issue），让合并关口恢复可靠，再离线定位根因。
3. 修复后恢复测试并关闭 issue。根因在产品代码时同时加 `kind/bug`。

## 需求与设计

### W-01 先写清目标和验收场景，再设计

**规则**：动手设计前写清：解决什么问题、给谁用、交付什么、本次不做什么；列出成功、失败、非法输入场景，以及实际适用的并发、重复、恢复场景，并写明观察到什么结果才算通过。区分"已受理""已完成""部分成功"。

**理由**：没有验收场景，就无法判断设计和实现是否正确。

**正例**：

| 场景 | 预期结果 |
|---|---|
| 受邀者在有效期内用正确登录名注册 | 账号创建并记录所用邀请，同一邀请不能再次注册 |
| 同一邀请被两个请求同时使用 | 只有一个成功，另一个返回冲突 |
| 邀请已过期 | 拒绝，不创建账号 |

**检查**：评审。

### W-02 写清规则、术语和数据归属

**规则**：列出关键术语、业务规则、状态及其所有者；写清数据归属、权限、读写范围和外部依赖；写清时效、一致性、安全、性能前提，不知道的标为未知。不用表名、接口名或技术组件名代替业务责任。

**检查**：评审。

### W-03 设计文档按需写

**规则**：普通变更只写受影响的变化，引用已有设计，不复制完整设计。低影响任务写清目标、变化和验证即可；复杂或跨边界任务补充模型、合同和一致性设计。系统设计同时写清运行前提（[W-06](#w-06-设计包含运行前提)）。

**检查**：评审。

### W-04 模型解释不了场景时回到需求

**规则**：模型或边界解释不了实际场景时，回到需求和业务责任重新分析，修正设计后重新验证受影响的场景。自动检查通过不等于业务设计正确。

**检查**：评审。

### W-05 组件设计回答五个问题

**规则**：新增或扩展平台能力时写清：

1. 谁用、用什么：调用方、公开合同、权限责任，并用真实消费方验证接入。
2. 默认实现怎么工作：支持范围、配置、依赖环境、失败行为。
3. 怎么扩展或替换：公开配置或最小扩展接口，用一个实际扩展实现验证，并回归默认实现。
4. 隐藏了哪些复杂性：客户端、资源配置、技术转换留在组件内；不能承诺的保证要告诉使用者。
5. 怎么升级：版本、依赖、迁移方法。

**检查**：评审。

### W-06 设计包含运行前提

**规则**：系统设计同时写清：配置来源与动态生效范围、依赖不可用时的行为与恢复、部署与数据恢复前提、性能测量条件与门槛，以及需要哪些自动检查、评审和真实场景验证。具体规则见[配置与运行](../rules/08-配置与运行.md)、[故障与可观测性](../rules/09-故障与可观测性.md)、[测试与验证](../rules/10-测试与验证.md)。

**检查**：评审。

## 分支与提交

- 从 `main` 新建分支，一个 PR 解决一个任务（或一个缺陷、不稳定测试、杂务 issue）。设计文档随第一个 PR 提交。
- 不叠放 PR：不以另一个未合并的功能分支为 base。上一个 PR 合并后再开下一个；等待期间只做不碰同一批文件的工作。合并会压缩提交，叠放的上层 PR 在下层合并后必然冲突。
- 提交信息使用中文，前缀为 `feat:`（新功能）、`bug:`（缺陷修复）、`build:`（构建、依赖、工具）、`doc:`（只改文档）；严格执行这四个，不用 `docs:`、`chore:`、`ci:` 等。可带范围，如 `build(deps):`。
- 开工前执行 `git config core.hooksPath .githooks`，钩子拦截在 `main` 上的直接提交。WIP 提交只放功能分支，暂停时推送功能分支；PR 不限行数，以一个 PR 的功能闭环为准。
- 推送前本地执行 `platform/mvnw -f platform/pom.xml verify`（本机没有 Docker 时见 [B-08](../rules/03-技术与构建.md#b-08-用-wrapper-构建不跳过检查)）。

## 依赖与升级

### W-08 升级要说明影响并重新验证

**规则**：升级版本时写清：理由、兼容影响、迁移和回退前提，并重新验证受影响的能力。发现某个基线不再有维护或安全更新时，提出升级，不继续把它当作受支持组合。

**检查**：评审；自动[CI]：CI 完整执行 `mvn verify`。

### W-09 新增、排除、覆盖依赖要说明理由

**规则**：新增库、排除传递依赖或覆盖上游管理的版本时，在 PR 中写清用途、作用范围和冲突处理依据，并验证受影响场景。不能为了消除警告而随意扩大依赖或覆盖版本。引入新的基础依赖需要人工决定（[W-07](#w-07-分清事实建议和需要人决定的事)）。

**检查**：评审。

### W-10 漏洞告警只提示，不阻断

**规则**：依赖漏洞由 Dependabot 提示，不阻断功能构建；构建成功也不代表没有风险。告警由研发者结合实际用途处理：需要升级时验证兼容性；暂不处理的，在对应 issue 中记录理由。不自建漏洞库、评分或抑制审计系统。

**检查**：评审：Dependabot PR 与定期复查已知风险。

## PR 要求

PR 描述按[模板](../../.github/pull_request_template.md)填写：关闭的 issue、闭合的验收场景、做了什么、怎么验证、风险与未完成项。合并条件：

1. CI 全部通过。`main` 的分支保护设置必需检查，未通过无法合并；检查按 CI 任务名称匹配，修改 `.github/workflows/ci.yml` 中的任务名称时须同步修改分支保护。
2. 人工读过 PR 并开启自动合并（Enable auto-merge）；CI 全绿后由 GitHub 合并并删除分支。不设审批人数：PR 由同一账号开出，作者不能批准自己的 PR。
3. 行为、接口、配置或设计变化时，对应文档已在同一 PR 中更新。改动目录、模块、脚本或 CI 时，同步 README 与[总体架构](../explanation/总体架构.md)。
4. PR 标题（合并时即压缩后的提交信息）使用上述前缀，且 PR 不含以 `wip` 开头的提交；`过程守卫` 作业检查这两项。

CI 失败、合并冲突和评审意见由开 PR 的一方（含 AI 编码工具）修复并推送，不需要等评审人提醒。

## 评审清单

评审者按下列顺序检查；自动规则已覆盖的内容（分层依赖、SQL 位置、格式、复杂度）不必重复看。

| 方面 | 关注点 |
|---|---|
| 范围 | 是否对应一个已就绪的 issue，闭合的验收场景是否真的端到端验证；有没有顺带做了未要求的事 |
| 设计 | 业务规则的所有者是否明确（聚合、领域策略还是用例）；有没有只转发、无职责的层；查询是否走短路径 |
| 正确性 | 边界输入、并发冲突、事务范围、失败时的返回与回滚 |
| 安全 | 默认拒绝；授权在后端执行；凭据与个人信息不进日志；审计按规范记录 |
| 测试 | 正常路径和关键失败路径都有测试；测试断言的是行为而不是实现细节 |
| 文档 | 规则只在一处维护，其他地方用链接；文档写的是当前结论 |

## 需要人工决定的事项

### W-07 分清事实、建议和需要人决定的事

**规则**：能调查的事实自己查清；会改变范围、合同或风险又查不清的问题，提给人决定。以下事项由人决定：

- 改变产品范围、公开接口合同、数据库结构兼容性。
- 安全语义：认证、授权、会话失效、审计、凭据处理。
- 引入新的框架、中间件或基础依赖。
- 删除或放宽已有测试、规则、校验。

尽量在开工前写进任务 issue 的“未决问题”，开工后才发现的在 PR 或对话中提问。只暂停依赖该问题的部分，其他部分继续推进。决定写成 [ADR](../decisions/README.md)（一个决定一个文件），不另建确认记录或摘要文件。

**检查**：评审。

### W-11 发现问题时修正对象，不放宽检查

**规则**：

- 实现没遵守规范，就改实现；规范本身错了或不适用，就提出有证据的规范修改并交人决定。不通过扩大例外、删除检查、降低通过条件、缩小扫描范围、降低可见性或删除断言来消除问题。
- 测试失败时先判断是实现缺陷、测试缺陷还是需求问题。不能因为实现变了就改预期，更不能删断言让测试通过；行为变化时同步更新受影响的场景和断言。
- 确需保留超限实现或跳过某项检查时，在 PR 中写明对象、指标、理由、影响和替代验证，由人工批准；批准只对该对象生效。不使用 `@SuppressWarnings`、抑制配置或排除路径自行放行。
- 自动规则漏判或误判时，修改 `platform/domain-forge-build-rules/` 中的规则并补正反例（[T-11](../rules/10-测试与验证.md#t-11-自动规则必须有正例和反例)），不绕过。

**检查**：评审。

## 文档维护

- 文档只写当前有效结论；过程和历史留在 issue、git 提交与 PR 中。
- 每条规则只有一处正文，其他地方链接过去，不复制。规则卡的格式与索引见[规则卡索引](../rules/00-索引.md)。
- 新增或调整自动规则时同时补充正例和反例（[T-11](../rules/10-测试与验证.md#t-11-自动规则必须有正例和反例)）；自动与评审的分工见 [T-12](../rules/10-测试与验证.md#t-12-自动检查与人工评审分工)。
- 改动 Markdown 后执行 `python3 scripts/check_doc_links.py`（同时检查规则卡的卡号、引用、索引与检查标签）。
