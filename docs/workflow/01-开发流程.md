# 开发流程

人和 AI 编码工具使用同一套流程：在任务 issue 中答复未决问题 → 分支开发 → `mvn verify` → PR（关闭任务）→ CI → 人工阅读并开启自动合并 → CI 全绿后 GitHub 自动合并。

## 任务与 issue

研发按产品验收组织，不按技术组件组织：每一份工作都要能说出它闭合了哪条验收场景。只做出组件、却没有使用方和端到端验证的“横向切片”，不算完成。

2026-11-05 起，issue 采用扁平结构：一个任务对应一个 issue，不再设跟踪层；产品验收场景到任务的对应关系记在[路线图](../product/02-路线图.md#首版跟踪)中。此前的跟踪 issue（`kind/capability`）都已关闭，作为历史保留。

| 层级 | 是什么 | 何时关闭 |
|---|---|---|
| 里程碑「首版」 | 首版剩余的全部任务 issue | 全部任务关闭 |
| 任务 issue | 一项完整、可验证的工作：产品任务 `kind/slice`，杂务 `kind/chore`，缺陷 `kind/bug`，不稳定测试 `kind/flake`。描述是唯一事实来源，包括背景、已确认的决定、未决问题、验收场景（各自对应的自动化验证）、改动范围、依赖与风险 | 对应 PR 合并（PR 描述写 `Closes #任务`）；一个任务需要多个 PR 时，由最后一个 PR 关闭 |

- **未决问题前置**：开工前，把需要人决定的问题（见[需要人工决定的事项](#需要人工决定的事项)）写进任务 issue 的“未决问题”，并加 `status/needs-decision`。人在 issue 中答复，全部答复后改为 `status/ready`。答复写进设计文档的“决定”小节，issue 只链接过去。不在开工后才在对话中临时提问。
- **推进顺序**：从里程碑中取 `status/ready`、且依赖（blocked by）已全部关闭的任务，编号小的优先。遇到未决问题时，把问题写进对应 issue，转去做其他已就绪的任务。
- **issue 描述保持最新**：进度、决定与实施历史都更新在描述中，不让读者翻评论才知道当前状态。
- **完成定义**：验收场景全部打勾，且每条都有在 CI 中执行的自动化验证（确实只能手动的，写明执行人、时间与结果记录位置）。没做完的部分转成范围清楚、写明理由的后续 issue，并经人同意；设计文档、部署说明与路线图已更新。
- **度量**：合并后返工的 PR 加 `rework`；门禁与评审都没拦住、合并后才发现的缺陷加 `escaped-defect`，供研发度量统计（[#103](https://github.com/liming-cloud/domain-forge/issues/103)）。2026-11-03 决定：
  - 字段都从 GitHub 现有数据取得，不另填表：PR 从创建到合并的耗时、评审轮次与评审意见数、是否返工（`rework`）；合并后发现的缺陷在缺陷 issue 上加 `escaped-defect`，并链接引入它的 PR。
  - 每个里程碑统计一次：脚本用 `gh` 从 GitHub 拉取，生成一份 Markdown 报告提交到仓库。

## 不稳定测试

同一代码时而通过、时而失败的测试按缺陷处理，不能靠反复重跑掩盖：

1. 首次出现：确认与当前 PR 的改动无关后可以重跑一次；同时搜索已有 `kind/flake` issue，有则追加本次运行链接与完整日志，没有则新建，标题为 `[Flaky test] <测试名>`。
2. 再次出现且尚未修复：先隔离该测试（禁用并在注释中链接 issue），让合并关口恢复可靠，再离线定位根因。
3. 修复后恢复测试并关闭 issue。根因在产品代码时同时加 `kind/bug`。

## 分支与提交

- 从 `main` 新建分支，一个 PR 解决一个任务（或一个缺陷、不稳定测试、杂务 issue）。设计文档随第一个 PR 提交。
- 不叠放 PR：不以另一个未合并的功能分支为 base。上一个 PR 合并后再开下一个；等待期间只做不碰同一批文件的工作。合并会压缩提交，叠放的上层 PR 在下层合并后必然冲突。
- 提交信息使用中文，前缀为 `feat:`（新功能）、`bug:`（缺陷修复）、`build:`（构建、依赖、工具）、`doc:`（只改文档）。
- 推送前本地执行 `platform/mvnw -f platform/pom.xml verify`。本机没有 Docker 时加 `-DskipITs -Ddocker.skip=true`，集成测试由 CI 执行。

## PR 要求

PR 描述按[模板](../../.github/pull_request_template.md)填写：关闭的 issue、闭合的验收场景、做了什么、怎么验证、风险与未完成项。合并条件：

1. CI 全部通过。`main` 的分支保护要求五项检查：mvn verify、服务模板、部署参考、MVP 闭环、文档链接；未通过无法合并。检查按 CI 任务名称匹配，修改 `.github/workflows/ci.yml` 中的任务名称时须同步修改分支保护。
2. 人工读过 PR 并开启自动合并（Enable auto-merge）；CI 全绿后由 GitHub 合并并删除分支。不设审批人数：PR 由同一账号开出，作者不能批准自己的 PR。
3. 行为、接口、配置或设计变化时，对应文档已在同一 PR 中更新。

CI 失败、合并冲突和评审意见由开 PR 的一方（含 AI 编码工具）修复并推送，不需要等评审人提醒。

## 评审清单

评审者按下列顺序检查；自动规则已覆盖的内容（分层依赖、SQL 位置、格式、复杂度）不必重复看。

| 方面 | 关注点 |
|---|---|
| 范围 | 是否对应一个已就绪的 issue，闭合的验收场景是否真的端到端验证；有没有顺带做了未要求的事 |
| 设计 | 业务规则的所有者是否明确（聚合、领域策略还是用例）；有没有只转发、无职责的层；查询是否走短路径 |
| 正确性 | 边界输入、并发冲突、事务范围、失败时的返回与回滚 |
| 安全 | 默认拒绝；授权在后端执行；凭据与个人信息不进日志；审计按规范记录 |
| 测试 | 正常路径和关键失败路径都有测试；测试断言的是行为而不是实现细节 |
| 文档 | 规则只在一处维护，其他地方用链接；文档写的是当前结论 |

## 需要人工决定的事项

以下事项由人决定，AI 编码工具应尽量在开工前写进任务 issue 的“未决问题”，开工后才发现的在 PR 或对话中提问：

- 改变产品范围、公开接口合同、数据库结构兼容性。
- 安全语义：认证、授权、会话失效、审计、凭据处理。
- 引入新的框架、中间件或基础依赖。
- 删除或放宽已有测试、规则、校验。

决定写进相关设计文档的"决定"小节（日期、选项、选择和理由），不另建确认记录或摘要文件。

## 文档维护

- 文档只写当前有效结论；过程和历史留在 issue、git 提交与 PR 中。
- 每条规则只有一处正文，其他地方链接过去，不复制。
- 新增或调整自动规则时，修改 `platform/domain-forge-build-rules/`，并同时补充正例和反例测试（`ArchitectureRulesTest` 与 `fixture` 包）。自动规则只拦能明确判定的问题，语义问题交给评审。
- 改动 Markdown 后执行 `python3 scripts/check_doc_links.py`。
