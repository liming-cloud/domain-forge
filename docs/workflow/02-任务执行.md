# 任务规划与执行流程

规范来源与固定输入见[第四层确认记录](../product/02-研发路线.md#第四层确认记录)；实际实现、验证及未完成项见[当前任务](../00-文档导航.md#当前任务)。

## 适用范围与阅读入口

适用于平台研发、消费项目业务研发及能力升级。按任务触发读取：

- 制定总体研发路线或判断任务细化范围：[已确认的任务规划原则](#已确认的任务规划原则)。
- 确定交付单元及人工验收时点：[已确认的交付单元验收原则](#已确认的交付单元验收原则)。
- 判断验收后能否进入下一单元：[已确认的验收后推进原则](#已确认的验收后推进原则)。
- 准备提交推送或提交人工验收：[已确认的 Git 交付次序](#已确认的-git-交付次序)、[候选提交与验收准备](#候选提交与验收准备)。
- 保存人工验收、核对记录提交及交付收尾：[已确认的验收记录原则](#已确认的验收记录原则)、[验收记录与交付收尾](#验收记录与交付收尾)。
- 判断执行、评审、例外及人工确认责任：[责任与人工决定](#责任与人工决定)。
- 准备当前任务、调整计划或核对记录是否足够：[计划形成与滚动更新](#计划形成与滚动更新)、[当前任务的必要信息](#当前任务的必要信息)。
- 中断后继续工作或核对恢复记录：[中断恢复与事实核对](#中断恢复与事实核对)。
- 处理检查或评审发现的问题、准备整改复验：[评审发现与整改复验](#评审发现与整改复验)。
- 核对流程与记录是否能支持执行：[流程与记录验证](#流程与记录验证)。

需求及设计内容遵守[需求与场景分析](../standards/01-需求与领域建模.md#需求与场景分析)，按需阅读与规则覆盖使用[文档流程](01-文档维护.md#渐进式加载与覆盖核对)，实际验证遵守[执行与证据边界](../standards/10-测试与验证.md#执行与证据边界)。本文组织任务，不另设产品要求或复制这些规则。

## 已确认的任务规划原则

- 先明确完整目标、里程碑、交付结果、依赖及验收路线，后续任务保留目标与验收边界。滚动细化不能将尚未实现的承诺从整体路线中静默删除。
- 详细设计聚焦当前任务及其必要前置决定；后续任务依据有效需求、新事实和前序结果逐步细化，不在依据不足时编造全部实现细节。
- 编码前完成应有的总体设计，当前任务明确需求、合同、依赖、适用规则及验证计划；滚动规划不能成为跳过设计或先写代码再补依据的理由。
- 细化及调整时核对整体目标和跨任务影响。会改变已确认范围、责任、合同或风险的取舍交由人工决定，其他可查明事实由 Agent 调查。
- 计划、设计、执行证据及验收分别记录。计划已填写不代表任务可用、验证通过或已验收；本项不授权自动启动后续任务、Git 操作或越过整套文档控制面的确认边界。

## 已确认的交付单元验收原则

- 按能够独立验证完整结果的交付单元提交人工验收，不以类、方法或内部开发步骤划分验收。单元边界及退出条件回指整体路线、需求和合同，不能把零散实现当作完整功能结果。
- 每个任务照常执行适用门禁、必要真实场景及语义评审；交付单元的结果与必要证据齐备后再提交人工验收。拆分内部步骤不增加逐步骤验收要求，也不减少必要验证。
- 范围、合同、责任或风险的重大取舍仍在依赖步骤前提交人工决定，不等待交付单元完成后再追认；正常内部实现不因本项增加逐类审批。
- 检查通过、CI 成功、提交推送或 Agent 自述都不产生人工验收。没有明确验收来源时不标为已验收，也不按已验收任务归档；验收对应的输入、范围及来源须可追溯，具体记录方式随本层后续交付流程明确。
- 单元验收不代替里程碑和整体产品所需的集成、部署、独立消费或升级验证；尚留待后续证明的结果继续保持可见。下一单元按[验收后推进原则](#已确认的验收后推进原则)处理，Git 操作与收尾分别见[候选提交](#候选提交与验收准备)及[验收收尾](#验收记录与交付收尾)。

## 已确认的验收后推进原则

- 本单元获得明确人工验收且必要收尾完成后，在已批准路线及已有授权范围内细化下一单元，不额外索取普通启动指令；本单元尚未验收或收尾未完成时，不能凭进度或自动检查自行视为已满足该推进条件。
- 下一单元的必要设计、合同、规则覆盖及前置条件明确后才执行相应实现，不因允许继续而跳过滚动细化或必需验证。当前条件不足时先查明或补齐，不带着未决前提直接编码。
- 新的重大范围、合同、责任或风险取舍仍先提交人工决定，只暂停依赖该决定的步骤；其他已授权工作可继续。新增单元或改变已批准路线时核对目标与影响，不将自动推进解释为自由扩大范围。
- 后续单元仍按[交付单元验收原则](#已确认的交付单元验收原则)验证及人工验收。更新当前前沿并保持待处理事项可见，不能预先将未来单元标为通过或已验收。
- 本项不自动跨越本轮逐层确认、整套控制面的确认边界或具体执行路线的授权范围；用户明确暂停或限定范围时遵守其要求。Git、生产环境及其他外部操作仍分别遵守有效授权，不由上一单元验收推定。

## 已确认的 Git 交付次序

- 仅在具体任务、仓库、分支及提交推送范围已有有效授权时使用该顺序；未覆盖的操作另行确认。常规候选提交不额外增加一次提交前预审，但必要评审及重大取舍的人工决定仍须完成。
- 本地完整适用验证与必要评审通过后，提交代码、测试及同步的受影响文档，再按授权推送候选。提交内容与中文前缀遵守[Git 工作边界](../../AGENTS.md#工作方式)，普通功能的文档随代码提交，不用独立进度提交替代功能交付。
- 核对远端对象及对应 CI 的真实输入、执行范围和结果，然后提交精确功能 SHA 及必要证据供人工验收。缺少必需结果、环境不足、未执行或失败时不报告通过，也不用另一输入的成功结果替代。
- CI 或其他交付检查发现问题时，按[整改复验流程](#评审发现与整改复验)处理；在已有权限内形成新的修复提交并重新核对，不能通过跳过门禁或改写结果放行。候选变化后重新提交准确对象，不把旧输入的确认延用为新输入验收。
- 提交、推送、CI 通过及人工验收分别记录，未取得明确验收来源时不标为已验收。验收记录引用[唯一来源与限定例外](#已确认的验收记录原则)；本项不授权强推、改写历史、提交无关改动、发布制品或操作生产环境。

## 已确认的验收记录原则

- 仓库任务记录保存真实人工验收来源、对应的精确功能 SHA 和范围，作为任务状态的唯一控制面；索引引用它，不另设 Git 标记或托管平台状态作为并行审批源。CI 等外部证据可以引用，但不独立产生人工验收。
- 每个交付单元明确获验收后，允许一次中文 `doc:` 例外提交，仅更新验收记录、相应状态及索引。不夹带代码、合同或规范变更，普通进度及 CI 状态回填不适用；常规功能文档及整体规范重建继续遵守[Git 工作边界](../../AGENTS.md#工作方式)。
- 记录提交不改写获验收的功能 SHA，也不自动产生对其他输入的验收。推送后核对文档门禁、实际远端及对应 CI；没有完成最终收尾，不报告完整交付或进入下一单元。
- 人工验收事实与记录提交的技术结果分别核对。功能已验收但记录收尾尚未通过时，保留真实验收来源及未完成项；不能抹去事实、隐藏失败或预写尚未产生的 CI 结果。Git 和 CI 的当前状态按实际对象查询，不通过持续追加记录提交维持“最新通过”叙述。
- 此例外仍限于有效的仓库、分支及提交推送授权，不扩展强推、历史改写或外部操作权限。记录格式及执行边界见[机制设计](03-研发控制机制.md#公开命令与记录字段)。

## 责任与人工决定

确认来源：2026-10-12 本会话用户选择 A。

普通任务的语义评审由 Agent 或研发者完成；重大取舍与完整交付单元验收由人工决定。不为每个角色新增文档或配置专职人员；确认来源见[评审责任决定](02-任务执行.md#责任与人工决定)。

| 责任 | 要完成的工作 |
|---|---|
| 当前任务的 Agent 或研发者 | 独立调查事实、准备必要设计、实现与验证，补充语义影响，维护受影响正文、使用说明、索引及任务事实；不自行产生人工批准 |
| 用户或其明确指定的需求、规范及风险责任人 | 决定实际影响范围、合同、责任或风险的取舍，批准必要规范变更及精确例外；决定来源与适用对象可核对 |
| 普通任务的 Agent 或研发评审者 | 按适用规范审阅目标、设计、源码及场景，记录当前输入、覆盖、材料、结论和未解决发现；不能只填写“通过”，也不能把 Agent 评审冒充独立人工评审 |
| 用户或其明确指定的单元验收人 | 对精确交付对象及范围给出明确验收结论；提交推送、CI 或执行者自述不能替代 |

决策访谈只解决无法自行查明、且会改变产品目标、首版能力、公开合同或重大责任的关键取舍。提问前先说明正在决定的层次、对象及对交付的影响；达到当前层的退出条件后停止细化。成熟工具的常规参数、接入及可重复核对由 Agent 完成，不逐项请用户审批；发现工具局限不自动扩张交付范围或生成新的访谈链。2026-10-09 的范围修正来源见[任务决定](../standards/03-技术与构建.md#已确认的依赖漏洞门禁原则)。

普通内部实现沿既定边界执行，不增设逐类、逐方法或每任务人工审批。重大目标、架构边界、规范或风险取舍在依赖步骤前取得人工决定，整套控制面及完整单元仍须人工验收。评审可复用仍适用于当前输入的证据；范围、前提或输入变化时核对适用性。未解决发现保持 Rework，未决重大取舍只暂停依赖步骤，不由 Agent 代为批准。

## 计划形成与滚动更新

以下操作落实上述规划方法，不提前划定具体能力的实现任务或系统结构。

1. 从有效目标确定完整交付结果、里程碑退出条件、依赖及最终验收路线。区分各任务能够证明的结果与仍需后续集成、独立消费或部署验证的结果，不能把阶段证据当作整体完成。
2. 对当前任务补足执行所需的需求、设计、合同和验证计划；必要前置决定即使涉及后续任务，也在当前实现依赖它之前查明或提交人工决定。其余后续任务保留目标、依赖及未定事项，不预先填写无依据的方案。
3. 按实际影响控制记录深度：低影响变更仍能说明目标、变化和验证；复杂或跨边界变更补足相应设计。引用有效基线，只记录受影响的增量，不为普通任务复制完整规范或重复维护同一合同。
4. 根据新事实和前序结果调整细化顺序及内容，检查对完整路线和其他任务的影响；保留必要的变更理由与决定来源，不持续累积所有过程叙述。尚未解决的前置问题明确阻断范围，不静默当作已决定。
5. 计划范围或实际变更调整后，重新进行[规则覆盖核对](01-文档维护.md#渐进式加载与覆盖核对)。验证范围和结果按实际输入记录；验收粒度使用[交付单元原则](#已确认的交付单元验收原则)，后续推进使用[推进原则](#已确认的验收后推进原则)，记录与收尾使用[对应流程](#验收记录与交付收尾)。

## 当前任务的必要信息

以下记录要求不固定文件格式、状态枚举或工具。每项可以引用既有有效来源，不要求创建一份独立文档；低影响任务保持简短，复杂任务按实际需要补充。

| 要回答的问题 | 必要信息 |
|---|---|
| 为什么做、交付什么 | 有效目标及需求来源、本次交付结果、范围与不包含内容；所属交付单元、整体路线及里程碑入口 |
| 对谁有用、依赖什么 | 当前调用方或消费者、依赖及必要前置决定；本次能够验证的结果及留待后续证明的结果 |
| 按什么方案和规则做 | 现行设计与合同、必要增量、适用规则及命中理由；不复制唯一正文 |
| 怎样判断结果 | 必要场景、适用检查及语义评审、真实环境前提和通过标准；不能只有检查名称 |
| 目前可以推进到哪里 | 当前前沿、待决定问题、阻断范围与下一步；未解决问题保持可见 |
| 实际发生了什么 | 对应输入、执行及评审证据、失败或未验证项、整改、决定及验收来源；人工验收与技术收尾结果不能相互替代 |

## 中断恢复与事实核对

以下操作使用任务记录及既定的[活动与归档入口](01-文档维护.md#已确认的文档生命周期原则)，不新增另一套任务状态。具体记录及入口使用上述机制设计；恢复仍须独立核对实际输入，不凭派生索引或旧报告继续宣称通过。

1. 从活动入口定位当前任务及所属交付单元，先读取目标、有效设计、当前前沿、待决定问题和下一步。只在需要解释有关决定或结果时检索相应历史，不重放全部过程或全量加载规范。
2. 独立核对工作区、输入版本、实际变更、依赖及证据对象，与记录中的前沿比较。未提交工作保留并辨明范围；遇到记录与事实不符，先调查，不通过覆盖修改、删除证据或把旧记录当新结果来消除差异。
3. 对实际范围重新进行[覆盖核对](01-文档维护.md#渐进式加载与覆盖核对)，检查前置决定、设计及已有证据是否仍适用于当前输入。环境、输入或合同变化影响验证时，明确需要补做的检查和场景；旧结果不自动延续为当前通过。
4. 更新受影响的任务事实和恢复点，在已有授权内推进；需要人工决定时标明问题及其阻断范围，其他已授权工作继续。验收是否成立依据真实来源，不因中断恢复重新生成验收，也不由本节授权进入下一交付单元。

## 评审发现与整改复验

以下操作使用已确认的[整改与复验原则](../standards/02-系统设计.md#运行约束与设计审阅)及[有效场景与断言](../standards/10-测试与验证.md#场景与有效断言)，不新增或降低通过条件。适用检查、真实场景、语义评审及必要人工决定各自保留证据，不能相互替代。

1. 记录问题对应的输入、规则或合同、事实证据、影响范围及尚未完成项。必要检查失败、场景缺失或必需环境不足时保留未通过或未验证的事实，不能先提交为已完成验收再补证据。
2. 先调查问题来源，再决定整改对象。实现未遵循正确规则时修正实现并补足回归；测试、路由或检查缺陷时按有效规则修正验证机制，并证明合法正例及目标违规反例得到正确结果；需求、合同或规范确需改变时说明依据、影响及验证，经适用人工决定后同步唯一来源。
3. 按实际授权完成整改及必要文档同步。确需风险例外时取得可核对的人工决定，只落实其精确对象、范围和条件；已有[漏洞处置要求](../standards/03-技术与构建.md#风险核对与验证)等专门规则继续适用。登记问题、填写例外理由或修改抑制配置本身都不产生放行依据。
4. 先定向验证问题已经修复，再执行[完整适用门禁及必要回归](../standards/10-测试与验证.md#执行与证据边界)，复核受影响的语义与场景证据。变更输入后重新核对覆盖和证据适用性，保留整改来源及真实结果；未完成复验时不提交为验收通过。

代码语义评审沿真实用例说明四件事：入口到持久化保护了什么规则；本次抽象隔离了什么真实变化；一次具体的权限、保护窗口或只读投影调整会修改哪些位置；哪些允许／拒绝反例证明简化没有改变合同。复用现有评审的覆盖、结论和证据字段，不逐类造过程文档，不以接口数量或关键词自动判定简洁。已约定代表代码审阅时先展示可运行样例，再按确认范围展开。

可判定检查验证覆盖、引用、输入匹配及实际执行；目标是否匹配、规则是否正确、断言是否有效和风险是否可接受仍按相应责任评审或人工决定。不通过删除必要断言、跳过检查、扩大豁免或降低规则使失败变绿；验证机制本身的合法修正也必须保留规则依据和正反例证据。

## 候选提交与验收准备

以下操作落实上述次序，不选定托管平台、CI 配置或记录格式，也不授权当前 Git 写入。

1. 核对任务目标、授权范围、仓库与分支、实际远端输入及工作区；保留无关或来源未明的修改。记录本次起点与差异，遇到输入变化或分支偏离先调查，不覆盖远端或将混入的改动算作本任务成果。
2. 根据真实范围核对设计与规则覆盖，完成[完整适用验证与必要回归](../standards/10-测试与验证.md#执行与证据边界)及必要评审，整改后复验。证据对应实际内容和环境；提交前再次核对待提交差异，验证后内容变化时评估影响并补做验证。
3. 将本任务代码、测试及受影响设计、合同、使用说明、索引与任务事实一并提交，仍缺少验收来源时保持待验收事实。核对实际提交内容及精确 SHA，再在既有授权内推送；功能验收结果不能提前填入提交。
4. 查询并核对实际远端及 CI，记录可追溯的提交对象、运行对象、执行范围和结果入口。不以命令返回成功、分支上的绿色标记、旧运行或其他 SHA 的结果代替当前候选验证；必要结果缺失或失败时按[整改复验流程](#评审发现与整改复验)处理。
5. 具备必要结果后，以精确功能 SHA、完整单元结果、验证及评审证据、支持边界和仍留待后续证明的事项提交人工验收。只有针对明确对象及范围的人工确认才能形成验收事实；提交推送或 CI 通过本身不能代替。

人工验收后使用[验收记录与交付收尾](#验收记录与交付收尾)；未完成必要收尾不报告交付完成，也不据此进入下一单元。

## 验收记录与交付收尾

以下操作落实已确认的唯一记录来源及一次限定提交例外。记录格式及命令见[控制面机制](03-研发控制机制.md#公开命令与记录字段)，不预写执行或 CI 结果。

1. 核对人工确认是否明确对应本单元的精确功能 SHA、范围及必要证据，保存日期与可追溯的原始确认来源。来源含糊或输入已变时只确认受影响事项，不猜测“已验收”，也不将代码的新输入沿用为已获批准。
2. 将验收事实写入仓库任务记录，关联功能 SHA、必要验证及评审证据；索引依据该唯一来源调整[活动与归档入口](01-文档维护.md#归档操作与验证)。仍有效设计、未解决问题和待完成收尾事项保持入口，不随功能获验收而隐藏。
3. 核对例外提交只包含验收记录、相应状态和索引；执行完整适用的文档及流程检查，再按既有授权完成一次限定 `doc:` 提交推送。不为本次记录重写功能提交，也不夹带尚未获确认的合同、代码或规范变化。
4. 从 Git 提交元数据识别记录提交 SHA，查询并核对其实际远端、文档门禁与对应 CI 输入、范围及结果。记录保存获验收功能的来源和证据，不需把自身提交 SHA 或尚未产生的 CI 结果预写入自身，也不为回填收尾 CI 再生成独立文档提交。
5. 收尾缺少必需结果或失败时保留未完成事实，按[整改复验流程](#评审发现与整改复验)定位处理；人工验收与收尾结果分别报告。若只需再次修改验收文档而超出本单元一次例外，先取得限定修正授权，不夹带无关代码伪装功能提交；实际功能改变时须重新验证及确认新的功能对象。
6. 完成必要核对后，报告精确功能 SHA、记录提交 SHA、实际远端及对应 CI 证据和当前单元结论。只报告已经证明的范围，整体产品或后续验证仍未完成时明确保留；满足[验收后推进原则](#已确认的验收后推进原则)后才进入下一单元。

仓库保存批准来源及任务事实，当前 Git、CI 和收尾结论由实际对象核对；这不建立另一套人工审批状态，也不通过反复保存“最新 CI 通过”产生无穷提交。

## 流程与记录验证

第五层落实以下可判定检查及隔离正反例，语义判断仍需有效目标、设计和场景证据。已实现子集及实际执行见任务证据，Git、CI、来源真实性和完整单元结果不能只靠字段检查证明。

| 情形 | 检查或评审要求 |
|---|---|
| 当前任务记录简短但信息充分 | 引用有效基线，目标、变化与验证可核对；不因未复制完整设计或未细化全部未来任务而拒绝 |
| 整体目标缺失、引用失效或任务缺少目标关联 | 对应引用及覆盖检查识别缺口；字段非空不证明任务与目标匹配，语义对应仍需评审 |
| 实现依赖的合同或前置决定尚未明确 | 标明依赖及影响，不把记录占位当作设计就绪或授权依据 |
| 滚动细化遗漏交付结果或掩盖跨任务影响 | 对照有效目标、整体路线和依赖评审；不能只证明当前局部实现可运行 |
| 计划或输入已变而仍沿用旧覆盖和验证结论 | 核对真实变更、规则覆盖及证据适用性；不能仅凭旧清单或旧结果报告当前任务通过 |
| 中断后任务指向错误对象、前沿过期或证据属于旧输入 | 引用和对象匹配检查识别可判定冲突，独立核对真实工作区及影响；不能仅凭恢复记录格式正确继续报告通过 |
| 交付单元有内部步骤通过，但完整结果或必要证据缺失 | 对照单元退出条件评审，不把内部任务进度当作完整单元已经可验收 |
| 无人工验收来源却被标为已验收或按已验收任务退出活动入口 | 对应状态及来源检查识别缺口；验收事实仍须核对来源和输入，不能以 CI 或 Agent 声明替代 |
| 沿批准路线继续或错误越过推进边界 | 具备验收、必要收尾及既有路线授权时不强加普通启动确认；缺少这些前提、跨越未确认层次或新增重大取舍时识别阻断 |
| 整改只改报告、遗漏复验或将登记例外当作批准 | 核对实际整改对象、输入、完整适用结果及有效决定；对应覆盖和来源检查识别缺口，语义及风险接受仍需证据评审 |
| 候选提交超出任务或授权范围，验证后内容已变 | 核对真实差异、输入及授权来源；范围和对象检查识别可判定冲突，不能只凭任务标签或旧验证结果放行 |
| 远端或 CI 未对应当前候选，必要检查缺失或失败 | 核对精确对象、实际执行与结果；旧 SHA 的成功、空任务或跳过必需检查不能证明当前候选通过 |
| 有效人工确认和限定验收记录提交 | 来源、功能 SHA、范围及索引可核对；不因功能已验收就假设记录提交的远端与 CI 已通过，也不强求提交自引用 |
| 验收来源缺失、精确对象不符或记录提交夹带其他变更 | 对应来源、对象及差异检查识别违规；字段齐全不证明确认真实，来源仍需核对 |
| 功能已获验收但收尾失败、归档隐藏待处理事项 | 分别保留验收事实与收尾结果，未完成事项保持可见，不能报告完整交付或提前推进下一单元 |

第五层固定记录格式、识别方式、路由及执行门禁，验证上述合法场景与隔离反例；不由当前格式核对代替这些机制。第四层确认不自行生成另一套审批状态或扩大具体任务授权。
