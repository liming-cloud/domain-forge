# 总体架构

本页解释仓库的分区、模块依赖和 DDD 分层为什么这样划分。可检查的规则在[规则卡](../rules/00-索引.md)，各组件的合同在[组件参考](../reference/components/)，构建与门禁在[工程与构建](../reference/工程与构建.md)，范围与进度见产品定义（平台仓库 `docs/platform/产品定义.md`）与路线图（平台仓库 `docs/platform/路线图.md`）。

## 仓库分区

```text
platform/
  pom.xml、mvnw、.mvn/         # 内部 parent、BOM 及聚合入口
  domain-forge-build-rules/    # 统一架构规则与 Checkstyle 配置
  domain-forge-bom/            # 只管理依赖版本
  shared/                      # 单个 JAR，org.domainforge.shared 一个包
  framework/domain-forge-*/    # 十三个组件，见下表
  services/iam/                # 四层业务服务（外加 bootstrap）
  services/gateway/            # API 网关（只有 bootstrap 与 infrastructure）
  templates/ddd-service/       # 生成一个本系统业务服务
deploy/、scripts/、docs/       # 部署资产与运维脚本、端到端验证脚本、当前有效结论
```

模块目录等于 artifactId；shared 不下设 Maven 模块或预建子包，只放已有领域标识与公共类型（如 CurrentSubject、两个失败基类，HTTP 分派留在 web-support）；源码合并时同步引用，不留旧坐标转发壳。Maven 层级、版本与门禁见[工程与构建](../reference/工程与构建.md)，依赖版本只有一个管理来源（[B-02](../rules/03-技术与构建.md#b-02-只用稳定版本版本只有一个管理来源)）。

## 组件与依赖

普通能力先一个 JAR，通过公开接口及依赖注入使用；仅有业务语义转换时才定义服务自己的端口（[S-08](../rules/02-系统设计.md#s-08-出口业务语义建接口通用能力直接用)）。原生事务、权限注解与 SPI 直接使用，不再包装同义接口。

| 组件 | 职责（合同见组件页） |
|---|---|
| [web-support](../reference/components/web-support.md) | 失败分派与 Problem Details；HTTP 响应构造留在本组件 |
| [persistence](../reference/components/persistence.md) | MyBatis-Plus、Flyway、附加数据源；本地事务用 Spring 原生入口 |
| [cache](../reference/components/cache.md) | Redisson 缓存、可选 L1、Lua、锁 |
| [access-control](../reference/components/access-control.md) | Sa-Token 会话／权限执行、默认拒绝、Same-Token 校验 |
| [config](../reference/components/config.md) | Nacos 动态配置快照 |
| [service-call](../reference/components/service-call.md) | Feign 调用的身份与链路传递、超时、失败分类 |
| [messaging](../reference/components/messaging.md) | 同事务 Outbox、中继、消费去重、RocketMQ 传输 |
| [scheduling](../reference/components/scheduling.md) | 任务登记，调度由 PowerJob 负责 |
| [tracing](../reference/components/tracing.md) | Micrometer Tracing＋OpenTelemetry，`X-Trace-Id` |
| [file-storage](../reference/components/file-storage.md) | 本地或 S3 兼容存储，文件信息同事务提交 |
| [notification](../reference/components/notification.md) | 短信发送与验证码 |
| [idempotency](../reference/components/idempotency.md) | `@Idempotent` 与 `Idempotency-Key` |
| [defaults](../reference/components/defaults.md) | 统一加载各组件的默认配置 YAML（最低优先级） |

组件依赖单向无环（[S-24](../rules/02-系统设计.md#s-24-组件之间无环依赖指向更稳定的一方)），下图取自各模块 POM 的 `domain-forge-*` 依赖；组件不依赖 IAM、业务表、模板或 Harness，shared 不依赖组件与服务。

```text
idempotency   → access-control、cache、web-support
access-control → cache、web-support、defaults
notification  → cache、web-support
file-storage  → persistence、scheduling、web-support
messaging     → persistence、tracing
scheduling    → tracing
tracing       → config、defaults
cache、config、service-call → defaults
persistence、web-support、defaults → 无其他组件
IAM           → access-control、config、persistence、scheduling、tracing、web-support
网关          → cache、config、tracing（WebFlux，不用 Servlet 版组件）
业务 domain   → 只用 shared 中的纯 Java 领域标识
调用服务 infrastructure → 本服务 Feign、Nacos、shared 传输类型、service-call 公开接口
```

三种消费方式：**组件**由内部 BOM 固定版本、显式添加所需模块；**服务**同系统部署，调用服务的基础设施经 Feign／Nacos 请求 IAM 的当前权限；**模板**在完整源码中生成一个服务骨架并验证接入，不现场注入隐藏源码，不预建业务聚合。

## DDD 边界与代码映射

采用轻量 CQRS：命令与查询按职责、合同和模型分开，默认同库、同步方法调用；独立读库、异步投影、事件溯源、命令总线都不是默认依赖（[S-09](../rules/02-系统设计.md#s-09-纯查询走短路径)）。IAM 是一个身份权限限界上下文、一个服务，账号／会话、组织／成员、角色／授权、菜单声明及审计是内部职责，不因包名拆成多个上下文；业务客户、员工等模型属于消费项目，与身份关联时用稳定标识，不共用可变 User 实体。网关是技术入口，组件是技术能力，都不等同于领域上下文。

默认一个服务一个 Maven 模块，以包约束上下文边界；单上下文服务直接以服务根包为 context，其下按 [S-01](../rules/02-系统设计.md#s-01-五个职责各管各的事) 的五个职责包布局。IAM 的实际布局：

```text
platform/services/iam/src/main/java/org/domainforge/iam/
├── bootstrap/            # 启动、配置与适配器接线；不承载业务判断或 SQL
├── interfaces/           # http（Controller）、message（入站消息）、job（任务触发）
├── application/          # command/<usecase>、query、event、port（外部能力接口）、contract/event
├── domain/               # model/<aggregate>、policy、service、repository、event
└── infrastructure/       # persistence、query、acl/<external-system>、messaging
```

`src/main/resources` 下有 `db/migration/`（本服务拥有的迁移）和 `contracts/`（协议源，与 Java 表示只选一种权威源）。子包只在已有内容确有不同职责时增加，不预建空包（[C-01](../rules/04-源码质量.md#c-01-按真实职责放代码不建空目录)）。bootstrap 属于本 context，可依赖本上下文四类实现，四类职责不得反向依赖它；启动类须显式覆盖本服务根包的组件发现范围并验证真实启动。将来多个上下文同部署时，各自使用互不嵌套的兄弟根包。结构检查只证明依赖方向，职责语义靠用例与评审，不能以目录齐全证明 DDD 正确。

| 对象 | 必须承担 | 不应承担 |
|---|---|---|
| 聚合根 | 维护一致性边界内的不变量，提供业务行为；引用其他聚合时用 ID | 按表机械生成；暴露任意 setter；调用远程 SDK／发 MQ |
| 领域策略／服务 | 真实业务判断；应用准备外部事实后传入 | 万能 DomainService；隐藏网络调用 |
| 应用 Handler | 授权、业务编排、调用规则所有者、事务与失败结果 | 重复聚合规则；直接调用 Mapper／SDK |
| Repository | 按聚合加载、保存，明确不存在／并发冲突语义 | 充当报表查询或返回 PO／IPage（[R-14](../rules/01-需求与领域建模.md#r-14-仓储只针对聚合根)） |
| Query 合同 | 按用例表达筛选和展示数据，技术无关 | 暴露 SQL、Wrapper、ORM 分页对象或绕过权限 |
| 防腐适配 | 翻译外部模型、协议、状态和失败语义 | 取代本地业务决策；把外部错误当作本地成功 |

模型与 PO 分开，不因同字段而合并（[S-13](../rules/02-系统设计.md#s-13-领域持久化接口和事件对象各司其职)）。客户端只提供命令输入，不直接提交可保存的聚合或 PO。

### 命令与查询路径

命令：`HTTP／消息入口 → CommandHandler → 聚合行为 → Repository 合同 → 持久化实现`。Command 表达业务意图，Handler 负责授权、编排与事务边界（[S-07](../rules/02-系统设计.md#s-07-用公开应用方法作为用例入口)），聚合维护不变量；简单维护若没有复杂不变量，允许轻量用例而不伪造聚合，一旦存在状态约束、并发或业务决策就须有明确所有者。

纯查询：`Controller → Query 合同的读取实现 → SQL／Mapper → ReadDTO`。接口是边界，不是额外执行层；没有编排时不再包一层只转发的 Handler（[S-09](../rules/02-系统设计.md#s-09-纯查询走短路径)），授权与数据范围按 [S-10](../rules/02-系统设计.md#s-10-查询不改业务状态并负责数据范围) 在查询用例边界执行。

| 查询类别 | 路径 |
|---|---|
| 本上下文列表、详情、筛选、统计 | 读取实现直接用本上下文 SQL／Mapper 返回展示结果，可联查本上下文拥有的表，不加载领域模型 |
| 有权限及数据范围要求 | 查询用例边界授权，SQL 用可信的服务端范围约束；默认拒绝及范围过滤须真实验证 |
| 需要跨源编排、资源授权决策或业务判断 | 增加确有职责的查询 Handler；需要领域规则时调用规则所有者 |
| 需要其他上下文数据 | 使用公开查询合同或合法投影，不同库联表读取其私有数据 |

### 领域事件与集成事件

| 类别 | 所有者与用途 | 可靠性责任 |
|---|---|---|
| 领域事件 | `domain/event`，本上下文业务变化；聚合返回或暂存，应用处理 | 产生时可能尚未提交，事务内处理随主事务回滚 |
| 集成事件 | `application/contract/event`，愿意向其他上下文承诺的已提交事实 | 应用选择字段并映射；需可靠发布时与业务同事务写 Outbox（[S-23](../rules/02-系统设计.md#s-23-集成事件经同事务-outbox-发布)） |
| 任务／消息命令 | 要求接收方执行动作，有明确处理者与结果合同 | 接收成功不等于业务完成，同样需要重复与恢复设计 |
| 安全审计／普通观测 | 各自有独立责任 | 不能用日志替代审计 |

事件用过去式业务名称和不可变数据，不携带聚合对象、凭证或全部表字段；集成事件信封含稳定事件 ID、类型、合同版本、来源和发生时间，重发同一事件不生成新 ID。只有真实订阅者或业务副作用才引入事件，不建强制继承的事件基类或统一命令总线。发布与消费流程：

```text
命令用例 ─ 同一个本地事务 ─ 改变聚合并保存 ─ 处理必须同事务的内部反应 ─ 映射公开事件写入 Outbox ─ 提交
中继读取已提交 Outbox → 发布消息 → 记录发送结果；消费者本地去重记录＋业务变更同事务提交 → 确认接收
```

按至少一次设计，不承诺全链路 exactly-once；投递、重试、顺序与死信合同见[消息与 Outbox](../reference/components/messaging.md)。[领域事件与集成事件的区别](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation)，[Transactional Outbox](https://microservices.io/patterns/data/transactional-outbox.html)。

### 事务边界与防腐

事务规则见 [S-11、S-12、S-15、S-20、S-21、S-22](../rules/02-系统设计.md#事务与一致性) 与 [P-09](../rules/05-持久化.md#p-09-并发约束由数据库保证)。IAM 的禁用、撤权、改密及旧会话失效不能改为“后台最终失效也算成功”，SQL 与会话状态的协调见[身份权限参考](../reference/身份权限.md#sql-与会话状态的生效合同)；关键安全审计与业务同事务（[A-10](../rules/07-安全与访问控制.md#a-10-关键管理操作与审计同事务)）。当前不引入分布式协调器；跨服务最终一致优先评估真实业务状态＋同事务 Outbox。

防腐层默认是消费方上下文内的适配器，不新增防腐微服务：接口归需要能力的一方，用本地业务语言返回本地事实与失败结果，外部 DTO、SDK、状态码留在实现中（[防腐层模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer)）。

```text
应用用例 → application/port/<业务所需能力> ← 实现 ─ infrastructure/acl/<外部系统>（协议、数据翻译、超时／拒绝／未知结果翻译）→ 外部公开合同
```

若通用短信或文件 API 已完全满足调用目的，直接使用其公开接口，不额外建没有翻译职责的 SmsPort＋SmsAdapter。入站集成事件由 `interfaces/message` 解码后转成本地命令，来源不自动获得本地权限。

**结构必须通过真实例子证明**：模板至少有命令、纯查询、需要编排的查询三条经过验证的路径；领域行为、事务回滚、聚合往返、并发冲突和外部失败有实际断言。架构检查只约束可判定边界（领域引 SDK、应用引 Mapper、引用其他上下文私有类型、组件依赖服务等必须失败，合法 bootstrap 与 Query 实现应通过），业务语义由评审负责。

## 部署与调用方案

单套系统内部共享 Sa-Token Redis 会话，IAM 独占身份业务表。后端默认 HTTP，TLS 在 Nginx 终止（[O-08](../rules/08-配置与运行.md#o-08-tls-在入口终止后端独立鉴权)）；纯登录校验不调用 IAM，权限经调用服务自身 Feign 读取当前用户，失败拒绝、不跨请求缓存允许结果。部署用固定镜像的 Compose，默认组合 Nginx、网关、IAM、PostgreSQL、Redis、Nacos、RocketMQ、PowerJob，Nginx 只做边缘，路由、登录前置校验、限流与 Same-Token 由[网关](../reference/components/gateway.md)负责；服务清单、端口与备份见[部署参考](../../deploy/README.md)。

## 模板与源码复用

业务项目以同仓库源码复用为主（2026-10-23 决定）：模板在 `platform/services/<name>` 生成服务，继承内部 parent，加入 `services` 聚合，自动执行架构规则；不要求发布组件到私有仓库（[B-10](../rules/03-技术与构建.md#b-10-业务服务在本仓库内以源码复用平台)）。以干净源码构建、部署和一个模板服务接入 IAM 证明可用，使用方式见[服务模板使用说明](../../platform/templates/ddd-service/01-使用说明.md)。
