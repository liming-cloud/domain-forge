# 企业级 DDD 微服务脚手架：产品定义

本文是首版的完整承诺。先交付哪些（MVP）、当前进度和阶段计划见[路线图](02-路线图.md)。

## 产品目的

Domain Forge 是公司研发的企业级领域驱动设计（DDD）微服务脚手架，为后续真实业务产品提供可持续复用的研发底座。交付主体包括可运行的通用基础组件、登录注册与身份权限等基础后端、业务服务起步模板及部署参考方案，使团队能够快速、准确地研发高质量、可靠且满足性能目标的产品。IAM 与业务服务共同组成一套业务系统；复制仓库用于另一套系统只是研发方式，不建立运行时项目身份。

默认从完整源码起步，在同一仓库按模块研发，使用内部 BOM、组件公开接口和服务模板；不要求先发布组件到私有仓库。DDD 用于划定业务规则、依赖和数据责任；微服务按实际职责、独立发布与运行需求划分。具体组织见[整体研发结构](../explanation/总体架构.md#ddd-边界与代码映射)，工程技术基线见[技术与构建规范](../rules/03-技术与构建.md#技术栈)。

研发规范与自动检查同样是交付物：保存产品方向、设计依据、规范与原则，指导 AI 编码工具按任务加载必要上下文、实现、验证，并让人工通过 PR 快速核对关键决定与证据。其有效性由真实研发任务证明，文档数量、检查数量或 CI 通过本身不代表产品正确或交付完成。

## 已确认的产品边界

| 事项 | 产品要求 |
|---|---|
| 服务对象 | 多个需要持续研发的业务项目；新零售是首个预期使用领域 |
| 复用方式 | 完整源码复用；业务服务使用组件接口，模板创建真实服务骨架 |
| 运行与数据责任 | 一套系统的 IAM 管理账号权限，各服务拥有业务数据；无 projectId 或跨项目认证协议 |
| 基础身份权限 | 账号密码登录与注册、账号、角色、组织结构／部门、操作权限、菜单按钮、数据范围和必要审计，能够供业务服务接入 |
| 规范强度 | 统一强规范；规定适用条件和统一落点，例外由人工确认，局部算法保留实现空间 |
| 产品交付 | 可运行的基础组件与后端服务、DDD 业务服务起步模板、部署参考方案，以及服务研发和人工审核的规范、流程与验证方法；完成状态单独记录 |
| 具体设计顺序 | 从产品场景推导必要设计与验收标准，再按既有规范实现、验证和评审；每个单元须能说明其产品用途 |
| 审阅方式 | 人工通过 PR 评审核对设计、实现与验证；需要人工决定的事项见[开发流程](../workflow/01-开发流程.md#需要人工决定的事项) |

## 身份权限交付形态

- 平台交付已确认身份权限功能的后端实现、接口文档、接入说明与接入验证，不交付基础管理前端。
- 注册是首版身份能力，不能用账号管理接口代替注册场景验收。注册采用邀请注册，初始组织与权限、账号启用规则见[身份权限模型](../explanation/身份权限模型.md)与[身份权限参考](../reference/身份权限.md)；本次范围确认不预定公共匿名注册、手机号登录或短信注册。
- 组织结构、成员归属、角色与权限关系须有真实后端行为；具体组织层级和管理规则在 IAM 模型中明确。账号、角色、组织／部门和权限等管理页面由各业务项目自行实现。
- 不交付管理前端不删减已确认的菜单按钮、数据范围等后端能力；界面展示和交互由业务项目负责，后端鉴权仍由相应后端执行，不能以页面隐藏代替访问控制。
- 后续验收以真实后端接口和消费项目接入场景验证完整能力，不以平台自带管理页面作为交付前提。接口合同见[身份权限参考](../reference/身份权限.md#接口与实现要点)，验收用例见[验证索引](../reference/验证索引.md)。
- 关键安全管理写入的审计失败责任见[安全管理审计失败原则](../rules/07-安全与访问控制.md#a-10-关键管理操作与审计同事务)，不由后端交付形态推导审计必然完整或可以省略必要审计。

## 新项目起步交付

- 首版提供可运行的轻量业务项目起步模板，包含启动、配置、平台依赖和最小接入验证。
- 起步方式为完整源码构建，模板生成本系统中的业务服务；不把私有仓库发布或两种外部 parent 消费作为例行前置。
- 起步模板须在干净源码副本中生成一个服务并完成构建、启动和接入；不能只交付静态目录示例。
- 模板按[模板方案](../explanation/总体架构.md#模板与源码复用)组织 DDD 服务工程，具体命令及接入场景在对应单元细化；技术范围遵守[主技术栈](../rules/03-技术与构建.md#技术栈)。通过代表性用例证明规则归属、依赖方向和可扩展性，不以生成空分层目录替代验证。

## 通用能力交付承诺

- 共同选定首版通用能力清单；纳入清单的每项能力均提供可运行、可验证的基础对接，不以规范说明或预留接口代替实现。
- 平台隐藏基础接入复杂性，并提供后续业务特性的扩展能力；扩展机制与清单见[扩展路径](../reference/扩展路径.md)与 [ADR 0008](../decisions/0008-组件扩展机制.md)。
- 能力是否纳入首版，以已确认清单为准；纳入某类能力不等于已经确定具体框架、服务商、支持实现数量或高级特性。

## 首版通用能力清单

首版除基础身份权限外，还须交付：

1. 关系数据持久化与数据库迁移。
2. 缓存。
3. 文件存储与访问。
4. 异步消息发布与消费。
5. 定时任务。
6. 通知发送。

以上六类均须满足通用能力交付承诺，不属于只写规范、等待业务需求后才实现的候选项。各类基础功能、支持范围及验收场景仍需细化；已纳入范围不代表已实现或已验收。

首版还包含通用分布式锁、访问限流和请求幂等支持，三者分别列为能力，不混称为缓存；范围见[缓存与额外通用能力](#缓存与额外通用能力)。

运行排障、配置管理、服务发现与统一 API 入口的首版范围分别见[应用侧可观测能力](#应用侧可观测能力)、[运行配置与 Nacos](#运行配置与-nacos)、[服务注册与发现](#服务注册与发现)和[基础 API 网关](#基础-api-网关)。

## 实现支持与扩展范围

- 通用原则：每类能力提供真实可用的默认实现和经过验证的扩展路径；未实际接入的实现不承诺可用。
- 文件存储：以本地存储为默认实现，同时在首版交付 S3 兼容 API 对接。本地存储和 S3 对接均须完成真实实现与验证，S3 不仅是预留接口。
- 文件存储的适用部署条件、S3 支持的操作范围和验证对象仍需明确；本次决定不自动承诺所有服务商、全部 S3 功能或已有数据的自动迁移。
- 其他能力的默认技术方案以本轮明确决定为准，尚未确认者留待后续选择，不从旧仓库继承。

## 文件存储功能边界

- 首版提供上传、下载、删除、必要文件信息与安全访问。
- 文件关联哪些业务对象、谁有权操作哪些文件，由业务规则决定；平台提供的安全存取能力需要支持这一责任划分，授权衔接方式见[文件存储](../reference/components/file-storage.md)。
- 首版不交付独立的文件管理产品，不包含目录、标签、版本、回收站、共享管理及专门的文件管理界面。业务项目可按自身需求扩展，但不因此成为平台首版交付义务。

## 通知渠道范围

- 首版以短信作为通知渠道，默认实现对接阿里云短信并以协议替身验证请求与失败处理；真实发送验证移到首版之后，在提供已审核的账号、签名与模板后执行（2026-11-03 决定，见 [ADR 0019](../decisions/0019-短信真实发送移出首版.md)）。
- 邮件保留后续扩展路径，首版暂不实现，不承诺邮件已经可用。

### 短信与验证码功能边界

- 首版除短信发送外，还提供通用验证码生成、校验、过期及使用限制，供业务复用。
- 业务决定验证码用途和验证成功后的业务处理；平台负责所提供的通用验证码流程。
- 本项不自动承诺手机号登录、短信注册或通知中心；首版注册责任及其待设计边界见[身份权限交付形态](#身份权限交付形态)，验证码组件通过不代替注册业务验收。安全策略、状态保存方式与失败处理见[短信与验证码](../reference/components/notification.md)，验收场景见[验证索引](../reference/验证索引.md#短信与验证码)。

## 异步消息功能边界

- 首版除消息发布与消费的基础对接外，还须提供业务数据保存与消息发送之间的故障恢复能力。
- 业务按平台约定接入后，当业务数据已保存、应用在消息发出前中断时，平台应能够恢复并继续发送对应的待发消息；该场景纳入首版验收。
- 接入前提、事务边界、恢复策略及故障验证方式见[消息与 Outbox](../reference/components/messaging.md)与[验证索引](../reference/验证索引.md#消息与-outbox)。
- 消息重复、顺序及消费者业务处理结果的合同另行明确，不能从发送恢复要求推导出全局只处理一次的承诺。

## 定时任务功能边界

- 首版支持在不重新发布应用的情况下修改任务执行周期、暂停或恢复任务、手动触发任务，并查看执行记录。
- 运行期管理可以复用所选框架的已有能力，不要求自研控制台。
- 框架、管理入口及其权限控制、任务并发与失败恢复语义见[定时任务](../reference/components/scheduling.md)，不把可管理等同于任务业务效果已得到保证。

## 缓存与额外通用能力

- 数据缓存：提供读写、过期、失效及故障处理能力。
- 通用分布式锁：提供供业务显式接入的跨实例互斥支持。
- 访问限流：提供可复用的访问频率控制能力。
- 请求幂等支持：提供通用接入能力，业务仍须明确哪些请求属于同一业务操作及其处理结果的含义。
- 上述能力均纳入首版真实实现与验证范围，分别明确适用边界与验证场景；运行条件、故障语义与业务接入责任见[缓存](../reference/components/cache.md)与[请求幂等](../reference/components/idempotency.md)，不承诺对任意业务自动提供完整保证。
- 本项不改变已确认的验证码使用限制，也不预定各能力必须采用同一种中间件。

## 关系持久化与多数据源边界

- 首版提供基础关系数据访问、单库本地事务和版本化数据库迁移。
- 默认使用一个业务数据源，同时交付经过实现与验证的多业务数据源接入能力，由项目按需启用；支持多数据源不意味着要求项目拆库。
- 每个数据源须明确用途、所属限界上下文和读写权限。上下文、数据库和微服务不强制一一对应；不能以多数据源接入绕过其他上下文的公开合同，直接访问其私有数据。
- 数据源配置与选择属于基础设施职责，领域模型不负责连接配置或数据源切换。
- 多数据源接入不自动提供跨数据源事务。涉及多个数据源的操作须明确各自事务范围、一致性要求及失败恢复责任，不把单库事务保证扩展为跨库保证。
- 本次决定不自动纳入分库分表、分布式事务或任意数据库兼容。技术方案、支持组合与迁移归属见[持久化组件](../reference/components/persistence.md)。

## 应用侧可观测能力

- 首版提供结构化日志、健康检查、指标、链路追踪及真实接入验证，支持业务项目观察应用运行情况和排查请求问题。
- 平台负责应用侧观测数据的产出与对接，并提供接入说明和可复验场景；不能以仅有配置或接口声明代替真实验证。
- 采集、存储、看板与告警环境由业务项目提供和管理；首版不交付默认观测工具组合、常用看板或示例告警。
- 数据合同、关联方式与故障行为见[观测数据](../reference/观测数据.md)与[链路追踪](../reference/components/tracing.md)；本项不替代已确认的身份权限必要审计。
- 普通观测故障对业务可用性的责任见[普通观测故障原则](../rules/09-故障与可观测性.md#f-08-观测故障不影响业务)，接入范围与正常验证要求不因故障时允许数据缺失而删减。

## 运行配置与 Nacos

- 首版接入 Nacos 配置中心，提供集中配置管理与下发能力；明确支持的配置项可以无需重启生效，不承诺所有配置均可动态更新。
- 基础外部化配置、环境注入和启动接入检查仍需提供。Nacos 管理的配置以已确认的[配置权威前提](../rules/08-配置与运行.md#o-09-nacos-发布内容是权威)为准；启动引导、其他必要输入及动态更新范围见[配置中心](../reference/components/config.md)，不建立平行的权威配置来源。
- 配置读取、变更生效和更新执行失败须完成真实场景验证。区分启动与运行阶段的读取、连接中断及应用执行失败，不能仅以收到变更通知作为生效证据；本轮不把 Nacos 发布内容错误作为需另建通用处理机制或强制验收的场景。
- 配置管理与服务注册发现分别定义接入和验证合同，后者范围见[服务注册与发现](#服务注册与发现)。
- Nacos 的版本、集成方式、部署前提、访问隔离和敏感配置处理见[配置中心](../reference/components/config.md)与[部署参考](../../deploy/README.md#配置中心)。本项不改变已确认的定时任务运行期管理范围。

技术核查（2026-09-29）：Nacos 官方文档分别提供配置客户端和服务注册客户端，并说明应用需在配置变更通知后更新自身状态。本次仅据此区分能力边界，未验证项目实现或选定版本。[Nacos 官方 Java SDK 文档](https://nacos.io/en/docs/latest/manual/user/java-sdk/usage/)

## 服务注册与发现

- 首版提供 Nacos 服务注册与发现的基础对接，供业务项目按需启用。
- 服务注册、服务发现及实例上线、下线等变化须完成真实场景验证；不能仅凭注册记录存在就认定消费方已正确发现服务或感知实例变化。
- 项目与环境隔离、发现结果更新条件，以及无可用实例、注册中心连接中断时的行为见[跨服务调用](../reference/components/service-call.md)与[API 网关](../reference/components/gateway.md)。
- 本项不强制项目拆分为微服务；服务边界、通信方式和具体接入方案按[总体架构](../explanation/总体架构.md)与规则卡设计。统一 API 入口的交付边界见[基础 API 网关](#基础-api-网关)。

## 基础 API 网关

- 首版交付可运行的基础 API 网关，提供统一入口和路由转发，并对接已确认的身份校验、限流与链路追踪能力。
- 网关不承载业务逻辑。业务权限和数据范围仍由相应后端执行，不能把通过网关身份校验等同于获得业务访问权限。
- 正常转发、身份校验拒绝、限流、链路关联及下游故障须纳入真实场景验证，合同见[API 网关](../reference/components/gateway.md)，验收用例见[验证索引](../reference/验证索引.md#api-网关)。
- 网关框架、部署方式、身份传递合同和策略配置方式的取舍见 [ADR 0012](../decisions/0012-API网关的取舍.md)。

## 运行与部署交付

- 首版提供版本化制品、可复现的本地／联调启动方案和部署说明。
- 在运行基线之外，针对 Linux 主机 + Docker Compose 交付生产部署参考方案，包括部署模板、升级与回退操作，并完成真实场景验证；首版不因此同时承诺 Kubernetes 部署模板。
- 生产参考方案除应用服务外，同时提供首版所需数据库、缓存服务、消息中间件、Nacos 等可自建依赖的部署模板；具体组件见[部署参考](../../deploy/README.md)，不从旧仓库继承。观测环境的交付边界仍见[应用侧可观测能力](#应用侧可观测能力)。
- 按各依赖的数据职责提供必要的持久化配置、备份与恢复操作，并以真实场景验证恢复结果；不能仅凭容器启动或备份文件存在就认定恢复成功。数据范围、前提和验收标准见[部署参考](../../deploy/README.md#备份与恢复)与[验证索引](../reference/验证索引.md#部署与闭环)。
- 首版生产参考方案采用可恢复的单机基线，允许维护停机以及故障后按操作说明人工恢复；持久化、备份恢复、升级与回退仍须验证，不能因允许人工恢复而省略验证。
- 首版不交付跨主机自动故障切换方案，不承诺高可用、零停机或零数据丢失。支持的系统与工具版本、部署明细及恢复操作的适用前提见[部署参考](../../deploy/README.md)，并如实记录恢复耗时和可恢复的数据范围。
- 环境前提、支持范围及升级与回退条件见[部署参考](../../deploy/README.md#升级与回退)。应用版本回退与数据恢复分别说明，不承诺任意数据库变更均可自动逆转。
- 实际生产环境、发布执行与持续运维仍由业务项目负责。本次决定只确定参考方案的交付责任，不授权操作生产环境，也不要求平台代运营业务项目。

## 性能验收边界

- 首版须明确平台性能测试的资源配置、典型场景、数据量、负载方式和性能门槛，再进行真实压测与验收；不能只记录测试结果而没有通过标准。
- 场景、指标和门槛见[性能基线](../platform/性能基线.md)与 [ADR 0021](../decisions/0021-性能基线的取舍.md)，形成可复验的基线；不在缺少负载与资源前提时承诺任意吞吐量或响应时间。
- 业务项目另行确定并验证自身的业务性能目标。首版平台交付不绑定首个新零售产品的并发、业务数据规模或响应时间硬指标，也不能将平台基线直接等同于业务产品已通过性能验收。

## 使用者需要完成的旅程

1. 创建项目：理解平台能力与使用前提，使用轻量起步模板建立可运行工程，选择并固定所需能力版本。
2. 接入平台：配置平台服务和组件，理解成功、拒绝及依赖故障的可观察行为。
3. 开发业务：从业务目标推导场景、模型、系统边界和实现任务，按照统一规范完成验证与交付。
4. 扩展能力：判断变化属于项目业务还是通用平台，找到受支持的扩展位置并验证兼容性。
5. 部署运行：依据受支持的生产部署参考方案明确环境前提，完成项目部署与运行验证，承担项目自身的生产运维责任。
6. 升级维护：识别版本差异、迁移要求、失败处理和回退条件，保持项目自身发布节奏。

这些旅程用于组织产品交付单元，并推导必要设计、合同和验证。实际命令、接口和运行结果须由对应实现提供，不能用规划说明替代验证。

## 产品成功标准

- 团队能从完整源码构建、部署一套系统，并生成业务服务接入已有基础能力；账号、权限与业务数据责任清楚，不依赖私有组件仓库或隐藏测试源码。
- 代表性用例能够从目标经过 DDD 设计、实现、检查和评审形成可验收结果；领域规则有明确所有者，代码保持简洁，业务变化通过公开合同与局部修改实现，不能以目录分层或类数量证明设计质量。
- 平台的登录注册、组织、角色、菜单按钮及数据范围等后端能力能够被业务服务完整消费，验证正常使用、越权拒绝、状态变更生效以及依赖失败。
- 已承诺基础组件均有真实实现、实际服务接入及必要失败与扩展场景；可靠性、部署恢复和性能按本文相应边界实测，不能用构建成功或启动耗时替代。
- 普通业务研发可以复用既定规范。以真实需求实现、缺陷修复和能力扩展任务验证 GPT-6 等 AI coding 工具的上下文使用、代码正确性和持续交付效果；记录完成耗时、返工与漏检问题、人工审核负担，具体比较方式和门槛在相关验收设计中固定，未实测前不宣称提效。
- 人工能够从精简任务摘要定位需求、关键设计、实际 diff、验证证据和未解决风险，作出验收判断；规则保留唯一有效正文，新增或变更检查须能解释所防缺陷与产品用途。
