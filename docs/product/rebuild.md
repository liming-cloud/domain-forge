| 层 | 交付与退出条件 |
|---|---|
| 1 产品与使用目标 | 产品定位、首版能力、旅程、责任和成功标准；人工确认 |
| 2 系统设计规范 | 需求、统一语言、上下文、职责依赖、数据责任及扩展方法；条件、产物和审阅方法明确；人工确认 |
| 3 工程规范 | 源码、持久化、接口、安全、配置、故障、观测及测试；规则有范围、正反例和验证责任；人工确认 |
| 4 研发与文档流程 | 任务、恢复、按需加载、评审整改、验收及 Git；普通任务可执行，重大决定有责任；人工确认 |
| 5 整体验证 | 完成通用及具体框架／合同／迁移／运行装配校验适配、有效反例、四类使用路径及必要审阅；固定候选，经授权核对 Git／CI，人工验收整套控制面 |
| 6 持续研发 | 文档控制面验收及必要收尾完成后，按交付单元开展脚手架与平台的设计、实现、评审和验证；真实构建、扫描、运行、部署、升级及独立消费随适用单元验收 |

第六层是使用已建立控制面开展稳定研发的阶段。按[本轮目标澄清](../tasks/control-plane-verification.md#目标与输入)，先细化当前交付单元的目标、必要设计与合同，再实现、验证和验收；上表所列真实结果是相应单元的交付责任，不要求在研发开始前完成全部产品能力。控制面在研发中按实际缺口维护，重大决定和质量责任继续执行。

## 文档形成原则

- 产品定义说明目标与范围；规范保存长期边界；设计与合同描述受支持实现；任务保存前沿、决定和必要证据。
- 每条规则只有一个有效正文。人从[编号索引](../index.md#人工阅读顺序)通读，Agent 从任务触发按需加载小节；不复制全文。
- 强规则明确条件、允许情形和验证责任：可判定约束有真实正反例，语义有源码及场景评审。
- 功能变化同步维护受影响设计、合同、说明、索引和任务；普通进度不扩写统一规范。
- 基线确认、技术通过、人工验收和 Git 收尾分别核对；旧输入摘要不代表修改后的正文已批准。
- 清理失效材料遵守[生命周期](../workflow/document-control.md#已确认的文档生命周期原则)，有效来源和未完成责任不随瘦身消失。
