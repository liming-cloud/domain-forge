- 产品定义说明目标与范围；规范保存长期边界；设计与合同描述受支持实现；任务保存前沿、决定和必要证据。

- 强规则明确条件、允许情形和验证责任：可判定约束有真实正反例，语义有源码及场景评审。
- 功能变化同步维护受影响设计、合同、说明、索引和任务；普通进度不扩写统一规范。
- 基线确认、技术通过、人工验收和 Git 收尾分别核对；旧输入摘要不代表修改后的正文已批准。
- 清理失效材料遵守[生命周期](../workflow/01-文档维护.md#已确认的文档生命周期原则)，有效来源和未完成责任不随瘦身消失。

### 前置依赖与首个可用闭环

此表表示研发与验收的前置条件，不等同于 Maven 传递依赖。编译方向见[组件依赖与消费边界](../architecture/01-总体架构.md#产品交付单元与依赖)；共用 Redis／客户端不增加组件间任意依赖。

| 交付对象 | 必需前置 | 不应被迫等待／不能混淆 |
|---|---|---|
| 最小模板及 IAM 首个切片 | R2-01 收尾；新结构规则；实际所需 Web、单库持久化／事务、配置与诊断；access 技术无关合同及后端接入随切片同步 | 不等全部组件、完整网关、通用任务／消息或 CI 百分比目标；外部消费尽早验证 |
| 登录和会话 | IAM 定义账号／调用维度、失败尝试限制、恢复策略和跨实例状态，配合固定身份技术；若复用 rate-limit 子集，该子集必须先到位 | 通用限流是执行能力，IAM 拥有登录策略；通用限流测试不能代替正常登录、超限、恢复、依赖故障及跨实例绕过测试 |
| 注册／账号开通 | 先固定允许谁注册、凭据与初始组织／权限、合法管理主体初始化；管理授权及审计从首个管理命令开始 | 仅在选定注册策略使用短信时才前置 notification＋verification-code；不暗中选择短信自助注册 |
| 组织／角色／菜单／数据范围 | 账号及最小授权闭环；可信身份、当前权限生效及数据所有权 | 菜单可见不等于 API 授权；完整 RBAC／数据范围不作为最初启动模板的依赖 |
| 网关 | 已稳定的 access 合同／gateway 适配及后端独立授权，实际发现、限流和观测 | 网关不提供后端免检；后端消费验证无需等网关才开始 |
| Outbox／消息恢复 | 先有传输合同与真实传输实现，再组合业务同资源事务及持久化接入 | 不依赖 IAM、通用缓存或分布式锁；非必需审计不强制加入使业务回滚的 Outbox |
| 短信／验证码 | 先定短信供应商适配及结果，再定验证码状态原子性、过期／次数及一次消费 | 验证码使用 notification，不反向依赖 IAM；幂等外部副作用不以 Redis 锁替代 |
| 文件、缓存、锁、幂等、调度 | 分别固定真实能力合同与默认实现；文件 local／s3 仅依赖自身 API；锁／幂等按保护资源与原子性设计 | 不强制缓存→锁→限流→幂等的组件链；调度不自建通用任务中心 |
| 公共质量规则与 Harness 分发 | 先在平台及最小模板验证规则，再在阶段 4 提取版本制品并做两项目验证 | 不等分发完成才约束 IAM；不把校准夹具／全部过程文档复制给消费项目 |

最早产品闭环采用“账号开通命令 → 登录 → 独立消费项目的受保护查询 → 最小授权变更／撤权 → 原访问被拒绝”。注册策略、权限定义及当前状态生效合同需先批准；不能为了早演示放宽默认拒绝、登录防护、跨实例一致性或审计责任。查询保持 `Controller → 查询合同实现 → SQL／ReadDTO` 的最短合法路径，有资源决策时增加确有职责的用例。
