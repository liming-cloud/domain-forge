# 项目定位与范围

状态：待讨论设计；依赖[已确认需求 C01–C16](00-baseline.md)。负责人：用户；文档整理：AI。评审轮次：R1。

## 产品目标与使用者

Domain Forge 服务于需要反复创建 Java 后端项目的维护者。主要使用者是执行研发任务的 AI，人工负责产品规则、设计取舍和代码评审。产品价值是提供一致的结构、可验证的权限约束和可升级的技术能力，减少新项目重复搭建和维护分叉。

首阶段成果是设计基线。未来首个研发版本的建议目标是：一个新服务能按模板创建、独立构建，接入注册配置、身份认证、操作与数据权限，并使用统一的数据访问和工程规范；验收使用测试夹具，不增加商品、订单等示例业务。

## 使用旅程

| 场景 | 使用者获得什么 | 使用者自行负责什么 | 成功信号 |
|---|---|---|---|
| U01 新建后端项目 | 服务骨架、BOM、组件接入说明、IAM 和网关使用方式 | 真实业务建模、接口、资源归属与权限点定义 | 无需复制公共组件源码即可完成独立消费验证 |
| U02 扩展技术能力 | 独立可选组件、契约说明、集成测试范式 | 选择是否启用、环境参数、业务容错语义 | 未选能力不影响基础服务启动；选中能力有验收证据 |
| U03 升级基础能力 | 版本说明、兼容矩阵、迁移步骤和回退条件 | 评估项目定制及执行项目级回归 | 依赖升级不覆盖业务代码，变更有可追溯 PR |
| U04 AI 开发人工评审 | 任务边界、设计引用、可执行验收条件 | 确认规则、审阅结果、合并与发布 | AI 不自行补齐高影响产品规则；评审对象具体可查 |

## 能力边界

| 类别 | 未来首个研发版本建议范围 | 后续迭代 | 明确边界 |
|---|---|---|---|
| 工程与 DDD | 服务骨架、边界检查、错误约定、配置与迁移、测试及文档 | 更多部署与诊断能力 | 不提供万能领域基类、通用业务 CRUD 或工作流引擎 |
| 服务治理 | Nacos 注册配置、网关、受控服务调用 | 更完整的限流熔断与部署方案 | 不因微服务选型预先引入分布式事务平台 |
| IAM | 已确认的单租户完整 RBAC，以及必要的会话和审计能力 | 新需求触发再设计 | 无前端、委派授权、多租户、SSO/OAuth 产品能力 |
| 数据与缓存 | MySQL、MyBatis-Plus、数据库迁移、Redis 会话与通用缓存接入 | 本地缓存及实际场景优化 | 授权数据缓存需单独设计生效与失效语义 |
| 扩展技术 | 仅明确 ES/S3/Kafka 的边界与路线 | 按独立能力逐项实现 | 不创建空 starter，也不默认启动全部中间件 |

## 基础组件、服务与模板

| 交付物 | 职责与升级单元 | 允许定制 | 不包含 |
|---|---|---|---|
| BOM / starter | 依赖组合、自动配置、技术契约；随版本升级 | 文档化配置、显式扩展点 | 账号数据库、业务实体、业务数据范围推断 |
| IAM / Gateway 可部署服务 | 提供身份授权与入口能力；作为独立发布单元维护 | 配置及已说明的接入边界 | 下游业务规则、跨服务数据库查询 |
| 项目模板 | 新项目结构、工作约定、对发布组件的引用 | 业务代码、命名及项目配置 | 公共组件实现的复制品 |

模板只负责初始化。已有项目升级通过组件版本及迁移说明完成；模板结构更新以差异说明供维护者选择应用，不覆盖定制文件。对公共组件直接 fork 属于使用方维护分支，不能承诺自动吸收上游升级。

推荐平台源码集中维护，待首个研发发布时另提供轻量消费模板；候选仓库与制品方案见 [ADR-0002](../adr/0002-reuse-and-release.md)。本阶段不创建 Git 或远程仓库。

## 质量目标与未设定指标

- 可理解：AI 能找到单一规则来源，并判断修改归属。
- 可验证：权限规则、失败行为及兼容风险都能映射到场景。
- 可复用：模板消费发布组件，不依赖基础仓库工作目录。
- 可演进：技术依赖和契约变更有版本与迁移策略。
- 不虚构并发量、P99 延迟、SLA 或多机房指标；首个研发版本以功能正确性和开发环境可复现为目标。生产负载与部署预算作为未来生产化设计输入。
