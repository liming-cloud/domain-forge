## 工程组织与方案比较

原候选 `ce20ca6` 的根目录单工程按已确认的[整体研发结构](development-structure.md#仓库分区与管理边界)迁入 `code/verification/boot-smoke/`。2026-10-16 用户进一步确认内部 parent＋Boot BOM，替代 `235a2c0` 中探针直接继承 Boot parent 的设计：`code/pom.xml` 同时作为内部 parent 和聚合入口，只聚合该实际模块；探针继承 `org.domainforge:domain-forge-build:0.1.0`，通过 `../../pom.xml` 解析仓库父 POM。`code/.mvn/wrapper` 与官方脚本作为构建入口。探针源码、坐标 `org.domainforge:domain-forge:0.1.0` 和运行合同保持原样，唯一生产类型 `org.domainforge.boot.DomainForgeApplication` 承担启动装配；当前无外部发布。

内部 parent 不继承其他 parent，以 `dependencyManagement` 导入 `spring-boot-dependencies:4.0.8`，依赖版本和 Boot 插件共用该 Boot 版本属性。内部构建统一 Java 21 release、UTF-8、编译参数名和可重现打包时间；在 `pluginManagement` 显式管理当前实际使用的 compiler、resources、surefire、jar 及 Boot 插件版本。必需测试保持 `failIfNoTests=true`；探针显式启用 Boot 插件的 `repackage` 与 `includeTools=false`。应用配置按原始字节打包，不引入 Maven 资源过滤或新的运行配置来源。

方案比较：内部 parent 继续继承 Boot 能减少配置维护，但仍继承其插件、资源过滤及其他默认约定；已确认方案采用内部 parent 导入 Boot BOM，由本仓库显式维护实际需要的构建约定。[Boot 4.0 官方说明](https://docs.spring.io/spring-boot/4.0/maven-plugin/using.html)明确 BOM import 只提供依赖管理，不提供插件管理。保留现有版本组合，不复制尚未使用的 Kotlin、native、war 或发布配置。

真实入口核对代码区全部维护文件、内部继承与 BOM、固定聚合模块及原生 reactor 两个项目的对应关系，拒绝空目标、额外模块、隐式聚合配置和未覆盖输入；父级编译配置同样接受既有守卫。再对实际 JAR 模块复用编译、源码、依赖、测试与打包校验，保留原始 reactor 及派生模块清单。聚合入口和直接选择子模块的构建都须实际验证，父 POM 不依赖提前 install。当前适配不宣称任意多模块、模板或服务已经支持。

| 方案 | 收益与代价 | 结论 |
|---|---|---|
| 单个技术探针 JAR，按真实职责组织包 | Wrapper、测试、打包和运行对象直接一致，可用于质量入口验证 | 保留为技术验证对象；其目录不决定整个平台结构 |
| 先设计平台制品及依赖，再按单元实现 | 产品已有版本化组件、服务及起步模板需求，应明确其归属和依赖，不必预先创建空实现 | 当前按用户纠正采用该推进顺序，具体结构已确认，当前执行 R1 |

使用 Boot 提供的依赖管理，项目直接使用的能力显式声明依赖；插件执行范围和最终解析版本必须确定。不预先引入全部 Cloud／Alibaba／数据库／安全组件。构建内部组织不成为未来消费项目必须继承的平台父 POM 合同。

## 最小运行合同

使用 Boot Actuator 的原生健康端点作为首个技术探针；框架运维端点按现行 HTTP 规范无需套业务 JSON 外壳。首个单元的受支持运行方式固定使用回环地址，供本地和 CI 启动核验；不开放公共服务、不引入登录入口。交付验证入口拒绝非回环启动目标；只开放健康读取，关闭健康细节及其他管理端点，测试真实 HTTP 响应及不可访问路径。

| 输入／事件 | 必须观察到的结果 |
|---|---|
| 声明的 JDK、合法监听端口、无外部中间件 | 打包后的实际 JAR 启动，`GET /actuator/health` 返回 HTTP 200、JSON `status=UP`，不包含组件细节；不能只检查 Spring 上下文或进程存在 |
| 指定另一合法端口 | 只在指定端口响应，原端口无该应用响应；输入属于启动引导，不建立与未来 Nacos 权威配置并行的业务来源 |
| 非法端口或端口被占用 | 启动失败并非零退出；诊断指出启动问题，健康不能返回成功 |
| 请求未开放管理端点 | 无敏感信息泄露，不因框架默认值额外暴露 env、配置、线程或堆信息 |
| 正常终止 | 子进程退出、端口释放；测试资源只清理本次创建的进程和目录 |

启动等待采用有界轮询观察实际 HTTP，不用固定睡眠猜测就绪；运行超时、进程退出和断言失败分别记录。后续业务和能力接入时重新设计其就绪、拒绝、恢复和授权合同，不从这个空能力应用推导全部平台可用。

## 质量检查接入

固定入口 `python3 -B tools/product_gate/verify.py --project .` 供本地和 CI 调用。入口绑定当前维护输入与实际工程，协调原生 Wrapper、已有检查器和场景测试；不新建通用任务编排平台。开发者可单独运行快速检查，但交付结果只来自完整适用集合。

| 检查责任 | 首个单元的真实对象与证据 | 必须识别的失败 |
|---|---|---|
| 文档及任务 | 当前任务、设计、实际路径和规则覆盖 | 新生产／测试路径未登记，设计与实际范围脱节 |
| 源码及架构 | 同次实际编译的生产／测试源码和类产物；现有格式、注释、复杂度、模块、职责及依赖检查 | 漏扫、未归属、用途伪造、源码违规及未声明依赖；保留准确诊断 |
| `build-gate` | 官方 Wrapper 的真实 `verify`、有效插件执行、测试报告、最终依赖及打包产物 | 跳过必需测试、零目标、测试失败、缺产物、浮动版本或与声明环境不符 |
| `dependency-risk-gate` | 实际项目直接／传递及测试依赖的原生扫描和报告 | 未执行、资料不可用或扫描失败不当成零漏洞；真实漏洞告警可见，按既定规范不自动阻断功能构建 |
| `behavior-scenarios` | 本单元启动参数、失败、停机等已定义工程行为 | 只验证配置存在，或失败场景因无关网络问题失败 |
| `runtime-scenarios` | 实际打包 JAR、真实回环 HTTP 和进程生命周期 | 上下文测试代替 JAR，收到通知／进程存在代替实际结果 |
| `product-scenarios` | 研发者从干净副本按说明构建、启动并复验本单元 | 依赖开发机私有文件、复制平台示例源码或隐含缓存才成功 |
| 普通语义评审 | 设计、职责、说明准确性、独立预期与证据范围 | 机械检查成功代替业务或人工结论 |

五个产品检查只有在对应入口真实执行且正反例验证后才能登记已实现；支持范围限于已接入的工程与场景。为后续能力继续按触发增加其必需场景，不能把本次单应用绿灯解释成全产品通过。测试使用同一真实工程内容；需要清洁输出时在隔离副本构建并记录输入摘要，不修改开发者工作区。

已有校准器的 CLI 与精确版本／干净输出前提需在本单元接线时核对。可复用观察和检查代码，但不得直接把其 `calibration-only` 报告换名为产品通过；真实产品执行、输入和结果明确关联，出现新的支持缺口只补必要适配。

## 使用路径

使用者按以下步骤复验。具体一次执行是否通过以本次报告为准：

1. 从精确提交建立干净工作副本，按版本基线选择 JDK 和质量工具环境，核对 Wrapper 分发校验。
2. 开发期间使用 `code/mvnw -f code/pom.xml -B -ntp verify` 运行真实 Maven 生命周期；交付前调用产品验证入口，包含当前适用源码、架构、构建、扫描和场景责任。入口不得接受历史成功报告作为执行替代。
3. 运行场景用 `java -jar` 启动该输入打包出的真实 JAR，传入回环绑定和本次隔离端口，检查健康、失败和停机。具体产物名由有效构建解析，不手写猜测。
4. 生成输入、环境、命令、范围、场景与诊断报告；完成普通语义评审后按授权提交推送，再使用公开 delivery 命令核对远端与 CI。
5. 人工验收精确工程单元；后续依次增加选定能力的必要设计、真实实现和验收。

本地需要 Bash、Git、`curl` 或 `wget`、上述固定 JDK／Python，以及 Maven Central、原生漏洞资料服务的网络访问。先设置 `JAVA_HOME` 并把同一 JDK 的 `bin` 放在 `PATH` 首位。以下缓存目录必须位于仓库外；源码工具由既有原生锁校验，不把校准结果用作产品结果：

```bash
export DOMAIN_FORGE_GATE_TOOLS="$(mktemp -d /tmp/domain-forge-source-tools.XXXXXX)"
python3 -B tools/engineering_gate/calibrate_source.py prepare
export DOMAIN_FORGE_GATE_ADVISORY_DATA="$(mktemp -d /tmp/domain-forge-product-advisory.XXXXXX)"
python3 -B tools/product_gate/verify.py --project . --environment
python3 -B tools/product_gate/verify.py --project . --prepare-data "$DOMAIN_FORGE_GATE_ADVISORY_DATA"
python3 -B tools/product_gate/verify.py --project .
```

可选环境变量 `DOMAIN_FORGE_PRODUCT_REPOSITORY`、`DOMAIN_FORGE_PRODUCT_WRAPPER_CACHE` 指向仓库外缓存；未提供时入口建立全新隔离目录。原生资料准备只更新缓存，不生成产品通过结论。入口完整执行真实构建、源码与架构检查、依赖扫描、JAR 场景和原生拒绝反例；`--check` 仅用于定向诊断，不作为完整交付证明。报告给出临时证据目录，包含原生命令日志、Maven 范围观察和原生 HTML／JSON 告警报告。CI 将该目录保存为 `product-evidence`。

CI 首次产品建库可从同一原生插件配置摘要对应的成功资料缓存复制数据库，避免重复下载 NVD 全部历史资料；已有产品数据库不覆盖，检查报告不复制。缓存只作为输入，随后仍执行原生更新及当前工程的完整扫描，缺失或损坏资料不产生通过结论。准备阶段的成功与失败日志均归档，原退出码保留。

日常开发执行 `code/mvnw -f code/pom.xml -B -ntp verify`，构建后可用 `java -jar code/verification/boot-smoke/target/domain-forge-0.1.0.jar --server.port=8081` 在 `127.0.0.1` 启动，检查 `/actuator/health` 后以 Ctrl-C 停止。普通 Maven 构建不等于完整质量入口通过。首个单元的公开验证入口只支持 `127.0.0.1`；额外配置文件、环境覆盖和其他网络目标需要先补支持合同。生成工具的临时目录不写入产品工作树，`target` 仅是普通开发构建的输出。

产品验证入口只承担这个真实工程的固定检查组合；`control_plane.py run` 和 CI 通过受控配置调用它或它的固定检查分组，避免自建另一套任务、审批或规则语言。构建与场景的内部步骤及报告复用必须绑定同一输入和环境；独立运行各检查不能借陈旧产物跳过实际责任。

## CI 接入与失败分类

继续使用 GitHub Actions；在现有工作流中增加明确的产品检查 job，并同步真实交付证据适配，不新建另一套审批状态源。文档与检查机制、产品路径及共同构建配置按事件精确差异选取适用集合。修改 POM、Wrapper 或共同质量配置必须触发产品检查；规则／工具变化继续触发现有相关校准；纯设计注册按实际变更执行文档及流程验证。

产品检查入口在当前 SHA 的干净 checkout 中实际执行。必需 job／step、输入、run attempt 和报告均可核对；必需检查缺失、被跳过、零测试或失败不能由总绿灯掩盖。新增 job 的成功、失败、未触发和条件跳过均加入 delivery 适配正反例；保留第五层历史工作流对象的读取能力，不重新解释旧 CI。

下载／环境准备与断言执行分开记录。Maven 下载超时归为依赖准备或网络环境未完成，允许有界重试及有效原生缓存，不认定代码或断言失效；准备未完成时也不报告完整验证通过。缓存命中、空报告或只执行准备不能代替实际检查。

实际入口分别记录 Wrapper 准备（300 秒）、构建（600 秒）、原生资料准备（2700 秒）、扫描（900 秒）、反例（240 秒）和运行场景耗时；完整入口在控制面内上限为 1800 秒，产品 CI 的 90 分钟上限覆盖单独资料准备与完整执行。上限是防止挂起的边界，不是正常耗时指标。预算按实际工作量调整：首轮量测依赖准备、编译／测试、源码检查、运行及扫描耗时，分别设置合理上限，必要时拆分原生准备；不把原校准进程上限机械套给完整产品构建。保留必要检查和独立断言，不以降低规则解决慢任务；不新建预算治理子项目。

依赖告警资料准备／扫描失败属于该检查未完成；工具发现漏洞与工具执行失败区分。漏洞告警按既有规范输出和处理，不恢复已撤回的自研评分或高等级自动阻断要求。

## 验收标准

以下是已确认的验收标准；实际执行结论及待人工决定项在任务记录中逐项列明，标准本身不自报通过。

| 编号 | 通过条件与必要证据 |
|---|---|
| E01 工程可复验 | 干净副本按说明仅提供声明环境即可经官方 Wrapper 构建；原生命令、退出码、环境、输入和产物可追溯 |
| E02 版本组合确定 | JDK／Maven／插件及真实最终依赖固定；缺少维护来源、版本不符、浮动依赖或校验失败明确拒绝 |
| E03 真实范围覆盖 | 新增普通生产类、测试类与资源均进入实际扫描；生产伪装为测试、遗漏目标不能放行 |
| E04 源码边界有效 | 对当前工程注入代表性格式／说明／复杂度／依赖违规，出现对应诊断；整改后复验成功 |
| E05 构建与测试有效 | 必需测试真实运行，关闭或跳过、零目标、失败测试、缺产物分别拒绝；不过度堆积数量型测试 |
| E06 原生扫描有效 | 正常报告、已知漏洞告警、资料缺失／执行失败分类可复验；包含实际测试依赖，不把工具错误当零风险 |
| E07 真实运行 | 实际 JAR 在受支持环境启动、健康、端口覆盖、非法及占用端口失败、停机与端口释放均有独立断言 |
| E08 管理暴露边界 | 仅回环健康可读且无详情；未声明管理路径和敏感数据均未暴露，不产生业务 API |
| E09 本地与 CI 一致 | 同一声明入口与规则用于本地和 CI，真实对象与结果一致，差异明确解释并复验 |
| E10 CI 不漏检 | 产品源码、测试、POM／Wrapper及共同配置触发适用 job；纯文档合法跳过产品检查；漏 job／step 或伪造跳过会被 delivery 拒绝 |
| E11 环境失败不冒充产品失败 | 隔离下载超时、依赖缺失、扫描资料失败和目标断言失败；重试成功后仍执行完整必要检查 |
| E12 交付范围准确 | 文档、普通语义评审、真实 Git／CI、delivery 和精确单元人工验收齐备；明确平台功能、模板、外部发布及后续场景未完成 |

## 实施顺序与确认事项

1. 先按最新用户决定补齐[整体研发结构](development-structure.md)，明确代码与文档分区、制品及依赖、检查责任和研发顺序；原设计批准不代替这项前置决定。
2. 整体结构确认后，按其落位迁移现有最小工程、Wrapper 和质量入口；已核查版本及健康／生命周期合同可复用，路径与构建假设须重验。
3. 复验迁移影响的真实输入分类、五项产品检查及源码／架构机制，保留必要断言和有效反例。
4. 对新候选执行适用真实 CI 和 delivery 核验，再提交结构迁移及工程基础验收；迁移前证据不代替新候选结果。

四步是同一工程单元的依赖顺序，不新增每步人工审批。若新事实改变产品目标、框架代际、公开合同或安全责任，仅暂停相关取舍并提交决定。

继续保留的技术合同：单个无业务功能的真实 Boot 探针，以回环健康和进程生命周期验证运行，将实际源码、构建、扫描和场景接入同一质量入口及 CI。它在整个平台中的职责与落位须服从前置结构设计；后续能力按该结构逐单元设计和实现。
