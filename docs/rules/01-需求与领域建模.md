# 需求与领域建模规范

适用于平台能力和业务项目的领域设计。需求、验收场景与设计文档的写法见[开发流程](../workflow/01-开发流程.md#需求与设计)；代码组织、依赖、事务等落地规则见[系统设计](02-系统设计.md)。

## 领域与上下文

### R-05 先按业务划上下文，再决定代码和部署

**规则**：限界上下文是一套术语和模型保持一致的范围。识别方法：

1. 从参与者、目标、流程和规则出发，先看已有上下文能否自然承担需求。
2. 核对同名概念的含义、生命周期、规则所有者是否一致；有真实冲突时，再比较拆分与不拆分。
3. 每个候选上下文写清：业务目的、主要术语、规则和数据责任、对外协作、不承担的内容。
4. 用成功、失败和协作场景检验边界，然后再考虑模块和部署映射（见[系统设计](02-系统设计.md#上下文与部署)）。

**反例**：因为新增了页面、表、目录、团队或服务就新增上下文；同名概念含义不同，却用一个万能对象加大量标志位强行统一。

**检查**：评审。

### R-06 写清上下文之间的关系

**规则**：每项跨上下文关系写清：调用或数据流向、业务意图、公开合同、数据所有者、模型在哪里翻译、版本兼容和失败责任。各上下文维护自己的模型，不直接共享内部可变对象；确需共享模型子集时，写清共同语义和维护责任。

**检查**：评审。

## 建模深度

### R-07 按规则复杂度选择建模方式

**规则**：先从场景中列出规则，再决定建模深度：

| 情形 | 做法 |
|---|---|
| 只有简单维护，没有复杂生命周期或多操作共同维护的约束 | 直接用清晰的应用用例实现，不创建没有职责的领域对象 |
| 规则相互制约：多阶段生命周期、复杂计算、多个操作共同维护的约束 | 用领域模型承载规则，让相关操作一致地维护它们 |
| 需求不足，判断不了 | 标明未知项和影响，向业务方确认，不把猜测固化为模型 |

必须写出选择依据，不能只说"这只是 CRUD"。两种做法都要处理授权、事务、失败和测试。

**正例**：字典项只有名称、启停和排序，用轻量用例；订单有金额计算、按状态限制取消、多个操作共同维护的约束，用领域模型表达这些行为。

**检查**：评审。

## 战术设计

### R-08 只采用有依据的模式

**规则**：

| 模式 | 什么时候用 |
|---|---|
| 实体 | 业务需要跨时间追踪同一身份 |
| 值对象 | 由值定义、不需要身份；优先不可变 |
| 聚合 | 存在必须原子维护的业务约束；边界由不变量解释，不由外键、请求结构或对象数量推导（设计规则见 [R-13](#r-13-聚合要小按-id-引用聚合之外最终一致)） |
| 领域服务 | 规则无法自然归属单个实体或值对象；不能变成堆放所有逻辑的万能服务 |
| 领域事件 | 已发生、业务关心的事实，且确有使用者 |
| 仓储接口 | 用例需要读取或保存聚合（见 [R-14](#r-14-仓储只针对聚合根)） |

工厂、规格、策略只在创建过程、组合规则或真实算法变化需要时使用。单一构造、单一判断或"将来可能变化"不构成理由。

**检查**：评审。

### R-09 用 shared 中的三个角色标识

**规则**：领域类型可以实现 `org.domainforge.shared` 的 `Entity`、`AggregateRoot`、`ValueObject`。它们只表达角色，不提供 ID、审计字段或存储方法，也不自动生成 `equals/hashCode`。实体按身份判断相等，值对象按组成值判断相等。DTO、PO、record 不会因此自动成为值对象。

**状态**：待修订。角色标识改用 jMolecules 类型（[ADR-0004](../decisions/0004-用jMolecules表达DDD构造块.md)），由 [#107](https://github.com/liming-cloud/domain-forge/issues/107) 修订本卡。

**检查**：自动[技术边界]：领域层只允许依赖 JDK 与 `shared`；评审：相等语义。

### R-10 写清生命周期

**规则**：每个重要生命周期列出：操作、前置条件、合法与非法状态转换、维护的约束、必要的事件。每项约束写清由谁维护、何时校验、失败结果。

**正例**：见[身份权限设计](../architecture/04-身份权限.md#聚合生命周期ddd-与-cqrs)中账号的状态转换表。

**检查**：评审；测试：覆盖每个非法转换。

### R-13 聚合要小，按 ID 引用，聚合之外最终一致

**规则**：聚合按 Vernon 的四条规则设计：

1. 聚合只为保护真实的不变式而存在。
2. 聚合要小，只包含维护不变式所必需的内容。
3. 只按 ID（或 jMolecules 的 `Association`）引用其他聚合；实体只属于一个聚合。
4. 聚合之外使用最终一致性：一个事务只修改一个聚合（见 [S-11](02-系统设计.md#s-11-一个事务只修改一个聚合)）。

**理由**：大聚合和对象引用会扩大锁和事务范围，让无关的修改互相冲突。

**状态**：按 ID 引用的自动检查待建（`JMoleculesDddRules`，[#107](https://github.com/liming-cloud/domain-forge/issues/107)）。

**检查**：评审：聚合大小与边界是否由不变式解释。

### R-14 仓储只针对聚合根

**规则**：仓储接口只为聚合根定义，按聚合整体读取和保存；聚合内部的实体和值对象不单独建仓储，也不绕过聚合根单独保存。

**状态**：自动检查待建（[#107](https://github.com/liming-cloud/domain-forge/issues/107)）。

**检查**：评审。
