# 测试与验证规范

适用于平台、模板和业务服务的测试。测试的运行方式（单元、集成、CI）见[工程与构建](../reference/工程与构建.md#质量门禁)；测试代码的注释与复杂度见 [C-12](04-源码质量.md#c-12-测试用清晰的名称代替冗余注释)、[C-13](04-源码质量.md#c-13-方法复杂度上限)；测试失败或检查不通过时的处理见 [W-11](../workflow/01-开发流程.md#w-11-发现问题时修正对象不放宽检查)。

## 场景

### T-01 从需求推导必要场景

**规则**：按需求、合同和风险确定必要的成功、拒绝、边界、故障场景（参见 [W-01](../workflow/01-开发流程.md#w-01-先写清目标和验收场景再设计)），不要求每个方法机械套用四类测试。必要场景缺失、没执行或失败时不能交付。

**检查**：评审：PR 模板要求说明验证方式。

### T-02 覆盖率只用于查漏

**规则**：不设覆盖率百分比下限。覆盖率用于发现可能漏测的路径；对没覆盖的部分核对用途和风险。覆盖率高、测试多、代码被执行都不代表断言有效或需求完成。

**检查**：评审。

### T-03 断言验证结果，不验证调用

**规则**：断言约定的结果，而不仅是方法被调用、没有抛异常或返回 2xx。拒绝和故障场景还要断言不应发生的效果（例如被拒绝的请求没有写入数据）。预期值来自需求或独立可核对的事实，不用被测实现再算一遍来比较。

**反例**：

```java
verify(repository).save(any());      // 只验证调用了 save
assertEquals(200, response.status()); // 只看状态码，没检查业务代码和数据
```

**检查**：评审。

## 测试放在哪里

### T-05 按职责选择测试方式

**规则**：

| 验证对象 | 测试方式 |
|---|---|
| 领域规则、应用用例 | 单元测试（`*Test`），直接构造对象，可用替身隔离外部依赖 |
| HTTP 入口 | 验证协议转换、授权执行、结果表达；不代替业务和数据范围判断 |
| SQL、映射、事务、Redis、组件交互 | 集成测试（`*IT`），使用真实 PostgreSQL、Redis |
| 默认装配与扩展 | 只提供必要输入时默认实现可用；合法覆盖和扩展生效，并回归默认行为 |
| 故障、并发、恢复 | 验证持久状态和外部效果，不只看线程启动、回调执行或连接恢复 |

框架和 SDK 的内部实现不用重复测试，但平台的配置、适配、默认约定和对使用者承诺的行为要有测试。

**检查**：评审；自动[CI]：`mvn verify` 执行全部 `*Test` 与 `*IT`。

### T-06 测试互相独立

**规则**：每个测试自己建立最小前置数据，不依赖其他测试的执行顺序或遗留数据。可以共享数据库进程，但数据和故障状态要隔离；确实需要连续状态的端到端流程放在同一个测试场景里。

**正例**：`IdentityPersistenceIT` 每个测试前清空业务表和 Redis，再初始化本测试需要的管理员。

**检查**：评审：单独运行某个测试也要能通过。

### T-07 可替换实现跑同一套合同测试

**规则**：同一接口的多个实现（如本地文件存储与 S3）运行同一组成功、失败、边界测试，再补各自的真实适配场景。Mock 的交互次数不能证明可替换性。

**检查**：评审。

## 环境

### T-08 用真实依赖验证真实行为

**规则**：数据库、Redis、Nacos、存储、消息等组件的行为用真实服务验证（集成测试由 docker-maven-plugin 启动容器）。不用内存数据库、另一种数据库或"能连上"代替被声明的行为。替身只用于隔离逻辑和制造特定条件。本地缺少 Docker 时的处理见 [B-08](03-技术与构建.md#b-08-用-wrapper-构建不跳过检查)。

**检查**：自动[CI]：CI 执行完整 `mvn verify`。

### T-09 测试环境安全可重复

**规则**：写清依赖版本、必要配置、数据前提、故障注入和清理范围；时间、并发、故障控制可重复。端到端验证的每次等待都有明确的条件和超时，失败时留下现场（日志、容器状态），不用固定时长的等待。只清理本次测试自己的资源。测试不写入生产数据，不向真实手机号或外部系统发送内容。测试夹具和报告中的凭据见 [A-08](07-安全与访问控制.md#a-08-凭据和敏感内容不进入日志响应审计和报告)。

**状态**：端到端脚本中的固定等待与失败现场导出由 [#102](https://github.com/liming-cloud/domain-forge/issues/102) 处理。

**检查**：评审。

### T-10 性能结论绑定条件

**规则**：性能结论必须写明输入、数据量、资源和负载；替身的耗时、空报告或旧版本的结果不能作为当前版本的性能证据。

**检查**：评审。

## 自动规则

### T-11 自动规则必须有正例和反例

**规则**：每条可自动判定的规则都有合法正例（必须通过）和违规反例（必须报出对应问题），放在 `domain-forge-build-rules` 的测试中（`ArchitectureRulesTest` 与 `fixture` 包）。反例要因目标规则失败，而不是因为编译错误或环境缺失；不能用"一律拒绝"冒充安全。修改规则时同时更新正反例。

**状态**：已知缺口：Checkstyle 规则（`main.xml`、`test.xml`、`format.xml`）没有正反例（[#118](https://github.com/liming-cloud/domain-forge/issues/118)）。

**检查**：自动[ArchitectureRulesTest]。

### T-12 自动检查与人工评审分工

**规则**：自动检查负责可判定的结构、依赖、格式、复杂度；场景是否充分、断言是否有效、注释是否准确、领域归属是否合理，由人工评审判断。工具不支持的情况如实说明，不默认放行，也不要求合法设计迁就检查工具；检查不通过时的处理见 [W-11](../workflow/01-开发流程.md#w-11-发现问题时修正对象不放宽检查)。

**检查**：评审。

## 反馈

### T-13 反馈时间有上限

**规则**：反馈时间是 AI 研发效率最直接的杠杆，目标为（[ADR-0002](../decisions/0002-双北极星与反馈时间目标.md)）：

| 范围 | 目标 |
|---|---|
| 单模块门禁 | ≤ 3 分钟 |
| 本地完整门禁 | ≤ 15 分钟 |
| CI 墙钟 | ≤ 12 分钟 |
**状态**：2026-11-05 基线：本地完整门禁约 25 分钟，CI 墙钟约 12.5 分钟，未达标；度量脚本待建（[#103](https://github.com/liming-cloud/domain-forge/issues/103)），缩短端到端耗时见 [#102](https://github.com/liming-cloud/domain-forge/issues/102)。

**检查**：评审。
