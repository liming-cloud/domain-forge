# 接口与错误规范

适用于业务 HTTP 接口和失败处理。合同的通用要求（结果、失败、重试、兼容）见 [S-14](02-系统设计.md#s-14-合同写清结果失败重试和兼容)；平台实现与接入方式见 [Web 组件](../reference/components/web-support.md)。

失败模型与协议的来由见[失败模型与协议](../decisions/0009-失败模型与协议.md)。

## 失败与协议

### H-10 失败分三类，各有确定的协议结果

**规则**：失败按实际语义分为三类，每类对应确定的协议结果：

| 类别 | 含义 | 表达 | 协议结果 |
|---|---|---|---|
| 业务拒绝 | 调用方可以理解、可以纠正 | 继承 `shared.BusinessRuleViolation` 的规则违反类型，带稳定错误码和类别；领域层直接抛出，应用层不用 try/catch 翻译 | 4xx，状态由类别决定（见 [H-01](#h-01-失败用-http-状态和-problem-details-表达)） |
| 依赖不可用 | 暂时性故障，可以重试 | 继承 `shared.DependencyUnavailableException`（缓存、锁、文件存储、通知、跨服务调用、身份服务都已继承） | 503 |
| 程序错误 | 属于缺陷 | 未分类的异常 | 500 |

两个基类放在 `shared` 中，web-support 的 `Problems.dispatch` 是唯一分派点；组件和服务不注册全局异常处理，也不按确切类型登记映射。第三方框架的原生异常（如 Sa-Token）由平台组件通过 `FailureTranslator` 转为上述类型。自动[领域异常]：领域层不抛 `IllegalArgumentException`、`IllegalStateException`、`RuntimeException` 等通用异常，应用层不 catch 领域异常。

**检查**：测试：web-support 的合同测试覆盖三类失败和全部类别的状态，各组件的合同测试证明它们的不可用类型继承基类；评审。

### H-01 失败用 HTTP 状态和 Problem Details 表达

**规则**：

| 情形 | HTTP 状态 |
|---|---|
| 成功、查询完成（包括没有匹配数据） | 200 |
| 已受理、尚未完成 | 202 |
| 成功且没有响应体（如删除） | 204 |
| 请求格式或参数错误 | 400 |
| 未认证 | 401 |
| 无权限 | 403 |
| 资源不存在或不在可见范围内 | 404 |
| 状态冲突、并发冲突、幂等请求的首次仍在处理 | 409 |
| 请求体超过上限 | 413 |
| 业务规则不满足、同一幂等键用于不同请求 | 422 |
| 限流 | 429 |
| 依赖不可用 | 503 |
| 未知错误 | 500 |

失败响应统一为 Problem Details（RFC 9457，`application/problem+json`），稳定的错误码放在扩展字段 `code`。业务规则违反的状态由 `BusinessRuleViolation.Kind` 决定，不能用 200 表达业务拒绝，也不能把技术失败改写成业务拒绝。

**理由**：HTTP 状态让网关、监控和客户端不解析响应体就能区分成功与失败；业务拒绝仍有稳定错误码供程序判断。

**检查**：测试：web-support 的合同测试覆盖每个类别的状态码；评审：新接口的分类。

### H-02 成功直接返回资源，失败只用 Problem Details

**规则**：

- 成功响应直接返回资源或集合，不再包外壳；没有响应体的成功用 204。
- 失败响应是 Problem Details：`type`、`title`、`status`、`detail` 加扩展字段 `code`。`code` 是稳定的字符串，程序据此判断；`detail` 面向用户，程序不根据它判断结果。
- 不增加 `success` 布尔值、时间戳或其他全局字段。二进制下载、流式响应和 Actuator 端点不受影响。分页结构、业务代码在各自的接口合同中定义。

**正例**：

```json
{"type": "about:blank", "title": "Conflict", "status": 409, "detail": "邀请无效或已失效", "code": "INVITATION_UNUSABLE"}
```

**检查**：测试：web-support 的合同测试固定响应形状，IAM 与网关与模板的集成测试和闭环脚本按该形状断言。

### H-03 HTTP 结果对象只出现在入口层

**规则**：`ResponseEntity`、`ProblemDetail` 等 HTTP 结果对象由 `interfaces` 层的 Controller 和 web-support 构造。领域模型、应用用例和非 HTTP 的平台能力只抛出 [H-10](#h-10-失败分三类各有确定的协议结果) 的失败类型，不返回 HTTP 结果对象；不为此引入统一父类或继承体系。

**检查**：自动[技术边界]：领域层只能使用 `shared.BusinessRuleViolation`；评审。

### H-04 在技术边界按实际语义分类失败，只有一个分派点

**规则**：

- 在基础设施等实际技术边界把组件错误转换为 [H-10](#h-10-失败分三类各有确定的协议结果) 的失败类型。失败分类依据实际语义，不依据异常名称、捕获位置推测；业务拒绝、身份权限失败、技术故障不能因为都是异常就合并处理。
- web-support 的 `Problems.dispatch` 是唯一分派点：按基类分派，未分类的异常一律按程序错误处理；组件不注册自己的全局异常处理。Filter 等没有 MVC 异常处理的位置用 `Problems.write` 写出同样的响应。
- 有自带处理器的入口（如 IAM 的持久化与限流归类）只处理自己独有的失败，其余交给 `Problems.dispatch`；其他控制器用 `@PlatformJsonApi` 接入。
- 对外只返回调用方需要的信息，不泄露内部实现、客户端类型、连接信息、堆栈、原始令牌或敏感数据；内部诊断要能定位原因。

**检查**：测试：web-support 的合同测试，接口测试覆盖每类失败的实际响应；评审。

## 接口合同

### H-05 代码是接口合同的唯一来源

**规则**：先写清场景、行为和验收，再用 Controller、请求与响应类型及描述注解定义接口，由 springdoc 生成 OpenAPI。不再手工维护另一份 OpenAPI，也不手改生成物。类型表达不了的业务拒绝代码、权限要求在描述注解中补充。

**检查**：评审：接口变化在 PR 中说明对调用方的影响。

### H-06 接口变化要考虑兼容

**规则**：修改字段、类型、错误代码或权限要求时，在 PR 中写清对已有调用方的影响；不兼容的变化需要人工决定，必要时提供新版本路径。不通过修改测试预期来掩盖不兼容。

**检查**：评审。

## 消费

### H-07 调用方同时处理 HTTP 状态和错误码

**规则**：客户端先看 HTTP 状态，失败时再读 Problem Details 中的 `code`。无法解析的响应不能当作空数据或成功；超时、没有收到有效响应时按结果未知处理（[S-15](02-系统设计.md#s-15-结果未知不能当成功)）。是否可以重试由接口合同决定，不对所有失败统一重试。

**检查**：评审；测试：调用方的适配测试覆盖业务拒绝、技术失败和超时。

### H-09 服务间调用经跨服务调用组件

**规则**：服务之间的同步调用使用 OpenFeign 并依赖 `domain-forge-service-call`：超时、不重试、身份与链路上下文传递、失败分类由组件统一提供，服务不另配重试或手写身份请求头。成功响应直接是资源；调用方把 `ServiceCallException` 的分类翻译为自己的结果（不翻译时它按依赖不可用返回 503）：401、403 保持语义，`REJECTED` 按对方 Problem Details 中的代码处理，`UNAVAILABLE` 与 `UNKNOWN` 不能当作空结果或成功，写入的 `UNKNOWN` 按结果未知处理（[S-15](02-系统设计.md#s-15-结果未知不能当成功)）。设计见[跨服务调用](../reference/components/service-call.md)。

**检查**：自动[组件装配]；测试：调用方的适配测试覆盖成功、401、403、不可用与超时。
