# 系统设计规范

适用于平台能力和业务项目的系统设计。目录布局、命令与查询路径、事件的完整说明见[总体架构](../explanation/总体架构.md#ddd-边界与代码映射)；领域建模见[需求与领域建模](01-需求与领域建模.md)。

## 职责与依赖

### S-01 五个职责各管各的事

**规则**：业务服务的每个类都位于五个职责包之一，包名为 `<上下文根>.<职责>`，按下表分工：

| 职责 | 负责 | 不负责 |
|---|---|---|
| `interfaces` | 协议解析、输入格式校验、取得身份、调用用例、结果转换 | 直接访问数据库或客户端（SQL、Mapper、Redis 客户端）；业务判断 |
| `application` | 编排用例、授权与数据范围、事务边界、调用领域模型和外部能力 | 重复领域规则；直接使用 Mapper、SDK |
| `domain` | 业务概念、状态、计算和不变量 | 依赖任何框架、HTTP、数据库或远程调用 |
| `infrastructure` | 数据访问、对象转换、技术客户端、适配实现 | 决定业务成功、权限或规则 |
| `bootstrap` | 启动、配置、接线、生命周期 | 业务逻辑、查询、SQL |

依赖方向：`interfaces → application → domain`；`infrastructure` 实现 `application`、`domain` 定义的接口；`bootstrap` 可以依赖全部，其他职责都不依赖 `bootstrap`。另外（[ADR-0007](../decisions/0007-适配器的依赖方向.md)）：

- `interfaces` 不依赖 `domain`，只认识 `application` 的命令、查询和视图。
- `infrastructure` 不依赖 `interfaces`，适配器之间只经端口协作。

**检查**：自动[职责归属]、自动[依赖方向]、自动[技术边界]；评审：规则放得对不对。

### S-02 领域层不依赖框架

**规则**：领域层只依赖 JDK、`org.jmolecules.ddd`、`org.jmolecules.event`（`@DomainEvent`）、JSpecify 空值注解（`org.jspecify.annotations`）和 `org.domainforge.shared.BusinessRuleViolation`。不使用 Spring、ORM、Web、序列化注解；`shared` 中的其他类型（传输、主体等）不进入领域。

**理由**：领域模型应能脱离容器、数据库和网络直接测试。

**检查**：自动[技术边界]：框架依赖与 `shared` 的允许范围。

### S-03 应用层只用必要的框架元数据

**规则**：应用层可以使用 `@Service`、`@Component`、`@Autowired`、`@Qualifier`、`@Transactional`（及其 `Propagation`、`Isolation`）、需要短事务时的 `TransactionOperations`（及其回调 `TransactionCallback`、`TransactionStatus`），组件 `api` 包中的技术无关接口（2026-10-12 决定），以及 JSpecify 空值注解。不直接使用 Mapper、PO、DataSource、Redis、HTTP 客户端或其他 SDK；不为去掉这些注解而增加一层事务包装接口。

**检查**：自动[技术边界]；评审：注解没有被用来绑定技术行为。

### S-24 组件之间无环，依赖指向更稳定的一方

**规则**：按 Martin 的组件原则控制耦合，粒度包括 Maven 模块，以及组件内的 `api`、`internal`、`autoconfigure` 与服务的职责包：

- 无环（ADP）：组件之间、上下文之间不形成依赖环。Maven 已禁止模块级循环。
- 稳定依赖（SDP）：被依赖方的不稳定度 I 不比依赖方大 0.2 以上。I = Ce/(Ca+Ce)，Ce 是向外的依赖数，Ca 是向内的依赖数。

主序列距离 D 和 Lakos NCCD 只作报表，不作门槛（[ADR-0003](../decisions/0003-组件耦合的度量与硬规则.md)）。

自动检查覆盖同一模块内的组件；各模块的 Ce、Ca、I、A、D 与 NCCD 在构建时写入 `target/architecture-metrics.txt`，只报告。

**检查**：自动[组件环]、自动[稳定依赖]。

## 上下文与部署

### S-05 多个上下文可以同一应用部署

**规则**：上下文划分（业务语义）与部署单元（一起发布运行的代码）分开决定。允许多个上下文同一应用部署；只有在独立发布、扩缩容、故障隔离等实际要求驱动时才拆分服务，并写明依据、收益和成本。

**检查**：评审。

### S-06 用包划分边界，跨边界只经公开合同

**规则**：

- 上下文默认在同一构建模块内按包组织；只有需要独立版本、独立复用或技术隔离时才拆模块。依赖要显式声明。
- 跨上下文只能引用对方的 `application.contract`；同进程、同库、多数据源都不能成为访问其他上下文私有数据的理由；同进程的上下文之间频繁出现强耦合时，重新评估上下文划分。
- 组件的公开 API 放在 `api` 包，内部实现放在 `internal` 包。`api` 包只放接口、值类型（record、enum）、注解、异常，以及没有状态的静态入口类（final、无实例字段、只有静态方法，如 `HttpResponses`），不放连接池这类有状态的具体实现。
- 组件只经其他组件的 `api` 协作，不绕过对方的抽象直接使用底层实现（例如直接调用认证框架或 Redis 客户端）。
- Java 的 `public` 不等于公开合同：只暴露实际合同和框架接入需要的访问范围；降低可见性不能免除注释、合同和架构检查。

**检查**：自动[跨上下文]、自动[内部实现]、自动[api 纯净]、自动[依赖分析]；评审：绕过对方抽象使用底层实现。

## 用例入口与出口

### S-07 用公开应用方法作为用例入口

**规则**：默认直接调用应用类的公开方法；只有存在实现替换或需要独立维护的合同时，才抽取入口接口。HTTP、消息、定时任务可以复用同一用例，各自只做协议适配。用例的参数和返回值不携带 HTTP 请求、响应或消息客户端类型。

**反例**：每个用例都生成 `XxxUseCase` 接口和唯一的 `XxxUseCaseImpl`。

**检查**：评审；测试：用例行为测试直接调用用例方法。

### S-08 出口：业务语义建接口，通用能力直接用

**规则**：

| 情形 | 做法 |
|---|---|
| 本上下文特有的业务能力（如订单仓储、库存预留） | 在 `application.port` 或 `domain.repository` 定义接口，基础设施实现 |
| 平台已提供技术无关的通用能力合同（如短信发送、文件存储），且满足需要 | 应用层直接使用，不再包一层本地接口 |
| 平台合同表达不了本上下文语义，或确有替换需要 | 增加本地接口和适配，写明它隐藏了什么差异 |
| 只有具体客户端或框架 API | 在基础设施中适配成接口再给用例使用 |

出口接口的参数、结果和异常都不能携带 SDK 响应、ORM 对象或查询构造器，包括嵌套字段。

**检查**：自动[技术边界]：直接依赖；评审：嵌套字段和失败语义。

## 查询

### S-09 纯查询走短路径

**规则**：采用轻量 CQRS，默认同库同步。纯展示查询的路径是 `Controller → 查询合同（application.query）→ 基础设施实现 → SQL → ReadDTO`，不加只转发的 QueryHandler、QueryService，也不重建聚合；`application.query` 和 `infrastructure.query` 不依赖 `domain.repository`。需要资源授权决策、跨源编排或业务判断时，才增加有职责的查询用例；它要加载聚合或使用仓储，放在 `application.usecase`，不放 `application.query`。

**正例**：`AccountQueries.list(...)` 是应用层查询合同，`SqlAccountQueries` 在基础设施实现并直接投影 `AccountView`。

**反例**：Controller 直接注入 Mapper；为纯展示查询先加载聚合再转 DTO。

**检查**：自动[查询短路径]、自动[依赖方向]：`interfaces` 不能依赖 `infrastructure`；评审：是否需要查询用例。

### S-10 查询不改业务状态，并负责数据范围

**规则**：查询不修改业务状态（安全审计和观测记录除外）。每项查询写清权限和数据范围由谁执行。有数据范围要求时，范围条件由服务端根据可信身份生成并作为参数绑定进 SQL，客户端不能自己提供可信范围。需要其他上下文的数据时使用其公开查询合同，不联表读取对方私有表。查询结果用于后续写入时，写入时重新校验当前条件。授权本身见 [A-02](07-安全与访问控制.md#a-02-授权在后端用例边界执行仅需登录不等于有权限)。

**检查**：评审；测试：覆盖授权、拒绝、范围内与范围外数据和依赖失败。

## 事务与一致性

### S-11 一个事务只修改一个聚合

**规则**：一个数据库事务只修改一个聚合（[ADR-0006](../decisions/0006-一个事务只修改一个聚合.md)）。只读其他聚合做校验不算修改；审计记录和 Outbox 记录不是聚合。业务要求一起生效的修改必须落在同一个聚合内；跨聚合、跨上下文使用最终一致性（[S-23](#s-23-集成事件经同事务-outbox-发布)）。

选择事务方式前，先写清必须维持的约束、哪些状态须原子生效、允许的暂时不一致和失败结果。同进程、同数据库地址或有 `@Transactional` 注解，都不能证明参与了同一事务。

**检查**：自动[单聚合事务]：同一用例方法（含其 lambda 与同类私有方法）不得调用两个仓储的写方法（`insert`、`update`、`delete`、`replace`、`invalidate`、`save`、`remove`、`add` 开头）；测试：在真实数据库上验证整体提交和中途失败回滚；评审。

### S-12 跨资源、跨服务没有原子性

**规则**：不同数据源、不同服务、Redis、短信、文件、远程调用、消息发送都不在数据库事务的回滚范围内，默认也不引入 XA、Saga 框架或分布式事务平台。这类流程：

- 每个资源分别在各自的本地事务中执行，并写清每步何时提交、暂时状态和可见延迟、重试与重复、补偿或人工处理、业务何时算成功。
- 跨数据源的用例设计成可重复执行（如模板示例的归档：主库读、归档库按 ID 覆盖保存）。
- 尽量不在持锁的事务里等待远程调用；需要先后保证时使用明确的状态机与恢复，不把同步调用包装成原子操作。
- 只有跨步骤确有持久进度和恢复需求，才建立应用流程协调器，保存必要状态和重试键；普通多行方法不升级成工作流引擎。
- 需要可靠消息时使用同事务 Outbox（[S-23](#s-23-集成事件经同事务-outbox-发布)）。拆分服务或事务资源时，重新设计一致性。

**反例**：为了原子提交，直接写另一个上下文的私有表。

**检查**：评审；测试：验证故障时的实际结果。

### S-15 结果未知不能当成功

**规则**：

- 没有取得有效完成结果（超时、没有收到有效响应）时，不推断远端业务没有发生，也不报告成功。按实际副作用写清需要的状态核对、幂等、恢复或人工处置；不用统一自动重试掩盖部分完成或未知结果。
- 技术失败映射为合同结果时，保留必要的诊断证据，但不泄露客户端细节和内部数据。
- 幂等合同写清可信主体、操作类型、幂等键与请求指纹、并发抢占、保留期，以及结果未知时如何核对；"重复键"本身不等于幂等成功。
- 缓存写清权威来源、可接受的陈旧范围和失效行为；身份权限的生效要求不能被通用缓存放宽。

**检查**：评审；测试：覆盖依赖失败、超时和结果未知。

### S-20 事务由应用用例决定

**规则**：在应用用例入口使用 `@Transactional`（默认 REQUIRED、全异常回滚，包含受检异常；需要异常后提交的场景显式声明），基础设施加入该事务。不把每次 Mapper 调用当作完整业务事务，也不另造事务包装接口。慢操作（如密码哈希、远程调用）放在事务外；只需要短事务时可以用 Spring 原生 `TransactionOperations`。

**理由**：事务边界是业务决定，应和用例在一起。

**检查**：评审；测试：在真实代理入口上验证提交和中途失败回滚。

### S-21 不让事务静默失效

**规则**：自调用、非 public 方法、跨线程执行、数据源切换都可能使预期的事务边界失效，以实际调用路径验证。不捕获异常后返回成功（会导致本应回滚的事务提交）。用返回值表达业务拒绝时，自己确保事务回滚。`readOnly` 只是提示，不能替代权限或无写入约束。

**反例**：

```java
@Transactional
public Result execute(Command command) {
  try {
    repository.save(...);
    audit.record(...);
  } catch (RuntimeException e) {
    return Result.failed();   // 事务被提交，save 的数据保留
  }
}
```

**检查**：评审；测试：覆盖失败路径的回滚结果。

### S-22 一个事务只用一个数据源

**规则**：事务管理器、`SqlSessionFactory`、Flyway 必须使用同一个数据源，由持久化组件按 Spring 原生默认 Bean 名（`dataSource`、`transactionManager`、`sqlSessionFactory`、`flyway`）绑定并在启动时校验，不一致直接启动失败。需要第二个独立数据库时用持久化组件的 `AdditionalDataSource`，不用动态数据源路由（用法见[持久化组件参考](../reference/components/persistence.md#附加数据源)）；一个事务里访问另一个数据源的 Mapper 时，组件在执行 SQL 前拒绝（双向），不会静默地以自动提交执行。

**检查**：自动[启动校验]、自动[跨数据源误用检查]；测试：`AdditionalDataSourceIT` 在真实 PostgreSQL 的两个数据库上验证。

### S-23 集成事件经同事务 Outbox 发布

**规则**：需要可靠送达其他服务的集成事件，在业务事务内经 `domain-forge-messaging` 的 `EventPublisher` 写入 Outbox，与业务数据一起提交；不在事务提交后直接发送消息，也不使用中间件的事务消息。消费方实现 `EventHandler`，处理者只做本地事务内的写入，依赖组件的去重保证同一事件只生效一次；不能假定恰好一次或全局顺序，需要顺序时显式给出顺序键并使用 FIFO 主题。设计见[消息与 Outbox](../reference/components/messaging.md)。

**检查**：评审；测试：覆盖回滚不发布、重复投递不重复生效、不认识的合同版本不被静默跳过。

## 对象分离

### S-13 领域、持久化、接口和事件对象各司其职

**规则**：领域模型、持久化对象（PO）、公开输入输出、集成事件是不同角色，即使字段接近也分开，不合并：

- 领域对象表达业务，PO 只承载表和列，由基础设施适配器完成转换和重建。不要求领域类型与表一一对应；写清哪些状态被保存、如何重建、哪些值计算得出。
- 数据传输对象和 PO 可以有普通属性读写，但不能和领域模型合并。
- 展示查询可以直接返回查询结果，不必先转成领域模型；没有领域模型的轻量业务（[R-07](01-需求与领域建模.md#r-07-按规则复杂度选择建模方式)）不需要伪造领域类，但数据访问仍在基础设施。

**理由**：PO 跟随表结构变化，领域对象跟随业务规则变化，两者合并后任何一方变化都会波及另一方。

**检查**：自动[技术边界]：领域层不能依赖 ORM；测试：保存后重建，行为不变；评审：公开合同不返回 PO。

## 合同与失败

### S-14 合同写清结果、失败、重试和兼容

**规则**：公开用例、出口、平台能力和跨上下文协作的合同写清：

| 内容 | 要求 |
|---|---|
| 目的与数据 | 输入输出含义、身份与数据归属、允许范围和限制 |
| 结果与失败 | 区分业务拒绝、无权限、无效输入、依赖故障、超时、部分完成 |
| 重试与重复 | 能否重试、如何识别同一业务操作、重复调用的结果 |
| 版本与兼容 | 字段、行为、错误、权限变化对调用方的影响 |
| 对外事件 | 发布数据、消费责任、重复和顺序语义 |

Java 合同还要写清空值、单位、集合是否可变、资源归属、阻塞与取消。"没有结果"和"执行失败"不能混用；不能用静默返回空值或 `UnsupportedOperationException` 冒充支持。

**检查**：评审：HTTP 层的具体映射见[接口与错误](06-接口与错误.md)。

## 组件与扩展

### S-17 抽象和模式按真实变化引入

**规则**：扩展点来自已承诺的扩展路径或真实变化，不为每个方法生成工厂、策略和包装。优先组合；继承只用于真实的可替换关系或框架明确支持的扩展。相似的代码如果变化原因不同，不要合并；少量清楚的重复好过用布尔参数、字符串动作和回调拼出的通用流程。

| 模式 | 什么时候用 | 避免 |
|---|---|---|
| Strategy／Factory | 已有多个可替换算法，或创建过程要维护约束 | 只有一个实现也建接口、工厂、注册表 |
| Adapter／防腐层 | 外部技术或语义确实需要转换 | 不做转换的逐方法镜像 |
| Decorator／Template Method | 有稳定公共合同和真实可组合的行为 | 隐藏执行顺序、事务或权限的深继承 |
| Specification／事件 | 组合规则或已发生事实确有使用者 | 为模式齐全造规则语言或事件总线 |

消费方通过公开合同、配置和扩展点接入，不依赖内部实现，也不复制或修改平台源码来做普通定制。

**检查**：评审。

### S-25 可替换的提供方以 Spring Bean SPI 定义

**规则**：组件的可替换提供方（如短信服务商、文件存储后端）以 Spring Bean SPI 定义：接口放在 `api` 或 `spi` 包，默认实现用 `@ConditionalOnMissingBean` 在用户自定义 Bean 时让位（[ADR-0008](../decisions/0008-组件扩展机制.md)）。组件的装配方式见 [O-03](08-配置与运行.md#o-03-spring-装配方式)，各能力的扩展路径见[扩展路径](../reference/扩展路径.md)。

**检查**：自动[Bean 可覆盖]；测试：`NotificationIT.customProviderReplacesDefault`、`FileStorageIT.customBackendReplacesDefault` 接入替身提供方，其余场景使用默认实现。
