# 故障与可观测性规范

适用于重试、恢复、日志、指标和链路。失败的分类与协议见[接口与错误](06-接口与错误.md#失败与协议)，结果未知见 [S-15](02-系统设计.md#s-15-结果未知不能当成功)，观测中不能记录的内容见 [A-08](07-安全与访问控制.md#a-08-凭据和敏感内容不进入日志响应审计和报告)，观测数据的对接方式见[观测数据参考](../reference/观测数据.md)。安全审计不属于普通观测，见[审计](07-安全与访问控制.md#审计)。

## 故障处理

### F-03 一条调用链只有一处负责重试

**规则**：写清由哪一层重试、哪些错误可重试、总时间预算、退避和抖动；各层都重试会放大负载。有副作用的重试必须满足幂等合同（[S-15](02-系统设计.md#s-15-结果未知不能当成功)）；确定重试安全后才重试整个命令，并重新加载状态，不重放已经发生但不可幂等的外部副作用。熔断、缓存、降级只在合同允许的结果范围内使用，不能把权限拒绝、写入失败或未知状态变成成功。核对客户端和框架实际生效的超时与重试配置，避免嵌套重试和无界等待。

**正例**：cache 组件的 Redis 客户端 `retry-attempts: 0`，重试与否由调用方按合同决定。

**检查**：评审。

### F-04 恢复以实际行为恢复为准

**规则**：恢复的判断标准是合同要求的行为恢复，而不只是连接重建、回调执行或进程仍在运行。

**检查**：测试：在依赖恢复后发起新请求验证。

## 观测数据

### F-05 结构化日志能串联一次调用

**规则**：部署环境的日志使用结构化格式（ECS JSON，字段见[观测数据参考](../reference/观测数据.md#日志)），能识别应用、版本、环境、操作和结果，并用关联 ID 串联真实的调用路径（请求、异步消息、任务）。只在入口生成 ID 不等于全链路可追踪；没有采集到的信息不伪造。

**检查**：评审；测试：链路贯穿网关、同步调用、消息与任务，由 `scripts/verify_closure.sh` 在临时采集端中核对（见[链路追踪](../reference/components/tracing.md)），同一请求的日志按 traceId 在网关、业务服务与 IAM 中关联，由同一脚本逐行解析核对。

### F-07 指标维度有界，区分业务拒绝和故障

**规则**：

- 指标标签只使用固定、有限的取值（应用、版本、框架提供的分类），不把请求 ID、用户输入、完整 URL 放进标签。个体诊断用日志和链路完成。
- 指标和日志区分请求处理、业务完成、业务拒绝和服务故障。业务拒绝不自动等于故障，也不能被计为成功；不用 HTTP 2xx 数量代替业务成功数量。
- 采样和过滤不能为了提高成功率而丢弃失败记录。

**检查**：评审。

## 观测故障

### F-08 观测故障不影响业务

**规则**：身份授权、数据访问和业务处理正常时，单纯的观测故障（日志导出、指标、链路失败）不能导致暂停接收业务请求，也不能把已完成的业务改报为失败（2026-10-06 决定）。观测数据允许缺失，但要暴露降级状态并如实记录可核对的缺失范围，不伪造未采集的数据，也不报告零丢失。安全审计不适用这条容错。

**正例**：模板的异步日志队列容量 256，满时丢弃而不阻塞业务，并通过 `domainforge.logging.degraded` 指标暴露降级。

**检查**：测试：制造观测故障，验证业务继续、降级可见。

### F-09 观测资源有上限

**规则**：导出、缓冲、重试、线程、存储都有上限和超限行为，不能无限积压、阻塞业务或反复记录同一故障造成放大。不为隔离观测故障而自建持久遥测队列或另一套容错平台。降级状态不能只通过同一条已故障的导出链路才能发现。

**检查**：评审；测试：验证持续故障下的资源占用。
