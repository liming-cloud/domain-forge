# 测试与验证规范

规范来源与固定输入见[第三层确认记录](../product/02-研发路线.md#第三层确认记录)；实际实现、验证及未完成项见[当前任务](../00-文档导航.md#当前任务)。

## 适用范围与阅读入口

适用于平台实现、官方起步模板及受统一规范约束的消费工程。按任务触发读取：

- 确定需求的必要测试场景、评审漏测或覆盖率：[已确认的场景与覆盖率原则](#已确认的场景与覆盖率原则)、[场景与有效断言](#场景与有效断言)。
- 新增或修改用例、入口、适配器及组件接入：[按职责组织测试](#按职责组织测试)。
- 准备真实依赖、并发、故障或恢复验证：[环境与真实证据](#环境与真实证据)。
- 实现或验收校验器、检查测试是否空转：[门禁与失败反例](#门禁与失败反例)。
- 执行交付验证或记录缺失环境：[执行与证据边界](#执行与证据边界)。
- 修改测试说明、夹具及测试辅助逻辑：[测试注释](04-源码质量.md#已确认的测试注释)、[测试说明与验证](04-源码质量.md#测试说明与验证)及[测试复杂度基线](04-源码质量.md#已确认的测试复杂度基线)。

测试以已确认需求和公开合同为依据，遵守[需求与场景分析](01-需求与领域建模.md#需求与场景分析)及[合同与失败语义](02-系统设计.md#合同与失败语义)。本规范不另定业务规则、能力范围或架构边界，也不通过测试数量衡量设计质量。

## 已确认的场景与覆盖率原则

- 按适用需求、合同及风险确定必要的成功、拒绝、边界和故障场景；必要场景缺失、未执行或失败时不能报告交付通过。不是要求每个方法机械套用四类测试。
- 覆盖率用于发现可能漏测的执行路径，不设置统一百分比下限，也不因工具默认值隐式增加数值硬门槛。对未覆盖部分核对实际用途及风险，不能将没有百分比下限解释为无需测试。
- 覆盖率高、测试多或代码被执行都不代替有效断言、合同场景及真实接入证据。覆盖率报告不能自行证明业务正确或需求已经完成。
- 必需的真实依赖、架构与源码检查、接口合同验证、校验器反例及语义评审继续有效；评审分工遵守[任务责任](../workflow/02-任务执行.md#责任与人工决定)。本项不降低[测试复杂度硬门禁](04-源码质量.md#已确认的测试复杂度基线)，也不新增自动豁免。
- 本项不选定测试框架、覆盖率工具、报告格式或具体测试执行方式；这些须结合后续真实工程落实，不把资料查询或草案当作已运行结果。

## 场景与有效断言

从需求与合同推导场景，说明前提、动作、预期结果和必要的持久化或外部效果。拒绝及故障场景同时核对不应发生的效果；不能只断言返回了某个错误，而遗漏错误发生前已经执行的越权或业务修改。

断言验证约定结果，不仅验证方法被调用、没有抛出异常或响应为 2xx。预期依据来自需求、合同或独立可核对的事实；不能用被测实现重新计算同一结果后相互比较，掩盖共同错误。HTTP 结果和消费者处理遵守[接口结果规范](06-接口与错误.md#分类映射与验证)。

必要场景与适用规则保留可追溯关联，使评审能定位对应测试或实际验证证据。已有有效测试可以复用，不为每条规则重复生成测试类，也不将所有规范无差别纳入每个任务。具体记录见[任务必要信息](../workflow/02-任务执行.md#当前任务的必要信息)。

行为变化同步更新受影响场景与断言。失败先定位为实现缺陷、测试缺陷或需求规范问题，按[整改与复验原则](02-系统设计.md#运行约束与设计审阅)处理；不能仅因当前实现不同而改写预期，更不能删除必要断言使测试通过。

## 按职责组织测试

按实际职责选择验证位置，不强制所有需求都具有相同层次、目录或测试配额。

| 验证对象 | 需要证明的内容 |
|---|---|
| 业务规则与应用用例 | 通过真实模型行为或公开用例合同验证规则、状态变化及拒绝；隔离测试可控制外部依赖，但不据此认定实际事务与框架接入成功 |
| HTTP 等入口与消费处理 | 验证协议转换、身份与授权执行、结果表达及合同兼容；入口检查不替代实际业务和数据范围判断 |
| 持久化与技术适配器 | 使用合同要求的真实依赖验证 SQL、映射、事务、组件交互及必要故障；不能只测测试替身或重新包装的接口 |
| 默认装配与公开扩展 | 最小必要输入下默认实现可用，合法覆盖及真实扩展生效，并回归受影响默认行为；扩展接口存在不等于扩展路径已经可用 |
| 故障、并发与恢复 | 验证合同约定的持久状态、外部效果、重复处理、隔离和恢复，不能只以线程启动、回调执行或连接恢复作为通过依据 |
| 部署与独立消费 | 按公开制品、说明和声明前提在目标环境执行相应旅程；平台联合构建与应用能启动不替代产品要求的独立接入、升级和恢复验证 |

框架及 SDK 不要求重复测试所有内部实现，但平台采用的配置、适配、默认约定、扩展位置及对消费者承诺的行为必须有相应证据。集成范围由实际合同决定，不因增加了第三方库就自动增加一套自建框架或全量上游测试。

## 环境与真实证据

验证前声明实际依赖版本、必要配置、数据与隔离前提、故障注入和恢复方式。测试使用明确允许的环境及资源，不凭默认地址、现存凭证或工具可访问性推断可对生产数据、短信收件人或外部资源执行写入。

数据、时间、并发及故障控制应可重复，明确清理和恢复范围，防止测试彼此污染。清理只针对本次允许的测试资源，不以删除共享数据或重建整个环境来掩盖失败。日志、报告和测试夹具不得泄露凭证或敏感业务内容，诊断仍保留核对失败所需的信息。

替身适用于隔离逻辑和控制特定条件；真实数据库、Redis、Nacos、存储、消息及其他组件的适用验收须按各自合同执行。不能用内存实现、另一种数据库或只验证连接建立代替被声明的真实行为。缺少必需环境时记录未验证及影响，不将跳过、预期失败或替身结果改写为通过。

配置验证遵守[配置权威前提](08-配置与运行.md#已确认的配置权威前提)，不借测试规范重新加入已经撤回的 Nacos 发布内容错误治理。具体能力的场景及执行前提留待后续设计，不把统一规范写成所有组件相同的故障脚本。

## 门禁与失败反例

检查须声明支持范围及未验证项；实际结果只记录于任务，不凭局部测试认定完整适用验证通过。

对可判定规则，使用同时具有合法正例和隔离违规反例的检查。反例应触发目标违规及对应诊断，不能因夹具损坏、无关编译失败或缺少环境而把任意失败当作规则有效；合法正例必须允许通过，避免用一律拒绝制造安全或合规假象。

实际扫描与执行范围须覆盖应检查的对象。关闭测试、未发现目标、遗漏必要任务或跳过必需环境时，交付入口不能报告完整通过；不能只验证配置里列出了某个插件或检查名称。

源码结构、架构依赖和 HTTP 合同的反例分别引用[源码验证](04-源码质量.md#适用范围与阅读入口)、[架构边界](02-系统设计.md#逻辑模块与依赖门禁)及[合同生成与验证](06-接口与错误.md#合同生成与验证)中的目标约束，不维护第二套规则正文。文档路由与流程检查的精确对象在第四、第五层形成。

场景是否足够、断言是否有效、注释是否准确及领域归属是否合理须有源码与场景证据的语义评审，普通任务由 Agent 或研发评审者完成；重大取舍和单元验收保留人工责任。脚本只核对当前输入、覆盖和材料关联，不冒充语义判断。校验器反例在相关规则、工具、执行流程变化及完整校准时纳入 CI，并验证整改后的合法对象恢复通过；普通功能任务不重复测试全部校验工具。

## 门禁分层与防漂移

门禁重点守住领域、职责、技术隔离和公开合同，按变更风险执行。普通业务研发不重复校准无关工具。

| 执行层次 | 触发与责任 | 不能替代的结果 |
|---|---|---|
| 常规检查 | 对实际变更执行文档一致性；产品工程接入后执行构建、必要测试、源码质量、明确架构边界及适用合同检查 | 不以 CI 成功证明领域设计正确、需求完整或已经人工验收 |
| 校验器维护检查 | 规则配置、工具或 CI 执行流程变化时校准；变更范围取真实差异，不取任务自报标签。完整校准保留有效正反例，普通任务不重复上游框架内部测试 | 校准成功不等于真实产品构建、漏洞扫描或运行成功 |
| 任务交付验收 | 从目标、现行设计、实际差异及风险核对全部适用责任；执行必要集成、权限、持久化、运行和消费场景及语义评审 | 局部检查或增量 CI 不能替代完整适用验证及原有人工批准 |

重点边界及唯一正文：领域语言、规则及上下文见[领域规范](01-需求与领域建模.md#领域与上下文识别)；职责、依赖和公开合同见[系统规范](02-系统设计.md#逻辑模块与依赖门禁)；持久化与框架适配见[类型边界](05-持久化.md#工程职责与类型边界)；源码与注释见[源码规范](04-源码质量.md#适用范围与阅读入口)；版本、依赖及制品见[构建规范](03-技术与构建.md#构建与依赖管理)。机械门禁守住可判定边界，评审核对需求依据、抽象必要性、模型语义及真实框架行为，不以模式数量或穷举全部语言形式作为质量目标。

- 必要测试失败、明确违规、必需证据或环境缺失均不能交付通过；不适用须有真实范围依据，并保留未执行事实。
- 工具不支持与代码违规分别报告。先以实际风险决定补工具、使用成熟检查或通过明确评审及场景补证；没有充分证据仍保持未验证，不能默认放行，也不要求合法产品设计迁就校验器。
- 普通任务不能通过改任务标签、降低可见性、缩小扫描、删除断言、扩大豁免或修改规则来自我放行。确需变更有效规则或例外时，按[规则整改原则](02-系统设计.md#运行约束与设计审阅)取得对应决定，并校准变更。
- 第五层完成已确认范围内的通用及具体门禁适配，包括框架、接口合同、数据库迁移和运行装配；必要技术基线与合同先行确定，正反例与使用成本真实验证。不建设穷举任意 Java／Maven／框架形式的证明平台。第六层接入产品工程并验证真实交付；当前必需适配不得改为延期，其他未支持范围显式保留。

CI 与执行器本身也属于受审阅输入。同仓库脚本无法独立防止有写权限的执行者同时篡改规则、测试和 CI；固定输入、规则变更审阅及人工验收共同提供约束，不能宣称已具备防恶意篡改能力。需由远端保护配置强制的措施，须在相应 Git 授权内落实并验证，不以本地文件存在当作远端已启用。

## 执行与证据边界

确认来源：2026-10-10 用户选择 A，分离机制与真实产品验收；2026-10-12 选择 B“第五层先完成全部具体适配”。

开发期间可以增量验证，交付执行[完整适用门禁](03-技术与构建.md#构建与依赖管理)，包含受影响行为及必要回归。完整适用不等于每次修改都重测所有不相关能力，也不能由 Agent 为获得通过擅自缩小必要范围。

按[阶段责任分离](10-测试与验证.md#执行与证据边界)执行：第五层完成全部必需具体适配、有效正反例、四类使用路径及必要语义审阅；真实产品构建、依赖扫描、运行和消费结果在第六层按真实合同验收。纯控制面任务可将产品结果明确列为未执行，但必须保留其对应机制责任；源码、职责、HTTP／访问、持久化、运行装配和交付核对等当前机制缺口不能借分层延期。为适配确定技术与合同不授权业务研发。适用性由目标与实际变更共同核对，真实生产或测试变更不能靠治理标签豁免产品检查；未执行不得记为通过。

证据能核对被测输入版本、实际环境、执行入口与范围、场景结果以及失败和未验证项。覆盖率报告用于查漏，不与场景结论混为一谈；代码或前提变化后，旧结果不自动证明新输入通过。任务恢复、人工验收及 Git 状态的记录方式由第四层统一，不在本规范另设状态源。

## 资料与验证边界

2026-10-06 经 Exa 读取的[JaCoCo 计数定义](https://www.jacoco.org/jacoco/trunk/doc/counters.html)说明行与分支指标基于代码执行信息，其分支计数不包含异常处理。由指标定义推断，百分比不能单独证明必要场景、有效断言或业务合同；这是指标边界的判断，不是项目已经验证的测试效果。

该资料不选定 JaCoCo、版本或项目阈值，不替代实际测试与覆盖率报告。具体工具须在后续工程中按基线选择并验证。
