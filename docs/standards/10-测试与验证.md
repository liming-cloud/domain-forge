# 测试与验证规范

适用于平台、模板和业务服务的测试。测试的运行方式（单元、集成、CI）见[工程与构建](../architecture/02-工程与构建.md#质量门禁)；测试代码的注释与复杂度见[源码质量 C-12、C-13](04-源码质量.md#c-12-测试用清晰的名称代替冗余注释)。

## 场景

### T-01 从需求推导必要场景

**规则**：按需求、合同和风险确定必要的成功、拒绝、边界、故障场景（参见[需求与领域建模 R-01](01-需求与领域建模.md#r-01-先写清目标和验收场景再设计)），不要求每个方法机械套用四类测试。必要场景缺失、没执行或失败时不能交付。

**检查**：评审（PR 模板要求说明验证方式）。

### T-02 覆盖率只用于查漏

**规则**：不设覆盖率百分比下限。覆盖率用于发现可能漏测的路径；对没覆盖的部分核对用途和风险。覆盖率高、测试多、代码被执行都不代表断言有效或需求完成。

**检查**：评审。

### T-03 断言验证结果，不验证调用

**规则**：断言约定的结果，而不仅是方法被调用、没有抛异常或返回 2xx。拒绝和故障场景还要断言不应发生的效果（例如被拒绝的请求没有写入数据）。预期值来自需求或独立可核对的事实，不用被测实现再算一遍来比较。

**反例**：

```java
verify(repository).save(any());      // 只验证调用了 save
assertEquals(200, response.status()); // 只看状态码，没检查业务代码和数据
```

**检查**：评审。

### T-04 测试失败先定位原因

**规则**：测试失败时先判断是实现缺陷、测试缺陷还是需求问题。不能因为实现变了就改预期，更不能删断言让测试通过。行为变化时同步更新受影响的场景和断言。

**检查**：评审（PR 中删除或放宽断言需要说明理由，见[开发流程](../workflow/01-开发流程.md#需要人工决定的事项)）。

## 测试放在哪里

### T-05 按职责选择测试方式

**规则**：

| 验证对象 | 测试方式 |
|---|---|
| 领域规则、应用用例 | 单元测试（`*Test`），直接构造对象，可用替身隔离外部依赖 |
| HTTP 入口 | 验证协议转换、授权执行、结果表达；不代替业务和数据范围判断 |
| SQL、映射、事务、Redis、组件交互 | 集成测试（`*IT`），使用真实 PostgreSQL、Redis |
| 默认装配与扩展 | 只提供必要输入时默认实现可用；合法覆盖和扩展生效，并回归默认行为 |
| 故障、并发、恢复 | 验证持久状态和外部效果，不只看线程启动、回调执行或连接恢复 |

框架和 SDK 的内部实现不用重复测试，但平台的配置、适配、默认约定和对使用者承诺的行为要有测试。

**检查**：评审；`mvn verify` 执行全部 `*Test` 与 `*IT`。

### T-06 测试互相独立

**规则**：每个测试自己建立最小前置数据，不依赖其他测试的执行顺序或遗留数据。可以共享数据库进程，但数据和故障状态要隔离；确实需要连续状态的端到端流程放在同一个测试场景里。

**正例**：`IdentityPersistenceIT` 每个测试前清空业务表和 Redis，再初始化本测试需要的管理员。

**检查**：评审；单独运行某个测试也要能通过。

### T-07 可替换实现跑同一套合同测试

**规则**：同一接口的多个实现（如本地文件存储与 S3）运行同一组成功、失败、边界测试，再补各自的真实适配场景。Mock 的交互次数不能证明可替换性。

**检查**：评审。

## 环境

### T-08 用真实依赖验证真实行为

**规则**：数据库、Redis、Nacos、存储、消息等组件的行为用真实服务验证（集成测试由 docker-maven-plugin 启动容器）。不用内存数据库、另一种数据库或"能连上"代替被声明的行为。替身只用于隔离逻辑和制造特定条件。本地缺少 Docker 时可以跳过集成测试，但 CI 必须执行；不能把跳过记为通过。

**检查**：CI 执行完整 `mvn verify`。

### T-09 测试环境安全可重复

**规则**：写清依赖版本、必要配置、数据前提、故障注入和清理范围；时间、并发、故障控制可重复。只清理本次测试自己的资源。测试不写入生产数据，不向真实手机号或外部系统发送内容。日志、报告和测试夹具不泄露凭据。

**检查**：评审。

### T-10 性能结论绑定条件

**规则**：性能结论必须写明输入、数据量、资源和负载；替身的耗时、空报告或旧版本的结果不能作为当前版本的性能证据。

**检查**：评审。

## 自动规则

### T-11 自动规则必须有正例和反例

**规则**：每条可自动判定的规则都有合法正例（必须通过）和违规反例（必须报出对应问题），放在 `domain-forge-build-rules` 的测试中。反例要因目标规则失败，而不是因为编译错误或环境缺失；不能用"一律拒绝"冒充安全。修改规则时同时更新正反例。

**检查**：自动（`ArchitectureRulesTest`）。

### T-12 自动检查与人工评审分工

**规则**：自动检查负责可判定的结构、依赖、格式、复杂度；场景是否充分、断言是否有效、注释是否准确、领域归属是否合理，由人工评审判断。工具不支持的情况如实说明，不默认放行，也不要求合法设计迁就检查工具。不能通过缩小扫描范围、降低可见性、删除断言、扩大豁免来通过检查。

**检查**：评审。
