# 质量模型与原则（总纲）

本页说明三件事：本仓库的“高质量工程”指什么，用什么判断方向是否正确，每条原则由谁来检查。原则的具体正文在 01–10 各份规则卡中维护，本页只维护映射，不复制正文。

标准按三层组织：

1. **质量模型**：质量包括哪些维度。
2. **原则与判据**：每个维度采用哪些业界原则，怎样才算违反。
3. **适应度函数**：每条判据由什么来检查。要么是 `mvn verify` 中的自动检查，要么明确标注“评审”，并写清评审看什么。适应度函数与系统一起演进：判据能够自动检查时，就从“评审”改为“自动”。

## 质量模型

以 ISO/IEC 25010:2023 的可维护性为骨架，补充可靠性中的容错。性能见[性能基线](../architecture/14-性能基线.md)，安全见[安全与访问控制](07-安全与访问控制.md)。

| 维度 | 含义 | 在本仓库中的体现 |
|---|---|---|
| 模块性 | 修改一个组件，对其他组件的影响最小 | 高内聚、低耦合 |
| 可复用性 | 资产能用于多个系统 | 平台组件与服务模板被多个业务项目复用 |
| 可分析性 | 能评估变更的影响、诊断缺陷 | AI 编码工具和评审人能快速读懂代码；失败能诊断 |
| 可修改性 | 修改不引入缺陷、不降低质量 | 可扩展：经扩展点接入，不改写已有代码 |
| 可测试性 | 能有效建立测试准则并执行 | 反馈快且结果确定 |
| 容错 | 依赖故障时行为确定 | 统一的失败分类与协议结果 |

## 北极星

| 类别 | 指标 | 口径 |
|---|---|---|
| 价值北极星 | AI 一次通过率；中位交付周期 | 在全新副本中，AI 编码工具只凭仓库文档交付真实业务用例。一次通过率指不经返工就通过门禁和人工评审的比例；交付周期从 issue 开工算到 PR 合并 |
| 质量北极星 | 原则可执行率 | 下文判据中，检查方式为“自动”的条数占总条数的比例 |
| | 变更局部性 | 单个业务 PR 涉及的 Maven 模块数和上下文数，越少越好 |
| 护栏 | 逃逸缺陷数不上升 | 带 `escaped-defect` 标签的缺陷 issue 数 |
| 领先指标 | 反馈时间 | 单模块门禁 ≤ 3 分钟，本地完整门禁 ≤ 15 分钟，CI 墙钟 ≤ 12 分钟（2026-11-05 基线：本地完整门禁约 25 分钟，CI 墙钟约 12.5 分钟） |

| | 变更前置时间、返工率 | 参考 DORA 的五项交付指标，返工率用修复类 PR 的占比近似 |

## 原则、判据与检查

“检查”一列的取值：

- **自动**：已经在 `mvn verify` 中检查。
- **待建**：已确认需要自动检查，规则尚未实现。
- **评审**：由人工评审判断。

### 类与方法

原则：单一职责；Connascence（共生性）。Connascence 从强度、局部性、程度三个维度衡量耦合，强耦合只能出现在局部。

| 判据 | 规则卡 | 检查 |
|---|---|---|
| 圈复杂度不超过 10，可执行语句不超过 30 | [C-13](04-源码质量.md#c-13-方法复杂度上限) | 自动 |
| 跨模块只允许名字、类型这类弱耦合，不用异常类型、魔法字符串或布尔参数约定语义 | 本页 | 评审 |

### 领域模型

原则：Evans 的 DDD 构造块，以及 Vernon 的四条聚合规则：

1. 聚合只为保护真实的不变式而存在。
2. 聚合要小。
3. 按 ID 引用其他聚合。
4. 聚合之外使用最终一致性。

另外，领域错误必须显式表达。构造块用 jMolecules 表达。

| 判据 | 规则卡 | 检查 |
|---|---|---|
| 聚合只按 ID 或 Association 引用其他聚合；实体只属于一个聚合 | [R-09](01-需求与领域建模.md#r-09-用-shared-中的三个角色标识)（待修订，见下文） | 待建：`JMoleculesDddRules` |
| 一个事务只修改一个聚合。只读其他聚合做校验不算修改；审计记录和 Outbox 记录不是聚合 | [S-11](02-系统设计.md#s-11-一起生效的操作必须共享真实的本地事务)（待修订） | 待建：一个用例不得调用两个聚合仓储的写方法 |
| 仓储只针对聚合根 | [P-02](05-持久化.md#p-02-po-与领域对象分开) | 待建 |
| 领域层以带错误码的业务规则违反类型表达规则，不抛通用异常；应用层不用 try/catch 翻译领域异常 | [F-01](09-故障与可观测性.md#f-01-在技术边界转换错误不合并不同性质的失败) | 待建 |
| 领域层不依赖框架和传输类型 | [S-02](02-系统设计.md#s-02-领域层不依赖框架) | 自动（`ApiResponse` 漏判，待补） |
| 聚合大小合理，只包含为维护不变式所必需的内容 | [R-07](01-需求与领域建模.md#r-07-按规则复杂度选择建模方式) | 评审 |

### 层与上下文

原则：依赖规则（Clean Architecture：源码依赖只指向内层）；端口与适配器（六边形架构）。

| 判据 | 规则卡 | 检查 |
|---|---|---|
| 类位于五个职责包之一，依赖方向符合规定 | [S-01](02-系统设计.md#s-01-五个职责各管各的事) | 自动 |
| `interfaces` 不依赖 `domain`，只认识 application 的命令、查询和视图 | [S-01](02-系统设计.md#s-01-五个职责各管各的事) | 待建 |
| `infrastructure` 不依赖 `interfaces`，适配器之间只经端口协作 | [S-01](02-系统设计.md#s-01-五个职责各管各的事) | 待建 |
| 跨上下文只引用对方的 `application.contract` | [S-05](02-系统设计.md#s-05-多个上下文可以同一应用部署) | 自动 |
| 纯查询走短路径，查询实现不依赖领域仓储 | [S-09](02-系统设计.md#s-09-纯查询走短路径) | 待建 |

### 模块与组件

原则：Martin 的组件原则。内聚由三条原则管：REP（发布的单元就是复用的单元）、CCP（一起变化的类放在一起）、CRP（不会一起被使用的类不放在一起）。耦合也由三条原则管：ADP（组件之间无环）、SDP（依赖指向更稳定的一方）、SAP（越稳定越抽象）。

度量用 ArchUnit 自带的 `ArchitectureMetrics`，分两级：Maven 模块级，以及组件内的 api/internal 级。三个度量的定义：

- 不稳定度 I = Ce/(Ca+Ce)，其中 Ce 是向外的依赖数，Ca 是向内的依赖数。
- 抽象度 A：公开类中抽象类型的比例。
- 主序列距离 D = |A+I−1|。

| 判据 | 规则卡 | 检查 |
|---|---|---|
| 组件之间无环（Maven 已禁止模块级循环，这里检查组件内 api/internal/autoconfigure 与服务职责包之间的环） | [S-16](02-系统设计.md#s-16-组件设计回答五个问题) | 待建：硬规则（2026-11-05 基线：0 个环） |
| 稳定依赖：依赖指向更稳定的一方（被依赖方的 I 不比依赖方大 0.2 以上） | [S-16](02-系统设计.md#s-16-组件设计回答五个问题) | 待建：硬规则（基线：0 处） |
| 组件 api 包只放接口、值类型、注解和异常，不放连接池、Web 响应这类具体实现 | [C-02](04-源码质量.md#c-02-public-不等于公开合同) | 待建：结构规则。D 值只作报表，不作门槛（原因见下文“耦合度量基线”） |
| 组件只经其他组件的 api 协作，不绕过对方的抽象直接使用底层实现（例如直接调用认证框架或 Redis 客户端） | [S-16](02-系统设计.md#s-16-组件设计回答五个问题) | 自动（只覆盖 `internal` 访问）；其余靠评审 |

### 扩展性

原则：开闭原则落在组件上。默认实现之外提供公开的提供方接口（SPI），并遵循 Spring Boot 自动配置惯例：自动配置在用户自定义 Bean 时让位，配置经类型安全的属性类绑定。抽象只在有真实变化时引入（[S-17](02-系统设计.md#s-17-抽象和模式按真实变化引入)）。

| 判据 | 规则卡 | 检查 |
|---|---|---|
| 可替换的提供方以 Spring Bean SPI 定义：接口放在 `api` 或 `spi` 包，默认实现用 `@ConditionalOnMissingBean` 让位 | [扩展路径](../architecture/15-扩展路径.md) | 待建：第三方提供方接入，并回归默认实现的集成测试 |
| autoconfigure 中的公开 Bean 都可以覆盖 | [O-03](08-配置与运行.md#o-03-spring-装配方式) | 待建 |
| 组件配置用 `@ConfigurationProperties` 绑定，并生成配置元数据 | [O-03](08-配置与运行.md#o-03-spring-装配方式) | 待建 |

### 失败与容错

原则：失败分为三类，每类对应确定的协议结果，并且只有一个分派点。

- 业务拒绝：调用方可以理解、可以纠正。
- 依赖不可用：暂时性故障，可以重试。
- 程序错误：属于缺陷。

| 判据 | 规则卡 | 检查 |
|---|---|---|
| 业务拒绝继承 `shared` 中带错误码的业务规则违反基类；依赖不可用继承依赖不可用基类 | [F-01](09-故障与可观测性.md#f-01-在技术边界转换错误不合并不同性质的失败) | 待建 |
| web-support 是唯一分派点，组件不注册全局异常处理 | [H-04](06-接口与错误.md#h-04-按实际语义分类失败) | 待建 |
| 业务拒绝返回 4xx 和 Problem Details（RFC 9457）；依赖不可用返回 503；程序错误返回 500 | [H-01](06-接口与错误.md#h-01-业务拒绝返回-200技术失败用对应状态)（待修订） | 待建：合同测试覆盖每一类 |
| 依赖故障时拒绝，不降级放行 | [A-03](07-安全与访问控制.md#a-03-依赖故障时拒绝不降级放行) | 自动（集成测试） |

## 耦合度量基线（2026-11-05）

用 ArchUnit 1.5.1 的 `ArchitectureMetrics` 对 `shared`、12 个组件、IAM 和网关的生产代码测量。

| 粒度 | 组件数 | 环 | 违反稳定依赖 | Lakos NCCD |
|---|---|---|---|---|
| Maven 模块 | 15 | 0 | — | 0.69 |
| 组件内（api/internal/autoconfigure 与服务职责包） | 44 | 0 | 0 | 0.62 |

D 值不作门槛的原因：Martin 的抽象度只把接口和抽象类算作抽象。由 record 和异常组成的 api 包会显得“又稳定又具体”，例如 `files.api` 的 D 是 0.88，`notification.api` 是 0.78，其实这是正常的值类型合同。反过来，`persistence.api` 在 api 包里构建连接池，这正是要发现的问题，但同包有注解，它的 D 是 0.00。D 对我们关心的问题既误报又漏报，所以“api 不放具体实现”改用结构规则检查。

同时测得的层违例：IAM 中 `interfaces → domain` 有 6 个文件，`infrastructure → interfaces` 为 0，领域层通用异常有 54 处。

## 已确认的决定（2026-11-05）

| 问题 | 决定 |
|---|---|
| 质量模型 | ISO/IEC 25010 的可维护性五个子特性，加上可靠性中的容错 |
| 北极星 | 价值：AI 一次通过率和中位交付周期；质量：原则可执行率和变更局部性；护栏：逃逸缺陷数 |
| 耦合 | 用 ArchUnit 度量，粒度分 Maven 模块级和 api/internal 级。看过基线后：无环和稳定依赖作硬规则，D 值和 NCCD 只作报表 |
| DDD 构造块 | 引入 jMolecules（新增依赖），优先使用它自带的 DDD 规则，自研规则只补缺。版本：`jmolecules-ddd` 1.10.0 与 `jmolecules-archunit` 0.33.0。技术验证结果：与 ArchUnit 1.5.1、Java 21 兼容；jmolecules-ddd 用 1.10.0 和 2.0.1 各跑一次，都是正例 0 违规、两类反例都检出。`jmolecules-archunit` 1.6.0 是按 ArchUnit 0.23 编译的，与 1.x 二进制不兼容，并且会传递引入 spring-core 5.3，不得使用 |
| 共生性 | 作为评审耦合的共同词汇；跨模块禁止意义耦合 |
| 事务边界 | 严格执行一个事务只修改一个聚合。已知违例 `AcceptInvitation` 通过重新建模邀请消除：邀请作为一次性凭据，由唯一约束防止重复使用。属于安全语义变更，具体设计在切片中确认 |
| 适配器 | 禁止 `infrastructure` 依赖 `interfaces`；`interfaces` 不依赖 `domain` |
| 扩展机制 | Spring Bean SPI；公开 Bean 可覆盖；配置用 `@ConfigurationProperties` 绑定 |
| 失败类型 | `shared` 定义业务规则违反和依赖不可用两个基类；web-support 是唯一分派点 |
| 失败协议 | 业务拒绝改用 4xx 和 Problem Details，属于不兼容的合同变更；与失败模型在同一任务（#105）中完成 |
| 反馈时间 | 单模块门禁 ≤ 3 分钟，本地完整门禁 ≤ 15 分钟，CI 墙钟 ≤ 12 分钟 |
