# 故障处理与可观测性规范

规范来源与固定输入见[第三层确认记录](../product/rebuild.md#第三层确认记录)；实际实现、验证及未完成项见[当前任务](../tasks/control-plane-verification.md#唯一任务记录)。

## 适用范围与阅读入口

适用于平台能力、官方起步模板及受统一规范约束的消费工程。按任务触发读取：

- 接入或修改普通技术日志、指标、链路及其导出：[已确认的普通观测故障原则](#已确认的普通观测故障原则)。
- 转换组件错误、处理超时或设计恢复：[故障处理与恢复责任](#故障处理与恢复责任)。
- 增加观测事件、聚合维度或调用关联：[观测数据与关联](#观测数据与关联)。
- 调整导出、缓冲、重试及健康状态：[观测隔离与资源边界](#观测隔离与资源边界)。
- 实现检查或验收观测接入与故障：[检查与真实场景](#检查与真实场景)。
- 修改关键安全管理审计：[安全管理审计失败原则](security-and-access.md#已确认的安全管理审计失败原则)及[审计内容与失败验证](security-and-access.md#审计内容与失败验证)。

失败语义的唯一原则见[合同与失败语义](system-design.md#合同与失败语义)，观测交付范围及项目责任见[应用侧可观测能力](../product/product-definition.md#应用侧可观测能力)。本规范不新增独立观测平台、默认看板或告警产品，不让技术日志代替业务事实或必要审计。

## 已确认的普通观测故障原则

- 身份与授权、数据访问及业务处理仍满足合同的前提下，不因单独的普通观测故障暂停接收正常业务请求。业务结果依实际处理表达，不能因遥测导出失败把已完成业务改写为未完成或要求重复执行。
- 隔离观测故障并暴露降级状态，限制相应资源消耗，验证影响与恢复。不能仅吞掉异常而宣称观测完全正常，也不能因继续服务就把所有能力汇总为完全健康。
- 允许部分观测数据暂时或永久缺失，不承诺全部补回。记录可核对的故障和缺失范围；无法精确计量的部分如实说明，不伪造未采集的数据或完整送达结论。
- 本项不削减正常观测能力及真实接入验证，不是允许只接入空实现或长期关闭观测。已有[关键安全管理审计责任](security-and-access.md#已确认的安全管理审计失败原则)独立适用，业务凭证与账本等业务事实仍遵守所属合同。
- 因观测重试、缓冲或故障日志耗尽资源而影响业务，是隔离缺陷，须整改及复验；不能借本项忽略实际业务不可用。启动策略仍遵守[配置与启动原则](configuration-and-runtime.md#已确认的配置与启动原则)，不把运行期选择强套于所有启动失败。
- 本项不选定 OpenTelemetry 或其他框架、采样、队列及重试机制，也不承诺第三方组件天然满足上述责任。

## 故障处理与恢复责任

在实际技术边界转换组件错误，保留合同要求的结果含义和可核对原因；业务拒绝、身份权限失败及技术故障不能仅因都表现为异常而合并处理。公开能力不泄露内部客户端类型、连接信息或敏感内容，内部诊断仍能定位失败原因。HTTP 表达引用[分类映射与验证](api-and-errors.md#分类映射与验证)，不在本规范另建错误编号或结果外壳。

按调用合同明确超时与取消的作用范围。没有取得有效完成结果时，不自行推断业务未发生；相应操作需要什么状态核对、幂等、恢复或人工处置，依实际副作用与能力设计说明。不能用统一自动重试掩盖部分完成或未知结果，也不因使用数据库事务就声称短信、文件或远程效果可被一起回滚。

采用标准客户端或框架机制时核对实际生效配置、调用层次及边界，避免嵌套重试、无界等待和重复副作用。恢复的成功条件是合同要求的实际行为恢复，不仅是连接重建、回调执行或进程仍存在。重试次数、等待预算、任务并发及人工恢复入口由后续能力设计声明并验证，不统一引入新的重试框架、降级实现或恢复状态机。

## 观测数据与关联

结构化日志及必要观测数据能识别应用、发布版本、项目或环境、实际操作与结果，并用适用的关联信息串联真实调用。请求、异步消息和任务的关联按真实支持路径声明及验证，不仅在入口生成一个 ID 就宣称跨组件链路完整；不存在或未采集的信息保持真实。

日志、指标与链路承担不同用途，必要的行为结果使用所属合同定义，参照[HTTP 消费处理与观测](api-and-errors.md#消费处理与观测)验证。不能用 HTTP 2xx 数量代替业务完成数量，也不能将业务拒绝一律统计为系统故障。采样与过滤说明支持范围及诊断影响，不能以提高成功率为由丢弃失败记录或改变统计口径。

观测内容按排障需要最小化，不记录密码、密钥、完整会话凭证或未经必要性判断的请求体与敏感业务数据。避免默认全量记录请求头、查询参数和响应内容；具体脱敏与保留要求依据字段及使用责任确定。外部传入的关联信息不是可信身份或权限依据，也不能直接作为未约束的日志内容使用。

聚合维度及输入长度具有明确边界，不把任意请求 ID、用户输入或完整资源地址机械放入无界指标标签。个体诊断通过适用日志与链路关联完成；具体字段、维度和配置只维护在相应实现及数据声明中，说明引用同一来源，不维护另一份易漂移的默认值清单。

## 观测隔离与资源边界

按已确认的可用性原则处理导出、回调与后台采集的故障，明确相应缓冲、等待、重试、线程及存储使用上限和超限行为。优先核对所选标准机制的能力，不因需要隔离就默认建设持久遥测队列或另一套容错平台。不能无限积压、阻塞正常业务或反复记录同一故障形成资源放大。

降级信息及必要自诊断在声明方式下可观察，避免只能依靠同一条已故障的导出链路发现问题。具体机制在后续接入设计中选择，不因此承诺故障时仍有完整外部告警；观测环境依旧由项目提供。能检测到的数据丢弃或导出失败如实表达，无法证明全部送达时不报告零丢失。

存活、业务流量与能力状态的职责引用[能力隔离与运行状态](configuration-and-runtime.md#能力隔离与运行状态)。普通观测降级不自动成为停止接收业务的条件，但必须能识别观测自身不可用；业务依赖或授权条件也已失败时按实际业务合同处理，不借观测容错放行。

恢复后验证实际新数据产出、接收及关联；故障期间数据只能按真实保存情况补送，不重造业务事实或假装缺口不存在。初始化及配置读取继续遵守[配置权威前提](configuration-and-runtime.md#已确认的配置权威前提)，不借观测规范重新引入 Nacos 发布内容错误治理。

## 检查与真实场景

| 约束 | 正例与必须识别的反例 |
|---|---|
| 正常真实接入 | 在项目提供的声明环境中实际产生日志、指标、健康状态及链路数据并核对消费结果；只有配置、空接口或连接成功不能作为通过 |
| 结果与关联真实 | 用真实业务成功、拒绝及技术故障验证适用数据和调用关联；误计成功、遗漏实际支持路径或伪造关联信息须识别 |
| 普通观测故障隔离 | 业务依赖正常时制造相应导出或采集故障，核对业务按合同继续、降级可识别及实际缺失；把遥测故障冒充业务失败、阻塞业务或伪报观测正常必须失败 |
| 资源与恢复边界 | 按声明负载及资源预算验证故障持续和恢复；无界积压、日志放大、恢复后没有真实数据而只报告连接正常须识别 |
| 内容与维度边界 | 验证必要脱敏、输入及聚合边界；泄露已知测试凭证或用无约束输入耗尽资源须识别，不能只搜索配置名称 |
| 审计与业务事实不混用 | 分别验证必要审计及真实业务效果；以普通观测采样、容错或丢弃替代其所属合同必须识别 |

可判定的状态、结果、字段边界及故障路径使用自动场景和有效反例；诊断信息是否充分、内容是否必要、采样是否合理及真实故障影响须有场景与源码证据的语义评审，分工遵守[任务责任](../workflow/task-execution.md#责任与人工决定)。支持的全部保证按[测试与验证规范](testing-and-verification.md#环境与真实证据)执行，缺少必需环境保留未验证，不用替身代替实际接收与恢复结果。

## 资料与验证边界

2026-10-06 经 Exa 读取的[OpenTelemetry 错误处理规范](https://opentelemetry.io/docs/specs/otel/error-handling/)要求其实现避免运行期未处理异常影响被观测应用，并描述错误诊断；它同时区分初始化失败及用户自定义错误处理。该资料支撑核对机制边界，不表示所有实现、日志框架或自定义接入天然满足本项目选择。

本项目的普通观测可用性原则来自本轮人工决定，不因引用上述资料选定 OpenTelemetry、版本或导出实现。资源参数、实际故障隔离及恢复仍须后续设计和真实验证，官方规范及本稿不构成项目运行通过证据。
