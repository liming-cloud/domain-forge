# 故障与可观测性规范

适用于错误转换、超时与重试、日志、指标、链路和健康状态。失败语义的通用要求见[系统设计 S-14、S-15](02-系统设计.md#合同与失败)，HTTP 层的表达见[接口与错误](06-接口与错误.md)。安全审计不属于普通观测，见[安全与访问控制 A-10、A-11](07-安全与访问控制.md#审计)。

## 故障处理

### F-01 在技术边界转换错误，不合并不同性质的失败

**规则**：在基础设施等实际技术边界把组件错误转换为合同结果；业务拒绝、身份权限失败、技术故障不能因为都是异常就合并处理。对外不暴露内部客户端类型、连接信息或敏感内容，但内部诊断要能定位原因。

**检查**：评审；测试覆盖各类失败的实际结果。

### F-02 超时不代表没有执行

**规则**：没有取得有效完成结果时，不推断远端业务没有发生。按实际副作用写清需要的状态核对、幂等、恢复或人工处置。不能用统一自动重试掩盖部分完成或未知结果；数据库事务也不能回滚短信、文件或远程调用的效果。

**检查**：评审；测试覆盖超时与结果未知。

### F-03 一条调用链只有一处负责重试

**规则**：写清由哪一层重试、哪些错误可重试、总时间预算、退避和抖动；各层都重试会放大负载。有副作用的重试必须满足幂等合同（[系统设计 S-15](02-系统设计.md#s-15-结果未知不能当成功)）。熔断、缓存、降级只在合同允许的结果范围内使用，不能把权限拒绝、写入失败或未知状态变成成功。核对客户端和框架实际生效的超时与重试配置，避免嵌套重试和无界等待。

**正例**：cache 组件的 Redis 客户端 `retry-attempts: 0`，重试与否由调用方按合同决定。

**检查**：评审。

### F-04 恢复以实际行为恢复为准

**规则**：恢复的判断标准是合同要求的行为恢复，而不只是连接重建、回调执行或进程仍在运行。

**检查**：测试在依赖恢复后发起新请求验证。

## 观测数据

### F-05 结构化日志能串联一次调用

**规则**：部署环境的日志使用结构化格式（ECS JSON，字段见 [F-10](#f-10-采集存储看板告警由业务项目提供)），能识别应用、版本、环境、操作和结果，并用关联 ID 串联真实的调用路径（请求、异步消息、任务）。只在入口生成 ID 不等于全链路可追踪；没有采集到的信息不伪造。

**检查**：评审；链路贯穿网关、同步调用、消息与任务，由 `scripts/verify_closure.sh` 在临时采集端中核对（见[链路追踪](../architecture/10-链路追踪.md)）；同一请求的日志按 traceId 在网关、业务服务与 IAM 中关联，由同一脚本逐行解析核对。

### F-06 不记录敏感内容

**规则**：日志、指标、链路中不记录密码、密钥、令牌、完整请求体或未经必要性判断的敏感业务数据；不默认全量记录请求头、查询参数和响应。外部传入的关联 ID 不能作为可信身份，也要限制长度后再写日志。

**检查**：评审；测试断言已知测试凭据不出现在日志中。

### F-07 指标维度有界

**规则**：指标标签只使用固定、有限的取值（应用、版本、框架提供的分类），不把请求 ID、用户输入、完整 URL 放进标签。个体诊断用日志和链路完成。业务拒绝、业务完成、系统故障分别统计，不用 HTTP 2xx 数量代替业务成功数量；采样和过滤不能为了提高成功率而丢弃失败记录。

**检查**：评审。

## 观测故障

### F-08 观测故障不影响业务

**规则**：身份授权、数据访问和业务处理正常时，单纯的观测故障（日志导出、指标、链路失败）不能导致暂停接收业务请求，也不能把已完成的业务改报为失败（2026-10-06 决定）。观测数据允许缺失，但要暴露降级状态并如实记录可核对的缺失范围，不伪造未采集的数据，也不报告零丢失。安全审计不适用这条容错。

**正例**：模板的异步日志队列容量 256，满时丢弃而不阻塞业务，并通过 `domainforge.logging.degraded` 指标暴露降级。

**检查**：测试制造观测故障，验证业务继续、降级可见。

### F-09 观测资源有上限

**规则**：导出、缓冲、重试、线程、存储都有上限和超限行为，不能无限积压、阻塞业务或反复记录同一故障造成放大。不为隔离观测故障而自建持久遥测队列或另一套容错平台。降级状态不能只通过同一条已故障的导出链路才能发现。

**检查**：评审；测试验证持续故障下的资源占用。

### F-10 采集、存储、看板、告警由业务项目提供

**规则**：平台负责应用侧观测数据的产出与对接，并提供接入说明；采集、存储、看板、告警环境由业务项目提供和管理，平台不交付默认观测工具组合。

对接方式：

| 数据 | 对接 |
|---|---|
| 指标 | 各服务管理端口上的 `/actuator/prometheus`（Prometheus 文本格式，带 `application` 标签），只在内部网络可达；业务项目的 Prometheus 在同一网络中抓取（目标为 `<服务名>:<管理端口>`，IAM 9091、网关 9093、模板服务 9092）。指标不附带链路 exemplars，日志与链路按 traceId 关联 |
| 日志 | 部署环境（`config-center` profile）每条日志是一行 ECS JSON，写到标准输出，由业务项目的采集端从容器日志读取；本地开发为文本。固定字段：`@timestamp`、`log.level`、`log.logger`、`service.name`（服务名）、`message`，有当前链路时带顶层 `traceId`、`spanId`；异常在 `error.*` 中。每个请求一条访问日志：网关 `gateway_access trace_id=… method=… path=… status=… route=… millis=…`，其他服务 `http_access method=… path=… status=… millis=…`（不含查询参数）。按 traceId 关联一次请求在各服务中的日志。各服务的 `logback-spring.xml` 注册状态监听器，Logback 的内部状态不以文本写到标准输出（配置错误仍使启动失败）。RocketMQ 客户端自带日志实现、不经 SLF4J，部署镜像把它的内部日志写到容器内 `/tmp/rocketmq`（不采集），消息收发结果以消息组件的日志与指标为准 |
| 链路 | OTLP 导出，见[链路追踪](../architecture/10-链路追踪.md) |
| 健康 | 管理端口上的 `/actuator/health/liveness`、`/readiness`，部署参考的容器健康检查使用 readiness |

`scripts/verify_closure.sh` 以临时 Prometheus 与 Jaeger 验证指标与链路可被采集和查询，并逐行按 JSON 解析各服务日志、按 traceId 关联；临时观测端不进入部署参考（[#44](https://github.com/liming-cloud/domain-forge/issues/44)）。

**检查**：评审。
