## 工程职责与类型边界

技术对象以实际职责判断，不以 `Service`、`Repository` 等类名或所在目录代替判断。

| 对象 | 归属及使用要求 |
|---|---|
| 业务仓储与查询出口 | 表达上下文实际需要的业务读写或展示合同；输入、结果及错误不携带持久化技术，遵守既有端口规则 |
| 仓储、查询适配器 | 位于基础设施，使用 Mapper 完成实际操作，负责对象转换、结果解释和技术失败映射 |
| 持久化对象及映射 | 位于基础设施，承载表、列及存储相关配置；采用领域模型时保持独立对象并完成转换 |
| Mapper、Wrapper、分页及框架通用基类 | 位于基础设施内部；不进入应用、领域或公开合同，包括其泛型、字段和继承关系 |
| 插件、数据源与会话配置 | 属于技术接入和装配；声明实际扫描范围、资源绑定及启用条件，不交给领域对象选择 |

`BaseMapper`、`IService`、`IRepository`、`ServiceImpl`、`CrudRepository` 等均是框架技术抽象，不能充当应用用例或领域仓储协议。必要时可在基础设施内部复用，不要求每个 Mapper 额外生成通用 Service 或 Repository 包装。

示例仅表达结构，不预定产品模型：业务用例调用自己的仓储协议，基础设施适配器使用 Mapper 操作持久化对象并重建模型；展示查询可由查询适配器直接生成技术无关结果。应用继承框架通用 Service、领域类继承 Active Record `Model`、公开接口返回 `IPage<PO>`，均不符合边界。

没有采用领域模型的轻量业务按既有适用条件实现，仍由基础设施承担数据访问。代码生成结果、改名或降低可见性不能免除适用规范；生成器模板和输出也要经过同一验证。

## 查询与 SQL

- 简单读写复用适用的通用 Mapper 和查询能力；复杂关联、统计或特殊更新使用清晰的自定义 SQL，不为调用链形式统一而强行拼装。SQL 属于 Mapper 的技术实现，XML 或注解选择以可读性、复杂度和验证需要为依据。
- 值使用参数绑定，不能直接拼入 SQL。外部排序、字段或筛选选项映射为服务端允许的选项，不接受客户端 SQL 片段；SQL 注入检测工具仅是辅助，不能替代白名单和合同限制。
- 明确结果字段、空结果、单行与多行含义，以及适用的空值、枚举、精度和时间语义。要求唯一结果时不能通过任意取一条掩盖重复或错误条件。
- 查询明确归属、权限和数据范围的执行责任；不能借自定义 SQL、联表或插件忽略跨上下文私有数据边界。自定义和通用查询都要验证范围内、范围外及拒绝场景。
- 面向列表的查询声明分页或其他有界读取方式、最大规模、排序及空集合行为。批量和导出按实际需求声明分批及资源前提，不以关掉分页获取全部数据替代设计。
- 使用分页插件时核对版本依赖、方言、插件顺序、分页输入及 COUNT 语义。关联、分组等复杂查询按真实数据验证总数与记录，不默认相信自动改写正确。
- 新增复杂或大规模查询说明索引与访问路径依据，在声明的数据量和负载下验证性能。不能只用极小测试数据推导生产表现，也不为所有简单查询机械增加完整性能报告。
- 启用会话或其他持久化缓存时说明数据可见性与失效责任，验证变化后的读取；不将其默认当作平台缓存能力或强一致保证。

技术依据：[MyBatis 映射说明](https://mybatis.org/mybatis-3/sqlmap-xml.html)说明参数绑定和结果映射；[MyBatis-Plus 安全说明](https://baomidou.com/guides/security/)指出 SQL 片段及动态字段风险和检测覆盖限制；[分页说明](https://baomidou.com/plugins/pagination/)说明方言、插件顺序与 COUNT 改写条件。具体项目合同及验收结果仍需独立验证。

## 写入与并发

- 每项写入明确允许修改的字段、目标范围和适用前置条件；不能把客户端数据直接绑定成可写 PO，或通过通用更新越过业务操作和授权。
- 更新与删除使用明确的业务目标和范围条件。普通功能不能执行无范围保护的全表更新或删除；确有批量维护需求时，单独说明目标、授权和恢复方式，不能当作普通接口自动放行。
- 明确受影响行数与驱动、语句的实际含义，处理未匹配、同值更新、冲突及异常结果。不能把布尔返回当作业务完成，或无依据地把所有零行结果解释为同一种失败。
- 存在并发约束时，按需要使用数据库约束、条件更新、版本比较或锁定等机制，并说明冲突合同。事前查询不能单独保证后续写入仍满足条件；已承诺的约束须有真实并发证据。
- 业务唯一性、必要引用完整性与合法状态分别说明维护责任；数据库可有效维护的约束不能仅靠应用事前检查。逻辑删除、主键策略、自动填充及版本列按实际需求选择，不统一向每张表添加没有职责的字段。
- 使用乐观锁时验证插件是否覆盖所用方法、自定义更新是否执行版本条件、零行结果及回写语义；仅添加 `@Version` 不算验证。可变 Wrapper 按本次操作创建，不能作为共享状态或随意复用。
- 批量操作说明数量上限、分批、整体或分段提交、部分成功及恢复责任。实际执行、批处理刷新和提交失败都须按合同处理，不能忽略部分结果或把已受理等同于全部完成。

技术依据：[乐观锁插件说明](https://baomidou.com/plugins/optimistic-locker/)列出支持方法、版本回写及 Wrapper 使用限制；[全表操作保护说明](https://baomidou.com/plugins/block-attack/)提供拦截能力。插件是否已启用、条件是否表达正确的业务范围及自定义 SQL 是否受保护，仍需测试和评审，插件不能替代权限与业务规则。

## 事务与多数据源

确认来源：2026-10-13，本会话用户选择 A：“统一默认异常回滚，特殊提交显式声明”，采用 Spring 原生配置，包含受检异常。

确认来源：2026-10-13，本会话用户选择 A：“技术装配前置路由；应用保留 `@Transactional`，装配层按明确的用例与资源绑定，先选库再启动事务，集中验证切面顺序”。

确认来源：2026-10-13，本会话用户选择 A：“采用 dynamic-datasource；数据源按配置别名接入，基础设施适配器用 `@DS` 选择”。

按需多数据源默认采用 dynamic-datasource，以配置别名接入；由基础设施适配器通过 `@DS` 选择数据源，领域与应用层不直接选择数据库。确切版本和实际组合须经过校准，本项不引入分布式事务。确认来源见[多数据源接入决定](05-持久化.md#事务与多数据源)。

应用明确业务事务范围，技术接入落实资源和执行机制；不将每个 Mapper 调用机械视为完整业务事务。

应用 `@Transactional` 涉及非默认资源时，由技术装配将明确的用例操作绑定到数据源别名，在事务启动前完成路由；不能等仓储 `@DS` 执行时再改变已绑定的连接。应用及领域仍不声明数据库选择。装配必须验证操作绑定、路由先于事务的切面顺序、事务内资源一致及调用后的路由恢复；未知绑定不得静默回落。具体装配形式由能力设计落实，不规定全项目固定的切面数值。确认来源见[事务前置路由决定](05-持久化.md#事务与多数据源)。

| 场景 | 必要设计及验证 |
|---|---|
| 单库原子操作 | 明确实际事务入口、事务管理器、数据源与会话绑定、参与方式和回滚规则；真实验证提交及后续失败回滚 |
| 声明式事务 | 核对代理、方法调用方式和异常策略；验证事务确实生效，不能只检查注解存在或依赖测试自身事务掩盖错误 |
| 跨上下文本地事务 | 按已确认原则通过公开合同协作，验证实际共享资源，不因同进程或相同地址推定原子性 |
| 多数据源接入 | 明确默认源、别名、数据归属、读写权限、Mapper 与会话及事务管理器绑定；真实验证路由和隔离 |
| 非事务副作用或独立资源 | 遵守既有一致性和恢复合同，不把消息、文件或多个独立事务解释为可共同回滚 |

默认单数据源与按需启用多数据源均须真实实现。未知或无效的数据源选择不能静默回落到错误的默认源；事务中不得通过隐式切换改变已声明的资源与原子性前提。跨线程或独立事务的参与关系也须显式说明并验证。

业务事务统一默认对传播出事务边界的异常回滚，包含受检异常，采用 Spring 原生全异常回滚配置。确需异常后提交的特殊场景必须显式声明原生例外规则，并按独立合同验证真实提交结果；不以异常类型的框架默认差异决定业务数据结果。确认来源见[默认异常回滚决定](05-持久化.md#事务与多数据源)。

不能捕获异常后返回成功使应回滚的事务提交；使用返回值表达业务拒绝时，仍按实际失败合同落实事务结果，不假定错误返回值会自动回滚。超时、冲突或依赖失败后的重试须遵守幂等与副作用合同，不统一无条件重试所有写操作。

技术依据：[MyBatis-Spring 事务说明](https://mybatis.org/spring/transactions.html)要求事务管理器与会话工厂使用匹配的数据源，并说明事务外调用的提交语义；[Spring 事务注解说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)说明代理、自调用、方法可见性、异常规则及多个事务管理器的条件。具体事务装配与版本组合须由实际校准固定，不从组件选型推定已通过。

## 数据结构与迁移

表、列和索引按所属上下文的数据与场景设计，明确标识、业务唯一性、字段类型、精度、字符与时间规则、空值、默认值及删除语义。PO 与领域对象的映射及重建按既有分离规则验证，不凭空生成全项目万能基类或全量复制所有对象。

数据库结构、必要基线与经设计确认的初始化数据通过版本化迁移管理，明确归属、执行顺序和支持的起始版本。业务启动逻辑不隐式建表、改表或反复覆盖初始化数据；自动执行版本化迁移与业务代码临时补写是不同动作。

敏感初值不硬编码，注入来源、缺失行为及执行权限在安全规范和对应能力设计中明确。初始化只处理已经确认的必要数据，不由生成器自行创建默认业务账户或权限。

迁移须验证空库初始化、受支持版本升级、既有数据兼容及失败后的状态与恢复办法。数据结构变化、应用回退和数据恢复分别说明前提，不假设所有 DDL 都能事务回滚或自动逆转；多个数据源分别明确迁移执行与失败责任。

支持新增数据库或更改驱动、方言时，重新验证类型、约束、SQL、并发、迁移及恢复，不将 MyBatis-Plus 的数据库支持列表直接变成平台已验证的兼容承诺。默认数据库及迁移工具分别见[已确认的关系数据库](#已确认的关系数据库)与[已确认的迁移工具](#已确认的迁移工具)；具体版本组合仍待验证。

## Flyway 迁移要求

本节落实迁移工具的工程约束，不重复数据结构、初始化与恢复的通用规则。

- 每条迁移明确所属数据源、Schema、扫描路径、执行责任及历史记录范围。平台与业务项目各自维护所拥有的数据；不得因依赖制品包含 SQL 就无边界扫描、自动改动其他项目或上下文的私有数据。多个数据源分别验证实际执行目标。
- 版本化 SQL 使用唯一版本与明确描述，例如 `V1__init.sql`；同一执行范围内避免版本冲突。已应用于长期保留环境的迁移不原地改写，通过新增迁移修正。可重复执行脚本仅用于确有重建需求的对象，不反复覆盖业务数据或初始化账户。
- 核对迁移文件与既有历史的一致性，按选定版本和执行阶段处理合法的待执行升级。迁移后验证目标版本、实际结构及数据结果；历史与校验和验证不能替代真实结构、数据兼容和业务场景验证。
- 明确单条脚本及整个升级的实际事务范围。PostgreSQL 存在不能在事务内执行的语句，需要非事务执行时单独声明前提、失败残留及恢复办法；不能为解决一条语句的问题统一关闭所有迁移事务，也不能假定后续脚本失败会回滚此前已提交的脚本。
- 发现校验差异、执行失败或未知历史时先定位原因，保留真实状态。不能自动执行 `repair`、`baseline`、关闭验证或 `clean` 来消除错误；有实际恢复需要时说明精确目标、历史与数据状态、操作后果及适用审批。`repair` 修复历史记录，不等于实际结构和数据已恢复。
- 检查声明的迁移是否确实被发现并执行，不能在需要迁移时因错误扫描路径或命名导致遗漏仍报告通过。已达目标版本且无待执行迁移是合法情形，须由历史与结果证明，不机械要求每次执行都产生变更。

技术依据：[Flyway 版本化迁移](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/versioned-migrations)说明版本、顺序、历史及校验和；[迁移发现与执行](https://documentation.red-gate.com/flyway/flyway-concepts/migrations)说明路径扫描与不同迁移形式；[事务处理](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/migration-transaction-handling)说明按脚本提交及非事务语句的条件；[Validate](https://documentation.red-gate.com/flyway/reference/commands/validate)与 [Repair](https://documentation.red-gate.com/flyway/reference/commands/repair)区分一致性验证与历史修复。具体命令、配置、接入模块和能力范围须按最终版本核对。

## PostgreSQL 适配要求

本节说明选定数据库后必须落实的语义，不预定业务字段、统一主键方案或事务隔离级别。通用读写、事务与迁移规则仍以各自正文为准。

| 对象 | 设计及真实验证要求 |
|---|---|
| 精确数量与金额 | 依据单位、范围和舍入规则选择精确表示，例如带明确精度与标度的 `numeric`，或有明确单位的整数；不能用浮点近似替代精确合同。验证 Java 映射、边界、超限及舍入，不能默认数据库舍入与业务规则一致 |
| 日期与时间 | 区分日期、本地时间及时间点，明确列类型、Java 映射、精度、连接时区与序列化。`timestamptz` 不保留原始时区标识，需要该语义时单独设计；不能把未带时区的时间静默当作确定时间点 |
| 标识生成 | 明确由应用还是数据库生成、实际返回值及唯一约束。采用序列时允许分配值出现间隙；业务连续编号不能由序列和事务回滚的假定实现，也不要求全部业务采用序列 |
| 隔离与并发失败 | 明确实际连接和事务隔离配置，按已声明业务约束验证并发结果。不能因开启事务就假定多次查询看到同一快照；需要重试时验证整个事务及副作用的处理，不统一提高隔离级别或无条件重试 |

技术依据：[PostgreSQL 数值类型](https://www.postgresql.org/docs/current/datatype-numeric.html)说明精确类型、精度、舍入与序列间隙；[日期与时间](https://www.postgresql.org/docs/current/datatype-datetime.html)说明时间类型及 `timestamptz` 的时区转换与存储；[事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)说明默认 Read Committed 的语句快照、隔离失败及序列的非回滚行为。实际采用时按固定版本复核，官方文档不能代替驱动映射、并发和迁移测试。

## 验证与失败反例

框架类型及角色检查负责可判定边界，数据库结果和业务语义需要真实场景与语义评审，分工遵守[任务责任](../workflow/02-任务执行.md#责任与人工决定)。

| 验证对象 | 必须识别的失败或不符合情形 |
|---|---|
| 技术隔离 | 应用继承框架通用 Service 或 Repository；公开合同经字段、泛型或继承暴露 Wrapper、PO 或 IPage；领域类承担存储操作 |
| 映射与重建 | 转换遗漏或误解释业务状态；保存重建后行为失效；仅靠测试替身掩盖真实类型或默认值差异 |
| 查询合同 | 越权或范围外数据被返回、动态字段绕过限制、复杂分页记录与总数不符 |
| 写入与并发 | 丢失更新、重复数据、错误更新范围或部分批处理结果被当作成功；按实际声明的约束判断 |
| 插件保护 | 关闭必需插件、使用不受覆盖的自定义方法或错误配置仍宣称相应保护通过 |
| 事务与路由 | 声明的失败未回滚、事务入口失效、资源绑定错误、错误数据源或独立提交被当作共同原子提交 |
| 迁移历史与执行 | 原地改写已应用的迁移、版本冲突、扫描遗漏或执行目标错误仍通过；自动修复历史掩盖未经核实的差异 |
| 迁移与恢复 | 只能新建空库而无法从支持的既有状态升级；失败后状态不明或恢复步骤未验证 |

自动检查也要有允许场景，不能误拒绝基础设施内部正常的框架复用或合法维护操作。SQL 权限、索引必要性、字段含义及事务合同不能仅靠关键词扫描判定；用源码、实际数据和场景结果评审。

真实数据库、所声明驱动及必要环境缺失时保留未验证状态。内存替代数据库、Mock 或测试事务自动回滚不能替代所有真实语义。校验器采用隔离反例，发现不符合时整改并复验；限定机制及其支持范围见[工程校准](../workflow/04-工程检查设计.md#默认职责与技术注解校准)，实际结果只在任务与报告中维护。
