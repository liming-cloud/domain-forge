# 持久化规范

适用于关系数据的读写、事务和迁移。业务边界见[系统设计](02-系统设计.md)，产品范围见[产品定义](../product/01-产品定义.md#关系持久化与多数据源边界)。

每条规则的写法：**规则**是必须做到的事；**理由**说明为什么；**正例／反例**给出具体样子；**检查**说明由谁发现违规（自动规则或人工评审）。

## 技术选型

| 项 | 决定 |
|---|---|
| ORM | MyBatis-Plus。不因框架提供通用 Service、Active Record 或代码生成器就采用其分层 |
| 数据库 | PostgreSQL。其他数据库不因 MyBatis-Plus 支持就算平台支持，新增须完整验证 |
| 迁移 | Flyway，应用启动时自动执行版本化 SQL（2026-10-13 决定），应用进程持有迁移凭据 |
| 多数据源 | dynamic-datasource，按配置别名接入，基础设施适配器用 `@DS` 选择（2026-10-13 决定）。MVP 不交付 |
| 事务回滚 | 全异常回滚，包含受检异常；需要异常后提交的场景显式声明（2026-10-13 决定） |

## 职责与类型

### P-01 持久化技术只出现在 infrastructure

**规则**：Mapper、PO、Wrapper、`IPage`、`BaseMapper`、`IService` 等框架类型只在 `infrastructure` 中使用；应用和领域通过自己定义的仓储或查询接口访问数据，接口的参数、返回值和异常都不携带持久化类型。

**理由**：业务规则不应随 ORM 变化而改动；公开合同泄漏 PO 会让调用方绕过业务操作直接改数据。

**正例**：

```java
// application/query/account/AccountQueries.java —— 技术无关的查询合同
public interface AccountQueries {
  AccountPage list(long cursor, int limit);
}

// infrastructure/query/account/SqlAccountQueries.java —— 用 Mapper 实现
@Component
class SqlAccountQueries implements AccountQueries {
  private final AccountQueryMapper mapper;
  ...
}
```

**反例**：应用类继承 `ServiceImpl<AccountMapper, AccountPo>`；领域类继承 `Model<Account>`；接口返回 `IPage<AccountPo>`。

**检查**：自动（架构规则 `[技术边界]`、`[依赖方向]`），评审核对公开合同的泛型与字段。

### P-02 PO 与领域对象分开

**规则**：采用领域模型时，PO 只承载表和列，由基础设施适配器完成 PO 与领域对象之间的转换和重建；字段相同也不合并。没有复杂不变量的轻量业务可以不建领域模型，但数据访问仍在基础设施。

**理由**：PO 跟随表结构变化，领域对象跟随业务规则变化，两者合并后任何一方变化都会波及另一方。

**检查**：评审。测试应覆盖"保存后重建，行为不变"。

## 查询与 SQL

### P-03 SQL 写在 Mapper XML

**规则**：自定义 SQL 放在 `src/main/resources/mapper/<职责>/*.xml`，namespace 等于 Mapper 全名，statement id 等于方法名。简单读写可以用 MyBatis-Plus 的类型安全链式条件（`eq`、`in`、`orderByAsc` 等）。禁止：

- `@Select`、`@Insert`、`@Update`、`@Delete` 及对应的 `*Provider` 注解；
- Java 中的 SQL 字符串或文本块；
- `apply`、`last`、`setSql`、`inSql`、`exists` 等拼接原始 SQL 片段的方法。

`@Mapper`、`@Param` 和字段映射注解不受限制。测试用的 SQL 同样放在资源文件中。

**理由**：SQL 集中在 XML 便于评审和查找；拼接原始片段是 SQL 注入的主要来源。

**正例**：

```xml
<mapper namespace="org.domainforge.iam.infrastructure.query.account.AccountQueryMapper">
  <select id="list" resultType="...AccountProjection">
    SELECT id, login_name, enabled FROM iam_account
    WHERE id &gt; #{cursor} ORDER BY id LIMIT #{limit}
  </select>
</mapper>
```

**反例**：

```java
@Select("select * from iam_account where id = #{id}")   // SQL 注解
wrapper.apply("login_name = '" + name + "'");          // 原始片段拼接
```

**检查**：自动（架构规则 `[SQL 位置]`、Checkstyle `IllegalTokenText`）。

### P-04 值用参数绑定，排序和字段用白名单

**规则**：所有值用 `#{}` 绑定，不用 `${}` 拼接。客户端传来的排序、字段或筛选选项先映射为服务端定义的枚举，再选择对应的 SQL；不接受客户端提供的 SQL 片段。

**理由**：参数绑定是防注入的唯一可靠手段，检测工具只能辅助。

**检查**：评审（XML 中出现 `${` 时必须说明来源是服务端白名单）。

### P-05 列表查询必须有界

**规则**：列表查询声明分页或其他有界读取方式、单次最大条数、排序和空集合行为。批量和导出单独设计分批。复杂关联、分组查询如使用分页插件，要用真实数据验证总数与记录一致。

**理由**：无界查询在数据增长后会拖垮数据库和内存。

**正例**：IAM 账号列表最多 100 条、按 ID 游标分页、不查总数。

**检查**：评审；持久化组件的分页插件把单页上限限制在 `domainforge.persistence.max-page-size`（默认 200）。

### P-06 查询负责数据范围

**规则**：有权限或数据范围要求的查询，范围条件由服务端根据可信身份生成并作为参数绑定进 SQL；客户端不能自己提供可信范围。不能通过联表读取其他上下文的私有表。

**检查**：评审；测试覆盖范围内、范围外和拒绝三种情况。

### P-07 明确结果语义

**规则**：写清单行、多行、空结果、空值、枚举、精度和时间的含义。要求唯一结果时，出现多条要报错，不能任取一条。

**检查**：评审。

## 写入与并发

### P-08 写入有明确目标和字段

**规则**：每项写入明确允许修改的字段、目标范围和前置条件。不把客户端数据直接绑定成 PO 保存；更新和删除必须带业务目标条件，普通功能不做全表更新或删除。

**理由**：通用更新会绕过业务操作和授权。

**检查**：评审。

### P-09 并发约束由数据库保证

**规则**：业务唯一性、引用完整性和需要防并发的条件，用唯一约束、条件更新、版本比较或行锁保证。"先查再写"不能单独保证并发正确。明确冲突时的返回（例如 HTTP 409）。使用乐观锁时验证自定义更新确实带版本条件，只加 `@Version` 不算完成。

**理由**：查询与写入之间的数据可能已被其他事务修改。

**正例**：邀请注册用唯一约束 + 行锁保证一个邀请只能被消费一次，并有真实并发测试。

**检查**：评审；已承诺的并发约束必须有真实数据库并发测试。

### P-10 正确解释影响行数

**规则**：处理未匹配、同值更新、冲突和异常等结果，不把布尔返回值当作业务完成，也不把所有零行结果都解释成同一种失败。批量操作说明上限、分批、部分成功和恢复方式。

**检查**：评审。

## 事务

### P-11 事务由应用用例决定

**规则**：在应用用例入口使用 `@Transactional`（默认 REQUIRED、全异常回滚），基础设施加入该事务。不把每次 Mapper 调用当作完整业务事务，也不另造事务包装接口。慢操作（如密码哈希、远程调用）放在事务外；只需要短事务时可以用 Spring 原生 `TransactionOperations`。

**理由**：事务边界是业务决定，应和用例在一起。

**检查**：评审；测试在真实代理入口上验证提交和中途失败回滚。

### P-12 不让事务静默失效

**规则**：注意自调用、非 public 方法、跨线程执行都不会进入事务。不捕获异常后返回成功（会导致本应回滚的事务提交）。用返回值表达业务拒绝时，自己确保事务回滚。`readOnly` 只是提示，不能替代权限或无写入约束。

**反例**：

```java
@Transactional
public Result execute(Command command) {
  try {
    repository.save(...);
    audit.record(...);
  } catch (RuntimeException e) {
    return Result.failed();   // 事务被提交，save 的数据保留
  }
}
```

**检查**：评审；测试覆盖失败路径的回滚结果。

### P-13 资源绑定明确

**规则**：事务管理器、`SqlSessionFactory`、Flyway 必须使用同一个数据源。持久化组件按 Spring 原生默认 Bean 名（`dataSource`、`transactionManager`、`sqlSessionFactory`、`flyway`）绑定并在启动时校验，不一致直接启动失败。多数据源时，路由必须在事务开始前完成，未知数据源不能静默回落到默认库。

**检查**：自动（持久化组件启动校验）；多数据源接入时补充路由测试。

### P-14 跨资源没有原子性

**规则**：多个数据源、跨服务调用、Redis、文件、短信都不在数据库事务回滚范围内。涉及多个资源时写清各自的事务范围、中间状态、失败恢复，不假定能一起回滚。需要可靠消息时采用同事务 Outbox（见[总体架构](../architecture/01-总体架构.md#领域事件与集成事件)）。

**检查**：评审。

## 迁移

### P-15 结构变更只通过版本化迁移

**规则**：表结构和必要初始化数据只通过 Flyway 版本化 SQL（`V<n>__<描述>.sql`）变更。业务代码不建表、不改表、不反复覆盖初始化数据。敏感初值（如管理员密码）不写进迁移，通过受控方式注入。

**检查**：评审。

### P-16 已应用的迁移不改写

**规则**：已经在长期环境执行过的迁移文件不修改，用新迁移修正。校验失败或历史异常时先定位原因，不自动执行 `repair`、`baseline`、`clean` 或关闭校验。

**理由**：改写已应用的迁移会让各环境的结构悄悄分叉。

**检查**：评审；模板与服务配置固定 `clean-disabled=true`、`validate-on-migrate=true`。

### P-17 迁移的事务与恢复

**规则**：明确每条脚本的事务范围。PostgreSQL 中不能在事务内执行的语句（如 `CREATE INDEX CONCURRENTLY`）单独成文件并说明失败残留。验证空库初始化和从支持版本升级两条路径；应用回退与数据恢复分开说明。

**检查**：评审；集成测试至少覆盖空库初始化。

## PostgreSQL 类型

### P-18 选对类型

**规则**：

| 数据 | 要求 |
|---|---|
| 金额、精确数量 | `numeric(p,s)` 或带单位的整数，不用浮点 |
| 时间点 | `timestamptz`；需要保留原始时区时另存时区字段 |
| 日期、本地时间 | `date`、`time`，不当作时间点 |
| 主键 | 写清由应用还是数据库生成；序列会有间隙，业务连续编号不能依赖序列 |
| 并发 | 默认 Read Committed，同一事务中的多次查询不保证看到同一快照；不统一提高隔离级别 |

**检查**：评审；边界值、精度和时区有映射测试。

## 集成事件

### P-19 集成事件经同事务 Outbox 发布

**规则**：需要可靠送达其他服务的集成事件，在业务事务内经 `domain-forge-messaging` 的 `EventPublisher` 写入 Outbox，与业务数据一起提交；不在事务提交后直接发送消息，也不使用中间件的事务消息。消费方实现 `EventHandler`，处理者只做本地事务内的写入，依赖组件的去重保证同一事件只生效一次；不能假定恰好一次或全局顺序，需要顺序时显式给出顺序键并使用 FIFO 主题。设计见[消息与 Outbox](../architecture/08-消息与Outbox.md)。

**检查**：评审；测试覆盖回滚不发布、重复投递不重复生效、不认识的合同版本不被静默跳过。

## 测试要求

- 持久化相关的测试使用真实 PostgreSQL（集成测试，见[工程与构建](../architecture/02-工程与构建.md#集成测试)），不用内存数据库或 Mock 代替事务、约束和并发语义。
- 必须覆盖：事务提交与失败回滚、已承诺的并发冲突、查询的范围内与范围外、迁移的空库初始化。
