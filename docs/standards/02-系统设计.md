# 系统设计规范

适用于平台能力和业务项目的系统设计。目录布局、命令与查询路径、事件与事务的完整说明见[总体架构](../architecture/01-总体架构.md#ddd-边界与代码映射)；需求与建模见[需求与领域建模](01-需求与领域建模.md)。

## 职责与依赖

### S-01 五个职责各管各的事

**规则**：业务服务按下表分工，包名为 `<上下文根>.<职责>`：

| 职责 | 负责 | 不负责 |
|---|---|---|
| `interfaces` | 协议解析、输入格式校验、取得身份、调用用例、结果转换 | 直接访问数据库或客户端；业务判断 |
| `application` | 编排用例、授权与数据范围、事务边界、调用领域模型和外部能力 | 重复领域规则；直接使用 Mapper、SDK |
| `domain` | 业务概念、状态、计算和不变量 | 依赖任何框架、HTTP、数据库或远程调用 |
| `infrastructure` | 数据访问、对象转换、技术客户端、适配实现 | 决定业务成功、权限或规则 |
| `bootstrap` | 启动、配置、接线、生命周期 | 业务逻辑、查询、SQL |

依赖方向：`interfaces → application → domain`；`infrastructure` 实现 `application`、`domain` 定义的接口；`bootstrap` 可以依赖全部，其他职责都不依赖 `bootstrap`。

**检查**：自动（架构规则 `[职责归属]`、`[依赖方向]`、`[技术边界]`）；规则放得对不对由评审判断。

### S-02 领域层不依赖框架

**规则**：领域层只依赖 JDK 和 `org.domainforge.shared`。不使用 Spring、ORM、Web、序列化注解；`shared` 中的传输类型（如 `ApiResponse`）也不进入领域。

**理由**：领域模型应能脱离容器、数据库和网络直接测试。

**检查**：自动（`[技术边界]`）。

### S-03 应用层只用必要的框架元数据

**规则**：应用层可以使用 `@Service`、`@Component`、`@Autowired`、`@Qualifier`、`@Transactional`（及其 `Propagation`、`Isolation`）、需要短事务时的 `TransactionOperations`（及其回调 `TransactionCallback`、`TransactionStatus`），以及组件 `api` 包中的技术无关接口（2026-10-12 决定）。不直接使用 Mapper、PO、DataSource、Redis、HTTP 客户端或其他 SDK；不为去掉这些注解而增加一层事务包装接口。

**检查**：自动（`[技术边界]`）；评审核对注解没有被用来绑定技术行为。

### S-04 授权在后端用例边界执行

**规则**：每个公开操作写清身份、操作权限、资源权限和数据范围由谁检查，覆盖实际的 HTTP、消息、定时任务和内部调用入口。用可信身份和业务事实判断归属；接口隐藏、前端限制、客户端自报属性都不能代替授权。新增入口时重新验证同一用例的权限和失败场景。

**检查**：评审；测试覆盖允许、拒绝和越权场景。安全细则见[安全与访问控制](07-安全与访问控制.md)。

## 上下文与部署

### S-05 多个上下文可以同一应用部署

**规则**：上下文划分（业务语义）与部署单元（一起发布运行的代码）分开决定。允许多个上下文同一应用部署；只有在独立发布、扩缩容、故障隔离等实际要求驱动时才拆分服务，并写明依据、收益和成本。同进程、同库、多数据源都不能成为访问其他上下文私有数据的理由。

**检查**：评审。

### S-06 默认一个服务一个 Maven 模块，用包划分边界

**规则**：上下文默认在同一构建模块内按包组织；只有需要独立版本、独立复用或技术隔离时才拆模块。跨上下文只能引用对方公开的合同（`application.contract`），不访问其内部实现；语言层面的 `public` 不等于允许跨模块使用。依赖要显式声明，上下文之间不能形成依赖环。

**检查**：自动（`[跨上下文]`、`[内部实现]`、依赖声明检查）。

## 用例入口与出口

### S-07 用公开应用方法作为用例入口

**规则**：默认直接调用应用类的公开方法；只有存在实现替换或需要独立维护的合同时，才抽取入口接口。HTTP、消息、定时任务可以复用同一用例，各自只做协议适配。用例的参数和返回值不携带 HTTP 请求、响应或消息客户端类型。

**反例**：每个用例都生成 `XxxUseCase` 接口和唯一的 `XxxUseCaseImpl`。

**检查**：评审；用例行为测试直接调用用例方法。

### S-08 出口：业务语义建接口，通用能力直接用

**规则**：

| 情形 | 做法 |
|---|---|
| 本上下文特有的业务能力（如订单仓储、库存预留） | 在 `application.port` 或 `domain.repository` 定义接口，基础设施实现 |
| 平台已提供技术无关的通用能力合同（如短信发送、文件存储），且满足需要 | 应用层直接使用，不再包一层本地接口 |
| 平台合同表达不了本上下文语义，或确有替换需要 | 增加本地接口和适配，写明它隐藏了什么差异 |
| 只有具体客户端或框架 API | 在基础设施中适配成接口再给用例使用 |

出口接口的参数、结果和异常都不能携带 SDK 响应、ORM 对象或查询构造器，包括嵌套字段。

**检查**：自动（`[技术边界]` 检查直接依赖）；嵌套字段和失败语义由评审核对。

## 查询

### S-09 纯查询走短路径

**规则**：采用轻量 CQRS，默认同库同步。纯展示查询的路径是 `Controller → 查询合同（application.query）→ 基础设施实现 → SQL → ReadDTO`，不加只转发的 QueryHandler、QueryService，也不重建聚合。需要资源授权决策、跨源编排或业务判断时，才增加有职责的查询用例。

**正例**：`AccountQueries.list(...)` 是应用层查询合同，`SqlAccountQueries` 在基础设施实现并直接投影 `AccountView`。

**反例**：Controller 直接注入 Mapper；为纯展示查询先加载聚合再转 DTO。

**检查**：自动（`interfaces` 不能依赖 `infrastructure`）；评审判断是否需要查询用例。

### S-10 查询不改业务状态，并负责数据范围

**规则**：查询不修改业务状态（安全审计和观测记录除外）。每项查询写清权限和数据范围由谁执行，测试覆盖授权、拒绝、范围外数据和依赖失败。需要其他上下文的数据时使用其公开查询合同，不联表读取对方私有表。查询结果用于后续写入时，写入时重新校验当前条件。

**检查**：评审；测试覆盖范围内与范围外。

## 事务与一致性

### S-11 一起生效的操作必须共享真实的本地事务

**规则**：业务要求一起成功或回滚，且调用链实际共享一个本地事务资源时，可以共同提交。先写清必须维持的约束、哪些状态须原子生效、允许的暂时不一致和失败结果，再选择事务方式。同进程、同数据库地址或有 `@Transactional` 注解，都不能证明参与了同一事务。

**检查**：测试在真实数据库上验证整体提交和中途失败回滚。持久化细则见[持久化 P-11 至 P-14](05-持久化.md#事务)。

### S-12 跨资源、跨服务没有原子性

**规则**：不同数据源、不同服务、短信、文件、远程调用、消息发送都不在数据库事务的回滚范围内。这类流程写清：每步何时提交、暂时状态和可见延迟、重试与重复、补偿或人工处理、业务何时算成功。需要可靠消息时使用同事务 Outbox（见[总体架构](../architecture/01-总体架构.md#领域事件与集成事件)）。拆分服务或事务资源时，重新设计一致性。

**反例**：为了原子提交，直接写另一个上下文的私有表。

**检查**：评审；测试验证故障时的实际结果。

## 对象分离

### S-13 领域对象与持久化对象始终分开

**规则**：领域对象表达业务，持久化对象（PO）表达存储结构，由基础设施转换；即使字段接近也分开。不要求领域类型与表一一对应。写清哪些状态被保存、如何重建、哪些值计算得出。展示查询可以直接返回查询结果，不必先转成领域模型；没有领域模型的轻量业务不需要伪造领域类。

**检查**：自动（领域层不能依赖 ORM）；测试验证"保存后重建，行为不变"；评审核对公开合同不返回 PO。

## 合同与失败

### S-14 合同写清结果、失败、重试和兼容

**规则**：公开用例、出口、平台能力和跨上下文协作的合同写清：

| 内容 | 要求 |
|---|---|
| 目的与数据 | 输入输出含义、身份与数据归属、允许范围和限制 |
| 结果与失败 | 区分业务拒绝、无权限、无效输入、依赖故障、超时、部分完成 |
| 重试与重复 | 能否重试、如何识别同一业务操作、重复调用的结果 |
| 版本与兼容 | 字段、行为、错误、权限变化对调用方的影响 |
| 对外事件 | 发布数据、消费责任、重复和顺序语义 |

Java 合同还要写清空值、单位、集合是否可变、资源归属、阻塞与取消。"没有结果"和"执行失败"不能混用；不能用静默返回空值或 `UnsupportedOperationException` 冒充支持。

**检查**：评审。HTTP 层的具体映射见[接口与错误](06-接口与错误.md)。

### S-15 结果未知不能当成功

**规则**：技术失败映射为合同结果时，保留必要的诊断证据，但不泄露客户端细节和内部数据。未完成或结果未知的操作不能报告成功。幂等合同写清可信主体、操作类型、幂等键与请求指纹、并发抢占、保留期，以及结果未知时如何核对；"重复键"本身不等于幂等成功。缓存写清权威来源、可接受的陈旧范围和失效行为；身份权限的生效要求不能被通用缓存放宽。

**检查**：评审；测试覆盖依赖失败和结果未知。

## 组件与扩展

### S-16 组件设计回答五个问题

**规则**：新增或扩展平台能力时写清：

1. 谁用、用什么：调用方、公开合同、权限责任，并用真实消费方验证接入。
2. 默认实现怎么工作：支持范围、配置、依赖环境、失败行为。
3. 怎么扩展或替换：公开配置或最小扩展接口，用一个实际扩展实现验证，并回归默认实现。
4. 隐藏了哪些复杂性：客户端、资源配置、技术转换留在组件内；不能承诺的保证要告诉使用者。
5. 怎么升级：版本、依赖、迁移方法。

**检查**：评审。

### S-17 抽象和模式按真实变化引入

**规则**：扩展点来自已承诺的扩展路径或真实变化，不为每个方法生成工厂、策略和包装。优先组合；继承只用于真实的可替换关系或框架明确支持的扩展。相似的代码如果变化原因不同，不要合并；少量清楚的重复好过用布尔参数、字符串动作和回调拼出的通用流程。

| 模式 | 什么时候用 | 避免 |
|---|---|---|
| Strategy／Factory | 已有多个可替换算法，或创建过程要维护约束 | 只有一个实现也建接口、工厂、注册表 |
| Adapter／防腐层 | 外部技术或语义确实需要转换 | 不做转换的逐方法镜像 |
| Decorator／Template Method | 有稳定公共合同和真实可组合的行为 | 隐藏执行顺序、事务或权限的深继承 |
| Specification／事件 | 组合规则或已发生事实确有使用者 | 为模式齐全造规则语言或事件总线 |

消费方通过公开合同、配置和扩展点接入，不依赖内部实现，也不复制或修改平台源码来做普通定制。

**检查**：评审。

## 运行约束

### S-18 设计包含运行前提

**规则**：系统设计同时写清：配置来源与动态生效范围、依赖不可用时的行为与恢复、部署与数据恢复前提、性能测量条件与门槛，以及需要哪些自动检查、评审和真实场景验证。具体规则见[配置与运行](08-配置与运行.md)、[故障与可观测性](09-故障与可观测性.md)、[测试与验证](10-测试与验证.md)。

**检查**：评审。

### S-19 发现问题时修正对象，不放宽检查

**规则**：实现没遵守规范，就改实现；规范本身错了或不适用，就提出有证据的规范修改并交人决定。不通过扩大例外、删除检查或降低通过条件来消除问题。

**检查**：评审。
