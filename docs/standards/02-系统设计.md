## 职责与依赖

职责适用于每个上下文；所需类型按实际场景创建。语言与主框架以[工程技术基线](03-技术与构建.md#已确认的主技术栈)为准，具体布局见[总体架构](../architecture/01-总体架构.md#ddd-边界与代码映射)。批准的 context.bootstrap、API 分类和查询短路径由阶段 2a 适配真实检查，具体支持以同次实际检查报告为准。

| 职责 | 承担的工作 | 依赖与验证要求 |
|---|---|---|
| 入口适配 | 协议解析、输入格式处理、身份上下文取得、调用用例及结果转换 | 使用公开用例契约；验证输入输出、身份及错误映射，不直接操作持久化或客户端实现 |
| 应用用例 | 编排操作、权限及数据范围责任、事务范围、业务模型和外部能力协作 | 依赖领域模型、所需出口及允许的平台公开契约；验证用例结果与失败路径 |
| 领域模型 | 业务概念、状态、计算和不变量 | 遵守业务与技术隔离要求；验证合法非法行为，持久化按独立对象转换 |
| bootstrap 装配 | 仅启动、配置、接线与生命周期 | 可依赖本上下文所需实现及公开装配入口；其他职责不得反向依赖它，不承载业务、查询或 SQL |
| 基础设施 | 数据访问、对象转换、事务机制、技术客户端、配置及适配实现 | 实现所需协议，验证真实依赖场景；不自行决定业务成功、权限或规则 |

一般依赖为入口到应用、应用到领域及需求协议、基础设施到其实现的协议与业务类型；装配负责选择实际适配器。禁止领域反向依赖技术实现，以及应用通过隐藏转接访问内部 SDK 或持久化实现。

领域仅额外准入[三个领域标识](01-需求与领域建模.md#上下文模型与战术设计)：按固定 GAV、实际 JAR 摘要及精确公开类型核对，制品只含这三个无状态接口，依赖闭包仅 JDK。不得由此开放整个组件、`api` 包或其他 neutral 合同，更不能引入 Spring、ORM、Web、序列化注解。普通组件合同仍不进入领域。四层内按业务和真实职责适度分包，`bootstrap` 只是装配位置；目录数量和名字不替代依赖检查。

复杂规则按[领域模型适用条件](01-需求与领域建模.md#建模深度)放在所属实体、值对象或必要的领域服务中；简单维护的规则可在清晰的轻量用例中表达。应用中的编排条件与领域约束按业务含义审阅，不以是否存在条件语句机械判定违规，也不为简单用例制造空领域对象。

公开操作明确身份、操作权限、资源权限及数据范围责任，覆盖实际的 HTTP、消息、任务或内部调用路径。业务规则涉及归属或参与者时，以可信身份和业务事实判断；接口隐藏、前端限制和未验证的客户端属性不替代授权。具体执行机制由后续工程规范和能力设计落实。

身份与权限检查可以由统一机制完成，实际合同须说明各入口如何参与验证。新增入口时复验同一用例的权限与失败场景，不能因入口不同遗漏必要检查。业务规则及授权判断的准确性须有语义评审，分工遵守[任务责任](../workflow/02-任务执行.md#责任与人工决定)。

输入输出依据公开合同组织，可复用已经兼容且技术无关的类型；此分工不强制额外复制每个入口的数据结构。领域模型、持久化对象和对外合同的角色与公开范围分别核对。

技术依据：[Fowler 的领域模型讨论](https://martinfowler.com/bliki/AnemicDomainModel.html)说明业务行为与应用编排的分工；[OWASP 授权说明](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)要求按实际访问验证权限。本项目采用上述职责边界，具体执行机制仍由后续工程规范和能力设计落实。

## 上下文与部署映射

### 已确认的映射原则

- 各上下文保持清晰的模型、数据责任和协作合同；允许多个上下文在同一应用内运行。
- 根据实际的独立发布、扩缩容、故障隔离等要求决定是否拆分服务，并记录依据。
- 新增上下文不自动要求新增独立部署服务；具体系统的服务清单和部署映射仍由后续设计确定。

### 映射判断与审阅方法

限界上下文说明某套业务语言与模型的适用范围；部署单元说明哪些代码作为应用一起启动、发布和运行。应先解释业务边界，再决定部署方式。

| 判断对象 | 必要依据与产物 | 审阅方式 |
|---|---|---|
| 上下文边界 | 业务目的、主要术语及语义差异、规则与数据责任、对外协作合同 | 用业务场景检查模型内部是否一致，边界能否由业务责任解释 |
| 多个上下文共同部署 | 明确上下文到应用的映射、发布责任，以及共同部署可接受的资源和故障影响 | 检查共同部署是否满足实际要求，并保留各自模型与数据责任 |
| 拆分独立服务 | 指明驱动拆分的要求、可验证的收益，以及通信、故障、数据一致性和运维成本 | 比较共同部署与拆分方案，以场景和运行要求验证所选方案 |

服务数量、代码目录和数据源数量不能单独证明业务边界正确。共同部署时仍须遵守[数据归属与访问边界](../product/01-产品定义.md#关系持久化与多数据源边界)；同进程、同数据库或多数据源配置都不能作为绕过其他上下文私有数据责任的理由。

后续新增或合并服务时，只更新受影响的映射、理由和验证场景，无需为普通业务变化重写本规范。共同部署时的代码组织原则见[逻辑模块与依赖门禁](#逻辑模块与依赖门禁)。

技术依据：[Fowler 的限界上下文说明](https://martinfowler.com/bliki/BoundedContext.html)强调模型与语言的一致性边界；[Microsoft 的领域分析指南](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis)先分析领域与上下文，再结合需求及架构特性识别服务。项目采用的映射策略来自上述人工决定。

## 逻辑模块与依赖门禁

### 已确认的模块组织原则

- 默认在同一构建模块内，按包或对应语言的命名空间组织上下文，明确公开契约、内部实现及允许依赖。
- 自动检查禁止访问其他上下文内部实现、未声明依赖及上下文模块间依赖环。
- 需要独立版本或复用时，再分出构建模块。应用内部组织与平台对外版本化组件、服务制品的交付要求分别判断。

### 依赖检查的细化要求

语言与主框架以[工程技术基线](03-技术与构建.md#已确认的主技术栈)为准。第五层的[真实编译与模块合同绑定](../workflow/04-工程检查设计.md#真实编译与模块合同绑定)已落实限定声明及检查；总体产品结构已经批准，新增 bootstrap、API 分类及查询短路径的规则适配仍属于阶段 2a，不由工具夹具预定产品模块或认定完整架构门禁通过。

设计应记录逻辑模块与上下文的对应关系、代码范围、公开契约以及允许访问的其他模块。公开契约按业务协作目的确定；语言层面的公开可见性本身不代表允许跨模块使用。

| 可判定约束 | 检查目标 | 必须失败的反例 |
|---|---|---|
| 仅访问其他模块的公开契约 | 检查跨模块类型或符号引用的归属及公开范围 | A 模块引用 B 模块内部模型或实现，即使语言允许编译 |
| 仅使用已声明依赖 | 实际依赖与允许依赖匹配 | A 模块引用 C 模块的公开契约，但 A 未声明依赖 C |
| 上下文模块间依赖无环 | 校验实际依赖图 | A 依赖 B、B 依赖 C、C 又依赖 A |
| 检查覆盖目标代码 | 核对扫描范围与模块声明，缺失或无法分析时报告失败 | 遗漏一个目标模块，或检查未发现目标代码却报告通过 |

允许依赖声明表达业务协作，不应为消除报错加入无依据的依赖或扩大公开范围。整改应核对设计或实现是否有误，并重新执行受影响检查。

源码依赖检查的适用范围须明确。运行时组装、直接数据访问和业务语义还需要对应的集成场景与语义评审，不能由类型或符号检查结果代替。业务规则所属模型及跨上下文的数据责任仍按前述小节审阅。

技术依据：[Spring Modulith 的模块说明](https://docs.spring.io/spring-modulith/reference/fundamentals.html)区分公开接口与内部实现，并说明部分内部公开类型的引用会被编译器允许；其[结构验证说明](https://docs.spring.io/spring-modulith/reference/verification.html)提供依赖环、内部访问及允许依赖检查。资料仅用于逻辑模块与真实依赖门禁的原则，采用 Java 与 Spring Boot 不代表选择该工具。

## 入口端口与用例契约

### 已确认的入口接口原则

- 默认通过明确的公开应用方法调用用例；存在实现替换或需要独立维护的接口合同时，再抽取入口接口。
- 多个入口可以复用同一用例；不为每个用例固定增加接口与实现的成对类型。
- 接口选择保留清晰的用例边界、失败语义与测试要求。

### 入口契约与审阅方法

`port.in` 表达外界调用业务用例的协议，公开应用方法和显式入口接口都可以承载该协议；具体包名、类型与数据结构尚待确定。

| 情形 | 设计与审阅要求 |
|---|---|
| 公开应用方法足以表达用例 | 明确调用目的、输入、结果、权限责任与失败语义；核对调用方只能使用已公布的契约 |
| 需要抽取入口接口 | 说明独立合同或实现替换的实际需求、调用方及变化范围；接口只暴露该需求所需的用例能力 |
| HTTP、消息或定时任务调用同一用例 | 各入口完成协议适配，复用用例；用成功、失败和非法场景验证入口差异是否改变业务语义 |

选择公开应用方法时，调用方仍须遵守[模块公开范围与允许依赖](#逻辑模块与依赖门禁)。语言允许直接引用某个类型，不代表它已成为公开用例契约。

入口适配负责传输协议及输入输出转换。应用用例契约不得携带 HTTP 请求、响应或消息客户端等入口技术类型，跨模块不得调用未公布的应用类型。访问控制遵守[接口策略](07-安全与访问控制.md#访问策略与执行细化)，业务校验由实际用例与领域规则承担。

用例的行为测试应能通过其契约执行；各入口另行验证协议转换与错误映射。接口或公开方法本身都不证明业务语义正确，仍需检查具体场景及规则归属。因后续需求引入入口接口时，更新受影响调用方和契约测试即可，无需改变本原则。

技术依据：[Cockburn 的端口与适配器原文](https://alistair.cockburn.us/hexagonal-architecture/)把端口描述为有目的的应用交互协议；其示例入口直接调用公开应用方法，并展示多个入口驱动同一应用。项目采用的入口接口强度来自上述人工决定。

## 出口端口与平台能力复用

确认来源：2026-10-12 本会话用户选择 A，允许应用层必要装配／事务元数据，领域层保持框架无关；不允许借许可调用技术客户端。

### 已确认的出口复用原则

- 订单仓储、库存预留等具有业务语义的能力使用本上下文需要的出口协议；这些名称仅为说明原则的示例，不预定业务系统划分。
- 应用层可以直接使用平台公开、技术无关的通用能力契约，例如通用短信发送与文件存储；不一律增加本地接口和转接实现。
- SDK、持久化框架及客户端实现留在基础设施中。
- 平台公开契约升级时，消费方须验证兼容性及自身适用场景。

### 出口选择与依赖检查

`port.out` 表达业务所需的外部能力；技术适配器负责连接实际实现。出口协议应围绕调用目的、结果与失败语义设计，具体归属、包名及类型组织仍须后续统一。

| 调用情形 | 设计与审阅要求 |
|---|---|
| 本上下文具有特定业务语义 | 定义能表达该需求的出口协议，由适配器连接数据访问、其他上下文的公开合同或平台能力；核对业务结果与失败语义 |
| 通用能力契约已满足应用编排需要 | 核对其公开范围、技术无关的数据合同、允许依赖及版本；可直接复用，验证成功与依赖失败场景 |
| 平台合同不足以表达本上下文语义，或存在实际替换需要 | 增加必要的本地出口与适配，说明它隐藏的差异及调用方，验证转换与失败映射 |
| 能力仅暴露具体客户端或框架 API | 在基础设施中适配为符合前述要求的协议，再提供给用例调用 |

出口和可复用能力契约的参数、结果及错误类型均须符合技术隔离要求；检查应覆盖这些类型引用的数据结构，防止客户端响应、持久化框架对象或查询构造器经包装后进入应用合同。

领域模型表达业务规则，其代码应能脱离 HTTP、依赖注入容器、数据库与外部 SDK 验证模型行为。应用层编排对业务出口及平台公开能力的调用；技术连接、数据源选择及具体框架／客户端操作由基础设施承担。该分工仍须与[数据源职责](../product/01-产品定义.md#关系持久化与多数据源边界)及[按业务复杂度建模](01-需求与领域建模.md#建模深度)共同审阅；简单用例同样遵守技术依赖边界。

### 已确认的应用层框架边界

应用层允许必要的 Spring `@Service`、`@Transactional` 等装配与事务注解；领域层仍保持框架无关。不为移除这些注解而强制增加一层事务包装接口，也不要求所有用例都采用这些注解。

该许可只针对必要的装配及事务元数据，不授权应用代码直接使用 Mapper、PO、DataSource 或客户端 SDK。具体技术实现留在基础设施，业务出口及公开通用合同继续遵守前述隔离要求。组合注解不能使领域模型间接绑定框架生命周期；降低类型或成员可见性不能免除职责边界。

注解存在不等于事务有效。后续真实实现须按[事务与多数据源要求](05-持久化.md#事务与多数据源)验证事务设施、调用路径、成功及失败回滚等适用场景；不由注解推定自调用生效或独立数据源具有原子提交保证。工具对具体版本和 API 的适配范围记在机制设计，不将工具暂未校准的合法用法误写成编码禁令。

| 可判定约束 | 必须失败的反例 |
|---|---|
| 领域模型保持业务依赖边界 | 领域模型引用 Web、持久化或客户端框架类型，或通过技术注解绑定其生命周期 |
| 应用层依赖公布的协议 | 应用代码直接调用平台内部客户端、持久化框架或另一上下文内部实现 |
| 应用层可使用必要的装配／事务元数据 | 借注解许可直接创建、调用客户端或使用技术类型作为业务合同；同一框架类型兼作普通代码引用也不能按注解放行 |
| 出口合同不暴露外部技术 | 接口表面采用本地类型，但其字段或方法继续暴露 SDK 响应、ORM 类型或技术查询对象 |

具体禁止依赖和扫描方式由后续技术选型及门禁实现确定。自动检查负责可识别的代码依赖；是否正确表达业务需求、失败转换是否准确以及版本升级是否兼容，仍需契约场景与语义评审。接口数量不作为隔离质量的证明。

技术依据：[Cockburn 的端口与适配器原文](https://alistair.cockburn.us/hexagonal-architecture/)强调应用与外部技术分离、交互协议表达调用目的。平台通用契约的复用策略来自上述人工决定，后续真实契约及适配实现须分别验证。

## 展示查询与领域写入

采用轻量 CQRS，默认同库、同步调用。纯查询可用 Controller → 应用查询合同的基础设施读取实现 → SQL／ReadDTO；不强加只转发的 Handler／Service 或聚合重建。Controller 不直引 Mapper，读取实现不写业务状态；可信授权范围、分页和字段可见性仍须验证。资源授权、跨源编排或业务判断需要有职责的查询用例。完整路径及事件／事务／防腐细节见[总体架构](../architecture/01-总体架构.md#ddd-边界与代码映射)，阶段 2a 先验证规则适配。

### 已确认的查询路径原则

- 应用可以通过本上下文的查询契约取得展示数据，由基础设施实现具体查询；不要求展示型查询一律加载领域模型。
- 修改数据和业务决策仍遵守对应领域规则。
- 查询须遵守权限、数据范围和上下文访问边界；查询与写入可以共用同一数据库。

### 查询设计与审阅方法

该原则允许按实际需要设置查询投影，不要求简单业务额外建立两套模型、两套处理框架或独立读库。

| 情形 | 设计与验证要求 |
|---|---|
| 仅展示既有业务数据 | 按需要定义查询输入和展示结果，记录字段含义、过滤、排序、分页及错误语义；验证真实数据与契约一致 |
| 查询结果包含业务判断或用于后续业务操作 | 明确判断所属规则，避免在查询中复制领域规则；实际执行业务操作时仍按其合同验证当前条件 |
| 读取本上下文数据 | 可在基础设施中查询和组合本上下文拥有的数据，返回技术无关的展示结果 |
| 需要其他上下文数据 | 使用其公开查询合同；若建立本上下文的展示投影，数据来源须为对方公开的集成合同，并明确授权、归属及更新责任；共同部署或同库不改变私有数据边界 |

查询契约与结果遵守[入口契约](#入口端口与用例契约)、[出口选择](#出口端口与平台能力复用)及[模块依赖边界](#逻辑模块与依赖门禁)。HTTP 入口和应用代码均不能借查询路径直接操作持久化框架或跨上下文私有表。

展示型读取不得通过该查询路径改变业务状态；审计与观测记录属于各自明确的技术或安全副作用，验证时须区分这些记录与业务状态。需核对查询涉及的数据和操作，防止用查询命名隐藏业务修改。

每项查询明确权限及数据范围的执行责任，以授权、拒绝、范围外数据及相关依赖失败场景验证。展示结果的可见延迟、并发读取与一致性要求按实际场景确定；分离查询路径本身不产生强一致或即时刷新保证。

查询实现、数据合同及字段变化同步更新受影响测试。自动检查可识别技术依赖及显式的违规引用；动态查询、运行时副作用、数据归属和规则准确性还需真实场景及语义评审。

技术依据：[Microsoft 的查询设计说明](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/cqrs-microservice-reads)说明展示查询可返回区别于领域模型的数据；[CQRS 模式说明](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)区分共享数据存储与分离数据存储。本项目采用查询路径的上述人工选择，具体查询仍按本项目职责与依赖边界组织，未选定示例技术栈或更复杂的读写架构。

## 本地事务与跨上下文一致性

### 已确认的本地事务原则

- 业务要求一起成功或回滚，且调用链实际共享一个本地事务资源时，可以共同提交或回滚。
- 跨上下文操作通过各上下文的公开合同协作，事务参与不改变模型与私有数据责任。
- 拆服务或拆事务资源时，重新设计并验证一致性要求。

### 事务设计与验证方法

先记录业务必须维持的约束、哪些状态须原子生效、允许的暂时不一致和失败结果，再选择事务及协作方式。

每项跨上下文操作说明协调责任、参与者、公开合同、实际事务资源、加入或独立提交方式，以及哪些外部副作用不在该事务内。相同进程、相同数据库地址或声明事务注解本身都不能证明参与了同一事务。

| 条件 | 设计与验证要求 |
|---|---|
| 原子业务操作实际共享一个本地事务 | 限定参与及锁定范围；使用真实数据环境验证整体提交、后续步骤失败时回滚以及适用的并发冲突场景 |
| 参与方使用不同事务资源或独立服务 | 明确各步提交结果及一致性合同，比较边界调整与流程协调方案，按业务要求处理部分成功 |
| 包含短信、文件、远程调用或消息发送 | 分别说明不可由数据库回滚的副作用、执行时机与恢复责任；真实验证故障结果 |
| 部署、数据源或事务参与方式变化 | 重新检查原来的原子性假设，更新受影响设计、协作合同及失败验证 |

共享事务需求还须审阅业务所有权与上下文边界理由。不能为取得原子提交直接操作另一上下文私有表，也不能把全部业务规则集中到协调用例中。公开合同、[模块依赖](#逻辑模块与依赖门禁)与[技术依赖](#出口端口与平台能力复用)约束持续适用。

独立事务的流程须明确暂时状态、可见延迟、重试与重复调用、必要的补偿或人工处置，以及业务何时算成功。同步调用或消息接收确认都须按实际合同解释，不能自动代替参与方的业务完成结果。具体协调模式由真实需求决定。

与消息相关的设计须满足已确认的[业务保存与消息发送恢复要求](../product/01-产品定义.md#异步消息功能边界)，并遵守[多数据源事务边界](../product/01-产品定义.md#关系持久化与多数据源边界)。本地事务参与规则不扩展为跨数据源、跨服务或外部系统的原子保证。

验证应核对真实持久化结果及外部效果，不能只以调用次数或事务注解作为证据。自动依赖检查负责可判定的越界引用；实际事务参与、提交回滚和故障恢复需场景验证。缺少必需的数据或依赖环境时保留未验证状态。

技术依据：[Spring Modulith 的事件说明](https://docs.spring.io/spring-modulith/reference/events.html)展示同步模块协作的事务语义及扩大边界的成本；[Microsoft 的 Saga 说明](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)说明独立本地事务协作的补偿及隔离限制。项目采用上述人工决定，未选定事件框架、Saga 或分布式事务实现。

## 领域与持久化对象分离

### 已确认的对象分离原则

- 领域对象表达业务，持久化对象表达存储结构；统一分别定义，由基础设施完成转换。
- 即使两者字段接近，也保留独立的持久化对象及转换关系。
- 领域模型保持技术独立，验证保存、重建及模型行为。

### 映射设计与验证要求

典型读取关系为：数据库数据到持久化对象，经基础设施转换为领域模型；保存时进行反向转换。框架注解、数据库操作和技术字段归持久化实现，领域模型不承担存储操作。

持久化对象按实际存储需要组织，领域对象按业务含义组织；不要求每个领域类型与数据库表一一对应，也不为每个枚举或值对象机械生成一套中间类型。转换说明哪些状态被保存、如何重建，以及哪些值由规则计算或不持久化。

| 验证对象 | 必要验证或失败反例 |
|---|---|
| 类型与依赖分离 | 同一类型同时充当领域和持久化对象、领域继承持久化对象或依赖 ORM 类型，应被对应检查拒绝 |
| 公开合同 | 应用协议、平台公开能力及跨上下文输入输出不能直接返回持久化对象；检查其引用的数据结构 |
| 保存与重建 | 用真实存储验证所需业务状态往返、边界值及适用的空值、身份和版本语义，发现转换遗漏须整改 |
| 模型行为 | 重建后仍可执行业务行为并维护约束；不因映射方便绕开规则或依赖持久化会话才能工作 |
| 数据与规则变化 | 变更同步核对转换、数据迁移和兼容场景，不能用无依据默认值掩盖不兼容旧数据 |

[展示型查询](#展示查询与领域写入)仍可直接返回查询合同的数据，不要求先转换为领域模型。没有采用领域模型的轻量业务也无需额外伪造领域类，其技术依赖与公开数据合同仍须满足既有边界。

自动检查负责可识别的角色混用、技术依赖和类型泄漏；字段语义、重建准确性及行为完整性需要映射测试和语义评审。具体转换工具及版本组合由后续技术选型确定。

当前持久化框架的确认范围及工程细化状态见[关系持久化规范](05-持久化.md#已确认的持久化框架)，本节保留对象分离的唯一原则正文。

技术依据：[Fowler 的 Data Mapper 说明](https://martinfowler.com/eaaCatalog/dataMapper.html)强调业务对象与数据库、映射技术的独立。本项目进一步采用始终分离持久化对象的人工选择，并不把该选择表述为所有项目的通用要求。

## 合同与失败语义

适用于公开用例、业务出口、平台能力及跨上下文协作。

| 合同内容 | 设计与审阅要求 |
|---|---|
| 目的与数据 | 调用目的、输入输出含义、身份与数据归属、允许范围及必要限制清晰，引用所属模型或能力 |
| 结果与失败 | 区分业务拒绝、无权限、无效输入、依赖故障、超时及部分完成；明确调用方如何观察结果 |
| 重试与重复 | 明确可否重试、如何判断同一业务操作、重复结果和必要的恢复责任；不能用统一重试隐藏副作用 |
| 版本与兼容 | 说明字段、行为、错误及权限变化对消费者的影响，验证兼容性和必要迁移 |
| 对外事件 | 区分内部领域事实与集成合同，明确发布数据、消费责任、重复及顺序语义和恢复场景 |

Java 合同同时明确空值、单位、集合可变性、资源所有权、阻塞与取消责任；“没有结果”和“执行失败”不得混用。可替换实现遵守同一前置条件、结果与失败合同，不以静默空结果或 `UnsupportedOperationException` 伪装支持。兼容评审区分源码、二进制、协议、行为、配置及数据；需要滚动升级时才设计扩展、迁移、收缩次序，并验证实际新旧组合。

有副作用的幂等合同明确可信主体、操作类型、键与请求指纹、并发抢占、保留期及结果未知时的核对路径；“重复键”本身不等于幂等成功。缓存须声明权威来源、容许陈旧范围、失效和故障行为；身份权限的已确认生效要求不能被通用缓存策略放宽。

技术失败映射为合同结果时保留必要的可观测证据，避免泄露具体客户端和内部数据。不能把未完成或结果未知的操作当作成功，也不能在转换中丢失调用方需处理的失败信息。

同一业务合同只有一个有效定义，入口、适配器及使用说明引用它。HTTP 状态、错误编号、序列化格式和具体事件编码在工程规范及后续能力设计中统一，不能在任务中自行形成平行规则。

当前 HTTP 状态原则及接口工程细化的确认范围见[HTTP 接口与结果规范](06-接口与错误.md#适用范围与阅读入口)；本节保留合同与失败语义的唯一原则正文。

## 组件与扩展设计

适用于平台新增组件、服务能力和消费项目的能力接入。

设计先核对[通用能力交付承诺](../product/01-产品定义.md#通用能力交付承诺)及[实现支持范围](../product/01-产品定义.md#实现支持与扩展范围)，再按真实调用需要形成能力边界。平台承担基础接入与技术差异，消费项目承担自己的业务规则和使用责任。

| 设计问题 | 必要产物与验证 |
|---|---|
| 谁使用、使用什么 | 已确认场景、调用方、公开合同和权限责任；用消费项目验证真实接入 |
| 默认实现如何工作 | 声明支持范围、配置、必要环境及失败行为；验证真实成功与故障场景 |
| 如何扩展或替换 | 公开配置或最小扩展协议、实现选择和兼容责任；以实际扩展实现验证，并回归默认实现 |
| 哪些复杂性被隐藏 | 将客户端、资源配置与技术转换放在能力内部；业务语义及不可承诺的保证对使用者明确 |
| 如何交付与升级 | 固定制品版本、依赖及接入前提，说明升级影响与迁移方法；保持项目独立选择和发布能力 |

扩展点来自已承诺的扩展路径或真实变化，不为每个方法统一生成工厂、策略和包装。接口大小按调用需要控制；可直接复用的通用合同遵守[出口复用原则](#出口端口与平台能力复用)。

SOLID 以实际变化检验：职责按变化原因聚合，接口按消费者需要裁剪，依赖方向保护业务，实现替换保持合同。优先组合；继承仅用于真实可替换关系或框架明确支持的基础设施扩展。复用相同知识及变化原因，不能仅因代码形状相似就合并不同业务；少量清楚的重复优于由布尔值、字符串动作和回调拼成的通用流程。

| 模式 | 采用时机 | 应避免的额外成本 |
|---|---|---|
| Strategy／Factory | 已存在可替换算法，或创建须维护真实约束 | 单一实现也逐层生成接口、工厂和注册表 |
| Adapter／防腐接口 | 外部技术或业务语义确实需要转换 | 无转换的逐方法镜像；把外部模型传入领域 |
| Decorator／Template Method | 有稳定公共合同与真实可组合行为／固定算法骨架 | 隐藏执行顺序、事务或权限责任的深继承 |
| Specification／事件 | 业务组合规则或已发生事实确有使用者 | 为模式齐全制造规则语言、事件总线或异步一致性 |

模式是否减少理解与修改成本由代表路径评审；不以模式数量、接口数量或条件分支数量评分。

消费方通过公开合同、配置和扩展点接入，不能依赖内部实现、修改平台源码或复制实现来完成普通定制。扩展声明说明其支持的合同，选择错误、配置无效及不可用依赖的处理必须明确并验证，不能静默改变业务语义。

已明确的本地与 S3 文件实现、短信、消息恢复及其他能力范围仍以产品定义为准；扩展设计不能将未实际验证的实现写为已支持。验证方式及使用说明随真实制品交付。

## 运行约束与设计审阅

具体系统设计须同时考虑使用场景及声明的运行前提。

| 约束 | 必要产物与验证要求 |
|---|---|
| 配置及依赖 | 配置来源、优先级、启动检查、动态生效范围与更新失败行为，观察应用实际效果 |
| 故障与观测 | 依赖不可用时的合同、恢复和必要日志、指标或链路证据，验证与业务结果一致 |
| 部署与数据恢复 | 按已确认参考环境声明持久化、备份恢复、升级与回退前提，以真实环境验证 |
| 性能 | 先明确资源、数据、场景、负载和门槛，再测量；平台基线与消费项目目标分别验收 |
| 设计到检查 | 列出适用规范、可判定约束及其失败反例、语义评审与必要真实场景，标明缺失环境 |

具体服务、组件、版本、接口、数据库结构、工程目录、权限生效语义及测试数值属于后续技术选型或能力设计。后续选择必须依据本层方法、产品边界及相应工程规范形成可审阅结果；改变范围或责任时重新提交人工决定。

设计问题按类型定位：实现未遵循正确规范时整改实现；规范错误或不适用时提出有证据的规范变更，核对影响并重新确认。不能通过扩大例外、删除检查或降低通过条件消除已发现的问题。
