## 已确认的配置与启动原则

- 能力通过明确、可复用的约定组织默认装配、合理默认值和一致的使用方式；消费项目只为必要输入与实际差异提供配置。具体默认值及接入约定依照已确认范围形成，不让消费者重复填写内部装配细节。
- 约定保留公开的配置覆盖及扩展路径，用于实际定制，不要求消费方复制平台实现或修改内部源码；扩展仍遵守已确认的[组件与扩展设计](02-系统设计.md#组件与扩展设计)。
- 启动时发现已启用能力的必需配置缺失或非法，经能力合同明确允许，可以启动并只提供不受影响的功能；对应能力保持不可用，其调用按失败合同拒绝，不能返回演示结果或假成功。
- 局部启动必须真实证明影响隔离、健康与流量状态准确、错误可观察及恢复有效。不能把进程存在当作所有能力可用，也不能仅记录警告却继续报告完整就绪。
- 按合同未启用的可选能力不要求配置。不能因配置错误静默改用另一实现，也不能以局部启动绕过[身份与授权](07-安全与访问控制.md#访问策略与执行细化)、[数据结构与迁移](05-持久化.md#数据结构与迁移)及业务失败责任。
- 启动策略只覆盖启动时可判定的配置缺失或非法，不代替依赖故障、更新执行与恢复合同，不改变能力交付范围。Nacos 发布内容适用[配置权威前提](#已确认的配置权威前提)，其内容错误不纳入通用启动错误治理。

## 已确认的配置权威前提

- Nacos 管理的配置以其发布内容为权威，内容正确性作为发布与使用前提；约定默认值适用于未被明确覆盖的项，不自行用本地内容纠正或替代权威发布值。
- 本轮脚手架不为 Nacos 发布内容错误另建通用正确性审核、拒收、保留旧值或停用机制，也不将该情形列为强制验收场景。采用所选框架的标准接入，不围绕该假设额外设计配置治理产品。
- 内容正确性前提不等同于配置已成功取得或已在应用中生效。必要启动引导、配置未取得、连接中断及应用执行失败仍按真实接入前提、标准机制与能力合同处理；不能把实际失败报告为成功，也不由本项承诺客户端不存在故障。
- 本项是本轮人工选择的范围与使用前提，不是框架已证明所有配置内容正确或已有运行验证的结论。既有[身份授权](07-安全与访问控制.md#已确认的业务接口访问策略)、[变更生效](07-安全与访问控制.md#已确认的账号与权限变更生效原则)及业务失败合同保持有效。

应用配置统一 application.yml，工具原生 properties 不改。后端默认 HTTP；TLS、证书与 HTTPS 重定向归 Nginx 等部署基础设施，可通过部署覆盖文件启停。真实生产边界需验证，后端仍独立鉴权。组件固定 YAML 低优先级装载，服务覆盖差异，cache 唯一维护 Redis 地址／凭据／池配置，access-control 仅维护 sa-token 会话策略。

## 默认约定与必要输入

| 信息类别 | 约定与配置责任 |
|---|---|
| 可复用的技术约定 | 提供符合已确认技术范围的默认装配、默认实现及合理参数；说明适用前提、覆盖方式与版本兼容，不要求重复声明相同内容 |
| 无法从已声明环境安全推导的输入 | 连接目标、隔离信息、访问凭证及资源位置等按实际需要提供；不猜测生产目标、填入通用密码或把缺失凭证解释为允许匿名访问 |
| 业务及安全策略 | 由业务合同和责任方确定；不能仅为减少配置而推断数据归属、授权范围或业务成功条件 |

能力接入说明给出最小必要输入、默认装配、有效覆盖与扩展方式、依赖前提及不可用行为。只暴露有真实消费需要的配置，不机械搬出底层 SDK 的全部参数；默认值以相应实现及配置声明为维护来源，说明引用同一来源，不另建漂移的默认值清单。

自动装配条件、用户覆盖及多实现选择须有确定结果。合法覆盖应只替换所需部分；冲突或不支持的选择不能依赖偶然加载顺序解决。具体条件声明与构建组织由后续设计选择，不强制所有能力采用同一种接口、工厂或包装模式。

Spring Boot 服务以构造器注入和原生自动配置为默认，显式配置只承担必须的资源、框架扩展及安全装配，不为每个用例复制 `@Bean` 接线。自有成组参数用类型明确的 `@ConfigurationProperties` 及适用校验；密钥不设演示默认值。先复用框架已有能力，扩展点和本项目增加的行为才是平台维护责任。Spring 代理、生命周期和线程上下文的真实作用范围须通过实际装配验证，不能以容器启动成功代替行为验证。

例如，未覆盖文件实现选择时按已确认的[文件默认实现](../product/01-产品定义.md#实现支持与扩展范围)接入；明确选择 S3 后，必要输入缺失按相应失败合同处理，不能悄悄切回本地存储或改变数据位置。示例不决定具体配置键、路径或桶名。

## 能力隔离与运行状态

区分按合同未启用、已启用且可用、已启用但不可用，明确依赖该能力的功能受影响范围。依赖不可用能力的操作不能被算作不受影响；不存在有效授权、迁移或数据访问前提时，不能继续提供相应受保护操作。

健康、可接收流量及能力可用状态依照实际服务合同汇总，不机械把任一可选能力错误等同于整个进程失效，也不能因其他功能正常就把不可用能力隐藏。具体健康端点、错误标识与流量策略仍待设计，不因本项采用 Actuator 或 Kubernetes。

启动引导与必要输入缺失等适用接入问题在启动阶段显式识别，不能等到首次调用才发现；Nacos 发布内容按[配置权威前提](#已确认的配置权威前提)处理。恢复方式及前提由能力合同声明并验证，不能承诺所有配置均可无重启恢复；诊断信息保留必要原因而不输出密钥或完整敏感配置。

## 配置读取与动态更新

支持范围仍以[运行配置与 Nacos](../product/01-产品定义.md#运行配置与-nacos)为准。

按照[配置权威前提](#已确认的配置权威前提)明确 Nacos 管理范围、启动引导及其他必要输入来源、项目与环境隔离和可动态更新范围，观察实际有效值及应用行为；能通过既有来源获取的必要输入不要求消费方重复填写。收到通知、配置发布成功或回调被执行，不等于应用已实际生效。

按内容正确的发布前提验证正常读取、支持项变更的真实生效、连接中断、应用更新执行失败及恢复。不另设内容正确性判定与本地择优流程；具体客户端标准机制、实际支持的故障与恢复合同、更新实现及一致性前提在后续能力设计中明确，不在统一规范中预造热更新状态机。

## 检查与失败反例

| 约束 | 正例与必须识别的反例 |
|---|---|
| 默认接入可用 | 只提供必要输入即按约定接入；缺少消费者不应重复声明的内部参数就无法工作须整改，不能用全量样板配置掩盖缺陷 |
| 合法覆盖及扩展 | 用公开配置或扩展替换所需部分并回归默认行为；覆盖不生效、重复装配或偶然选择错误实现必须识别 |
| 可选能力未启用 | 不需要其必要配置，其他功能按合同工作；未启用仍要求其凭证或阻塞不相关功能须识别 |
| 局部启动与失败隔离 | 启动必要输入缺失等合同内接入问题对应能力不可用，不受影响功能真实工作；伪造成功、调用遗漏检查或影响未隔离必须失败，不扩展为 Nacos 发布内容错误治理 |
| 健康与实际状态一致 | 真实故障及恢复与对外状态一致；进程启动却报告不可用能力完全就绪必须识别 |
| 配置与实现选择不漂移 | 明确选择的实现及目标保持合同语义；配置错误后静默切换实现或数据位置必须失败 |
| 配置权威及实际生效 | 按正确发布前提验证真实读取及应用行为；自行用本地值覆盖 Nacos 权威配置、只收到通知就报告生效或跨项目读取配置不能作为通过 |

可判定的值、条件与覆盖结果使用自动检查和隔离反例；默认值是否合理、故障影响及状态汇总是否符合业务须有场景证据的语义评审，分工遵守[任务责任](../workflow/02-任务执行.md#责任与人工决定)。真实依赖按任务场景要求提供，替身仅服务隔离测试；缺少必需环境保留未验证。第五层建立机制，能力实现及真实运行在后续设计研发阶段验证。
