# HTTP 接口与结果规范

规范来源与固定输入见[第三层确认记录](../product/rebuild.md#第三层确认记录)；实际实现、验证及未完成项见[当前任务](../tasks/control-plane-verification.md#唯一任务记录)。

## 适用范围与阅读入口

适用于平台和受统一规范约束的消费项目的业务 HTTP 接口。按任务触发读取：

- 设计或修改 HTTP 业务结果与拒绝表达：[已确认的 HTTP 失败状态原则](#已确认的-http-失败状态原则)。
- 新增或修改普通业务 JSON 响应：[已确认的 JSON 响应外壳](#已确认的-json-响应外壳)。
- 定义接口声明、生成或发布机器可读合同：[已确认的接口合同来源](#已确认的接口合同来源)及[合同生成与验证](#合同生成与验证)。
- 接入客户端、网关或接口观测：[消费处理与观测](#消费处理与观测)。
- 实现 HTTP 入口、失败转换或接口测试：[分类映射与验证](#分类映射与验证)。
- 新增或修改业务 HTTP 入口的访问策略：[安全与访问控制规范](security-and-access.md#适用范围与阅读入口)。

业务合同、完成语义、重试和兼容责任遵守[合同与失败语义](system-design.md#合同与失败语义)，本规范只细化 HTTP 表达，不另定领域规则、服务边界或调用重试保证。框架运维端点、二进制下载及流式接口的响应合同须分别明确，不能把普通业务 JSON 外壳自动套用于这些协议。

## 已确认的 HTTP 失败状态原则

- 应用处理后明确拒绝的业务命令返回 HTTP 200，并提供稳定的业务错误标识及必要说明；响应合同必须使消费者能够识别业务拒绝，不能把未完成的命令描述为已完成。
- 协议错误、身份认证与权限失败、服务故障仍按对应 HTTP 语义处理。本项不是“所有异常都返回 200”，也不允许把依赖故障或未知结果改写为普通业务拒绝。
- 消费者同时处理 HTTP 层失败和响应体中的业务结果，不能仅凭 HTTP 200 判断业务成功或完成。
- 接口观测显式识别业务拒绝；仅按 HTTP 状态统计的 2xx 数量不能作为业务命令成功数量。
- 正常合同结果不因业务含义是否正面就一律视为错误，例如查询完成但没有匹配数据。命令成功、业务拒绝、正常查询结果及尚未完成的处理须按各自合同区分。
- HTTP 状态选择不决定响应体字段、错误标识编码或实现框架；具体合同在能力设计中明确。

资料依据：[RFC 9110 的 200 定义](https://httpwg.org/specs/rfc9110.html#status.200)表示请求成功，[4xx](https://httpwg.org/specs/rfc9110.html#status.4xx)及[5xx](https://httpwg.org/specs/rfc9110.html#status.5xx)定义 HTTP 错误类别。本项目选择由响应体进一步区分应用业务命令的成功与拒绝，这是本轮人工决定，不将其描述为 RFC 对所有业务拒绝的规定。客户端及观测的配套处理仍需真实验证。

## 已确认的 JSON 响应外壳

- 普通业务 JSON 的成功、业务拒绝与失败响应只包含 `code`、`message`、`data` 三个字段。`code` 为稳定字符串，`message` 为面向用户的说明文本，`data` 承载业务数据；无数据时显式返回 `null`，不增加重复的 `success` 布尔字段。
- `SUCCESS` 表示成功，`ACCEPTED` 表示仅受理、不保证完成；其他标识按所属业务拒绝或 HTTP 失败合同解释。消费者不得通过说明文本或 HTTP 200 代替结果标识判断。
- 外壳不改变[HTTP 失败状态原则](#已确认的-http-失败状态原则)：业务命令拒绝仍为 HTTP 200 与业务错误标识，协议、身份权限及服务故障仍使用相应 HTTP 状态。
- 二进制下载、流式响应及框架运维端点不强套普通业务 JSON 外壳，按各自明确的协议与合同处理。
- 统一外壳只统一结果表达，不代替业务完成、权限或重试合同，不为每个上下文建立一套不同的通用返回约定。
- 各能力的业务标识、分页数据结构及入口映射在所属合同中明确，不另造通用外壳。上述约定不表示已有可消费接口或检查结果。

## 已确认的接口合同来源

- 先明确场景、接口行为和验收，再通过入口、请求与响应类型及必要描述元数据定义接口，生成版本化 OpenAPI。不得先随意编码，再把当前实现当作已经确认的需求或合同。
- 有效代码声明与描述是当前接口的唯一维护来源。字段或类型变化在该来源修改，不能同时手工维护另一份 OpenAPI 定义，或手改生成物使文档暂时匹配。
- 补充类型无法充分表达的业务拒绝、身份权限及必要行为语义；生成合同不能仅凭 HTTP 200 或返回类型推断业务成功与授权保证。
- 发布合同可追溯到相应版本及输入，并核对消费者兼容性与真实 HTTP 行为。生成成功不等于验证通过，重新生成也不等于合同变更已经获准或验收。
- 已发布版本的不可变合同产物用于消费与兼容对照，不成为当前另一份可人工修改的定义来源；不能覆盖既有发布产物或重置对照基线来隐藏漂移。
- Boot 4.0 配套线采用 springdoc 3.0.x 从有效声明生成 OpenAPI 3.0.1，并复用成熟请求响应验证及兼容工具；第五层[固定适配与支持边界](../design/engineering-gates.md#真实-http-合同校准)不得外推为完整产品组合验证，也不产生源码检查例外。其他代际或协议在使用前补适用校准，不直接采用资料页面最新版。

资料依据：[OpenAPI 规范](https://spec.openapis.org/oas/v3.2.0.html)提供语言无关的 HTTP 接口描述及相应工具使用场景；[springdoc 官方说明](https://springdoc.org/)介绍从 Spring Boot 配置、类型与注解生成描述，并可补充描述信息。上述说明支持该工程方向，不证明所选项目基线兼容或接口行为正确，也不将引用规范的版本视为项目固定版本。

## 合同生成与验证

生成入口固定工具、版本、配置及扫描范围，引用[技术与构建基线](technology-and-build.md#版本与兼容)。合同产物绑定输入与发布版本；描述输出、使用文档及消费方引用同一合同，生成文件不由人工二次修补。具体保存与发布方式在后续工程设计中确定。

核对全部适用接口的请求、响应、稳定结果标识及已知拒绝与失败，避免只生成成功类型却遗漏消费者必须处理的情况。自动检查负责可判定的覆盖、结构、生成一致性及已声明兼容约束；业务含义、权限责任及完成语义仍需场景与语义评审，不宣称从类型或注解能够推断全部语义。

以有效来源重新生成并核对产物，用真实 HTTP 场景验证实际响应和声明一致；已有发布合同作为兼容对照。当前生成物与当前实现同时改变后相互匹配，不能自行证明符合原合同。具体兼容处置继续遵守[合同与失败语义](system-design.md#合同与失败语义)，不得通过替换测试预期、关闭检查或覆盖发布基线使不一致消失。

## 消费处理与观测

接口合同在统一最小外壳中明确业务成功、拒绝、仅受理及结果未知的识别方式。稳定标识供程序判断，说明文本供用户理解，不能要求消费者以中文消息是否匹配判断业务结果。具体业务标识及恢复信息由所属合同确定。

外壳属于 HTTP 入口的结果表达，不要求领域模型、公开用例或非 HTTP 平台能力普遍改为返回通用 HTTP 结果对象。职责继续遵守[职责与依赖](system-design.md#职责与依赖)，具体入口映射按真实合同设计，不由本项强制引入统一父类、继承体系或特定包装机制。

客户端的统一处理位置须保留 HTTP 层与业务层的差异，使业务调用能够观察所需结果。不能用空数据或默认成功对象掩盖无法解析的响应；没有收到有效响应时，也不能仅凭本地超时断言远端业务未发生。可否重试继续由所属合同决定，不为所有拒绝或 HTTP 故障统一重试。

观测按合同区分请求处理、业务完成、业务拒绝与服务故障。业务拒绝不自动等于系统故障或告警；具体指标和告警由相应运行规范与能力设计确定。若网关或其他组件只统计 HTTP 状态，须说明其观测边界，并提供能够识别业务结果的配套证据。

## 分类映射与验证

能力设计须明确统一外壳的确切字段、状态映射及框架接入，再用实际接口与独立期望验证；不能只验证配置或注解存在。

入口与失败转换须引用同一有效响应合同。分类依据实际语义，不以异常名称、捕获位置或是否进入控制器推断结果；区分协议解析错误、业务规则拒绝、身份权限失败和服务故障。对外保留调用方所需信息，同时避免泄露内部实现或敏感数据。

| 场景 | 验证要求及必须识别的反例 |
|---|---|
| 合同来源与生成覆盖 | 手工改写生成物、重复维护另一份定义或遗漏适用接口的情况必须识别，不能将未生成目标当作通过 |
| 合同变更与兼容对照 | 保留相应变更与兼容证据；覆盖既有发布合同或仅重置测试预期，不能作为消除漂移的证明 |
| 普通业务 JSON 的统一外壳 | 按已确定的响应合同核对成功、拒绝与失败；各入口自行使用不兼容外壳必须失败，不能以重新生成合同掩盖漂移 |
| 业务命令成功或正常查询完成 | 返回所属合同的正常结果；不能将所有否定数据误判为请求失败 |
| 业务命令明确被拒绝 | HTTP 200 与稳定业务错误标识一致，消费方识别拒绝；只有状态为 200 就报告业务成功必须失败 |
| 协议错误、身份权限失败或服务故障 | 按相应 HTTP 合同处理；兜底转换为 200 与普通业务拒绝必须失败 |
| 仅受理、部分完成、超时或无有效响应 | 不误报全部完成，不丢失合同要求的状态与恢复信息；不能由 HTTP 状态自行推导安全重试 |
| 入口与消费方合同不一致 | 接口文档、实际响应及消费识别的漂移必须被对应契约测试识别 |
| 观测结果与业务结果不一致 | 真实拒绝场景仍全部计入业务成功的情况须整改，不能仅凭 HTTP 2xx 比例验收 |
| 非普通业务 JSON 协议 | 下载、流式及框架运维端点按各自合同验证；通用包装破坏所声明协议的情况须识别并整改 |

可判定的状态、结构、标识及已声明分类通过契约和 HTTP 场景验证，并为对应检查保留有效正例与隔离反例。领域规则是否正确、分类是否符合真实业务语义及说明是否准确仍需源码、场景和语义评审；分工遵守[任务责任](../workflow/task-execution.md#责任与人工决定)。真实依赖或运行环境是否必需按具体场景声明，缺失时保留未验证，不用测试替身冒充完整集成证据。
