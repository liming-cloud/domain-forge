## 已确认的主技术栈

确认来源：2026-10-12 本会话用户选择 A。

- 首版平台实现与官方起步模板统一采用 Java、Spring Boot 和 Maven。
- 产品框架采用 Spring Boot 4.0、Spring Cloud 2025.1 与 Spring Cloud Alibaba 2025.1 配套线；MyBatis-Plus、Sa-Token 使用对应 Boot 4 适配。确切版本按下方兼容规则锁定并验证，不将代际选择当作组合通过。来源见[框架代际决定](03-技术与构建.md#已确认的主技术栈)。
- 各组件选型以相应唯一规范为准；具体发行版与版本组合按[版本与兼容](#版本与兼容)确定，不由 Java、Spring Boot 或 Maven 的采用推导其他组件。
- 其他语言或框架的官方工程、模板和组件适配不因本项决定而成为首版交付承诺。服务调用仍按公开合同设计，不将实现语言当作业务或数据边界。
- 采用上述框架不改变领域模型的技术隔离要求，也不代表选定 Spring Modulith 或所有 Spring／Alibaba 组件。

## 版本与兼容

生产基线优先选择仍有明确维护与安全更新来源的稳定版本，JDK 优先采用适用的 LTS 版本；不默认采用预览语言特性、快照或候选发布版本。

| 基线对象 | 必须记录的内容 | 验证要求 |
|---|---|---|
| JDK | 发行版、确切版本、编译目标及支持的运行环境，维护来源与适用许可证 | 核对编译与运行环境，验证受支持环境中的真实行为；LTS 名称不能替代发行版的维护依据 |
| Spring Boot 及框架 | 确切版本、官方依赖管理范围、使用的组件及兼容限制 | 检查同一工程的最终依赖组合，验证启动、关键能力及故障场景 |
| Maven 与构建插件 | 确切版本、下载来源、分发校验及各插件执行范围 | 本地与 CI 使用相同声明的构建入口，不依赖开发机偶然安装的版本 |
| 技术适配及运行依赖 | 驱动、客户端、适配模块、服务端和必要插件的版本及受支持组合 | 验证实际启用的能力和声明的默认、扩展及运行环境，不以各组件单独支持声明代替组合验证 |

长期规范保存选择和验证方法；具体版本组合集中保存于相应版本基线与构建配置，第五层先落实具体门禁必需的基线，其他能力按后续系统设计确定，不在多份规范中复制版本号。资料页面更新不触发项目自动升级；普通需求使用已有受支持基线。

版本升级说明变更理由、兼容影响、迁移及回退前提，并重新验证受影响能力与消费方。发现基线缺少维护或安全更新依据时，提出升级或有证据的例外决定，不默默继续把它称为受支持组合。

技术依据：[Spring Boot 系统要求](https://docs.spring.io/spring-boot/system-requirements.html)明确运行及构建前提，也提示第三方组件可能有额外要求；[Spring 支持策略](https://spring.io/support-policy)区分项目及支持条件；[Oracle Java 路线图](https://www.oracle.com/java/technologies/java-se-support-roadmap.html)的商业维护与许可说明仅适用于其声明范围，不能推导所有 OpenJDK 发行版的支持承诺；[Maven 下载页](https://maven.apache.org/download.cgi)区分稳定与预览分发。

## 构建与依赖管理

确认来源：2026-10-12 本会话用户选择 A：官方能力入口承诺的 API 可用，偶然传递库须显式声明，BOM 不算能力入口。

- 官方工程提供 Maven Wrapper，固定分发版本与校验信息；JDK 的安装和选择单独声明，Wrapper 不代替 JDK 校验。构建前验证必要环境，不能在版本不符时仍记为通过。
- 构建插件及依赖版本有唯一管理来源。平台用集中依赖管理公布受支持组合，具体父 POM 与版本化 BOM 组织在后续设计中落实；消费工程不因导入 BOM 被强制继承平台内部构建结构。
- 源码直接使用的库应显式声明依赖，版本可由有效依赖管理提供。官方 starter／聚合入口已承诺提供的 API 可通过该入口直接使用，不要求对同一能力重复逐 JAR 声明；普通偶然传递库仍须显式声明，BOM 单独不算能力入口。声明必要的作用范围；不能靠碰巧存在的传递依赖、机器上的 JAR 路径或未公布内部模块完成构建。
- 交付使用的依赖及插件不得采用浮动版本、范围、`LATEST`、`RELEASE` 或 `SNAPSHOT`。研发期临时版本不作为交付证据；受支持组合须核对最终解析结果，而非仅查看手写配置。
- 新增库、排除传递依赖或覆盖上游管理版本时，说明实际用途、作用范围和冲突处理依据，验证受影响场景；不能仅为消除警告扩大依赖或随意覆盖版本。
- 构建配置及下载地址不包含凭证；私有仓库访问通过受支持的外部配置注入，日志和交付文件不暴露密钥。
- 快速增量检查可以服务开发过程，但交付必须运行完整适用门禁。跳过测试、未触发必需插件、没有扫描到目标或缺少必需环境的结果，不能标为交付通过。

具体 Maven 命令、插件配置、扫描范围及必需测试列表在相应工程和门禁中固化。生产版本固定不等于依赖组合已经兼容，构建成功也不替代真实运行场景。

技术依据：[Maven 依赖机制](https://maven.apache.org/guides/introduction/introduction-to-dependency-mechanism.html)说明传递依赖、直接依赖、作用范围和集中版本管理；[Maven Wrapper 文档](https://maven.apache.org/wrapper/)说明版本化分发与校验能力。工具校准与产品构建的责任边界见[工程机制](../workflow/04-工程检查设计.md#真实-wrapper-构建生命周期校准)。

## 已确认的依赖漏洞门禁原则

确认来源：2026-10-09 本会话用户要求仅确定版本，接入 Maven 依赖扫描并提示安全告警。

依赖安全采用固定成熟工具，扫描新增或变更的 Maven 依赖并提示安全告警。范围决定见[任务决定](03-技术与构建.md#已确认的依赖漏洞门禁原则)。

- 固定成熟 Maven 扫描插件的版本；新增、升级或移除依赖后，对实际解析的直接及传递依赖运行检查，包含测试依赖。
- 输出能够定位组件、实际版本、漏洞标识和工具报告等级的告警及报告。漏洞发现不自动阻断功能构建，也不因构建成功被解释为没有风险。
- 扫描未运行、资料不可用或执行失败必须显式标为未完成；不能把空报告或缺失结果当作零漏洞。扫描工具错误与发现漏洞分别处理。
- 使用工具原生识别、评分、资料更新及报告能力。不自研漏洞库、评分器、抑制审计、原生资产清单、发行审批或重新打包组成核对，不将这些作为脚手架的前置交付。
- 基础扫描有识别及来源局限，不承诺完整安全证明。告警由研发者结合实际用途处理；需要整改时验证升级兼容性，不为了消除提示删除扫描或隐匿已知风险。

具体固定版本、最小配置与执行方式集中在[基础 Maven 告警接入](../workflow/04-工程检查设计.md#基础-maven-依赖安全告警)。本项不改变业务鉴权、源码、架构及真实功能验证要求，也不新增产品安全平台。

## 风险核对与验证

只验证与上述范围直接相关的三个结果：

| 场景 | 必须观察到的行为 |
|---|---|
| 正常依赖检查 | 实际 Maven 解析和扫描完成，生成报告；结果仅限扫描范围，不宣称整个项目安全 |
| 新增已知漏洞依赖 | 告警定位组件、版本及漏洞，保留报告；不因发现漏洞自动使功能构建失败 |
| 扫描缺少必要资料或执行失败 | 明确执行失败／未完成，不能输出安全通过；修复环境后重新执行 |

配置检查只能证明固定版本、执行绑定及告警参数，不能替代真实 Maven 正常、漏洞告警和执行失败场景。没有实际产品 Maven 工程时，只记录隔离接入验证，产品扫描保持未完成。依赖整改后重新解析、扫描并执行受影响功能回归。

资料依据：[OWASP Dependency-Check Maven 官方配置](https://dependency-check.github.io/DependencyCheck/dependency-check-maven/configuration.html)区分漏洞失败阈值与分析执行错误，并提供原生 HTML／JSON 报告；本项目按最新范围使用这些成熟能力，不另建安全策略执行系统。

## 制品与独立消费

每个交付制品明确坐标或身份、不可变版本、来源输入、运行前提及所需配置。业务配置与密钥不打入通用制品；构建输入与产出可追溯，不能用同一正式版本覆盖发布不同内容。

消费项目显式选择平台版本，通过公开制品、合同和扩展位置接入。升级时按[合同兼容要求](02-系统设计.md#合同与失败语义)验证；不能把升级平台制品隐式变成消费项目同步发布的要求。

验证起步工程时使用声明的制品获取方式和运行前提，在独立目录完成构建、启动与接入。不能仅依赖平台工作区的源码联合构建、相对文件路径或开发者未声明的本地临时安装。须按产品要求验证[两个项目独立消费](../product/01-产品定义.md#第一层验收场景提纲)，并保留各项目的版本与结果。

具体制品拆分、仓库、发布和创建工程的方式由后续系统设计确定；普通功能文档与代码同步交付的流程由第四层规定，本规范不建立第二套任务状态或 Git 验收源。

## 检查与失败反例

以下要求结合真实工程及适用风险验证；工具范围见[工程机制](../workflow/04-工程检查设计.md#基础-maven-依赖安全告警)，局部结果不代替完整适用检查。

| 可判定约束 | 必须失败的反例 | 仍需其他证据的内容 |
|---|---|---|
| 构建使用声明基线 | JDK、Maven 或必需插件不符却继续通过 | 具体版本组合的能力兼容性 |
| 交付版本可确定 | 最终解析依赖包含禁止的浮动或快照版本 | 上游支持与安全风险的实际影响 |
| 基础依赖告警真实执行 | 没有告警或报告、扫描失败／未执行却声称安全通过 | 工具识别局限及实际影响，详见[风险核对与验证](#风险核对与验证) |
| 技术与模块依赖符合边界 | 应用或领域代码访问持久化实现，或引用未公布内部模块 | 业务归属、规则准确性及动态装配 |
| 必需检查确实执行 | 关闭测试、跳过必需门禁或目标扫描遗漏仍报告交付成功 | 断言是否检验真实合同与失败结果 |
| 独立消费前提成立 | 消费工程只能靠平台源码或开发机隐含文件构建运行 | 接入、扩展、升级和故障的完整业务场景 |

校验器本身用隔离反例验证，并纳入后续 CI。配置存在、编译通过或插件返回成功不证明门禁有效。发现违规按已确认的[整改与复验原则](02-系统设计.md#运行约束与设计审阅)处理，不能删除断言或降低规则使其通过。
