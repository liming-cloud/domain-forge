# 源码质量规范

适用于平台、模板和业务服务的 Java 源码。职责划分见[系统设计](02-系统设计.md)，自动检查的配置见[工程与构建](../architecture/02-工程与构建.md#质量门禁)。

## 职责位置

### C-01 按真实职责放代码，不建空目录

**规则**：业务服务按 `bootstrap`、`interfaces`、`application`、`domain`、`infrastructure` 五个职责包组织（含义见[系统设计 S-01](02-系统设计.md#s-01-五个职责各管各的事)），每个职责内按真实业务适度分组。没有对应职责就不创建源码或目录：不要求空领域层、成对的接口与实现、只转发的层。通用技术组件（如 web-support、cache）按自身职责组织，不套用业务分层。

**反例**：为"目录齐全"创建只有一个空接口的 `domain/service`；每个类单独一个子包。

**检查**：自动（`[职责归属]`：业务服务中不在五个职责包内的类会被拒绝）；是否过度拆分由评审判断。

### C-02 `public` 不等于公开合同

**规则**：只暴露实际合同和框架接入需要的访问范围。Java 的 `public` 不授权其他模块使用内部实现；组件的公开 API 放在 `api` 包，内部实现放在 `internal` 包。降低可见性不能免除注释、合同和架构检查。

**检查**：自动（`[内部实现]`、`[跨上下文]`）。

## 格式

### C-03 统一 google-java-format

**规则**：所有 Java 生产和测试源码使用 google-java-format（版本见 parent POM），本地和 CI 使用同一配置。提交前运行 `spotless:apply`。不要顺带重排无关文件；会改变行为的重构不能混在格式化提交里。

**检查**：自动（`spotless:check` 在 verify 阶段执行，只检查不改写）。

## 表达与状态

### C-04 命名表达业务含义

**规则**：类型、方法、字段按所属上下文的业务语言命名，缩写和常量要有可理解的依据。不靠统一后缀、类型数量或模式名称表达职责。

**检查**：评审。

### C-05 保护领域状态

**规则**：领域对象的状态只能通过表达业务行为的方法改变，核对构造、属性写入、集合返回和重建等所有入口。不用通用 setter、可变引用或生成方法绕过规则。实体不使用 Lombok `@Data`；生成的 `equals`、访问器、`toString` 要逐项符合身份、状态保护和不泄露秘密的要求。数据传输对象和 PO 可以有普通属性读写，但不能和领域模型合并。

**反例**：`account.getPermissions().add("iam:grant:manage")` 绕过授权规则直接修改返回的集合。

**检查**：评审；测试覆盖非法状态转换。

### C-06 合理使用 Java 21 特性

**规则**：

| 特性 | 用法 |
|---|---|
| record | 透明数据载体；可变成员要防御性复制，不能假定深不可变 |
| `Optional` | 主要用于返回值缺失，不用于参数，不代替校验或故障结果 |
| switch 模式匹配、sealed | 用于简化真实的类型分支 |
| Stream | 用于清楚的转换；复杂副作用、事务、错误处理用普通控制流 |

**检查**：评审。

### C-07 时间、金额、资源、异常

**规则**：

- 时间来源通过注入或最小接口取得；区分墙上时间、经过时长、数据库权威时间，不混用时区。
- 金额和比例使用明确单位、舍入规则和 `BigDecimal`（或带单位的整数），不用浮点。
- 资源由创建方关闭，优先 try-with-resources。
- 异常保留原因；捕获 `InterruptedException` 时恢复中断标志或继续传播，不吞掉取消。

**检查**：评审。

### C-08 并发要有协议

**规则**：无状态 Spring 单例不保存请求状态。共享可变状态要写明并发协议：`volatile` 只保证可见性，不保证复合操作原子；进程内锁不能作为跨实例保证。线程池、队列、连接、重试都必须有界。

**检查**：评审；有并发约束的代码要有并发测试。

## 注释

### C-09 每个生产类型都有中文说明

**规则**：生产代码中的每个命名类型（类、接口、枚举、record、注解、嵌套与局部命名类型），不论可见性，都有自己的简体中文 Javadoc。首句说明这个类型承担什么职责；有使用前提、数据含义、生命周期、线程安全等容易误用的约束时补充说明。Javadoc 放在所有注解之前。

**正例**：

```java
/** 装配当前模块的关系持久化组件。 */
@Configuration
class PersistenceConfiguration {}
```

**反例**：

```java
@Configuration
/** 装配当前模块的关系持久化组件。 */   // 位置错误：在注解之后
class PersistenceConfiguration {}
```

**检查**：自动（Checkstyle `MissingJavadocType`、`InvalidJavadocPosition`、`SummaryJavadoc`）；说明是否准确由评审判断。

### C-10 合同方法和关键行为要有说明

**规则**：以下方法要有中文 Javadoc：公开合同（用例、出口接口、组件 API）的方法与构造器；包含业务规则、副作用、失败处理或其他容易误用语义的内部方法，即使是 private。说明完成什么操作，以及调用方需要知道的参数含义、结果与空值、副作用、失败行为，适用时再说明权限、事务、并发、资源责任。没有额外语义的简单访问器和纯委托可以省略。

**反例**：名为 `getPermissions()` 的方法实际做了权限过滤却没有说明；用 `@Override` 默认继承说明，但实现新增了校验。

**检查**：评审（自动检查只覆盖类型说明）。

### C-11 匿名类和 lambda

**规则**：简单的局部回调可以用匿名类或 lambda，不要求单独的类型说明；有独立职责时提取为命名类型并按 C-09 说明。不能把独立职责藏进匿名体来规避说明和检查。

**检查**：评审；匿名体和 lambda 同样计入复杂度、依赖和行为检查。

### C-12 测试用清晰的名称代替冗余注释

**规则**：测试不强制 Javadoc，用清晰的测试名和必要说明表达条件与预期。复杂夹具、时间与并发控制、故障注入、特殊断言依据要说明。测试改变时同步更新说明。生产用途的代码放到测试目录也仍按生产规则处理。

**检查**：评审；测试中如果写了 Javadoc，位置同样受 `InvalidJavadocPosition` 检查。

## 复杂度

### C-13 方法复杂度上限

**规则**：生产和测试代码的每个方法、构造器、初始化块：圈复杂度不超过 10，可执行语句不超过 30。lambda 的分支计入所在方法。超限时消除混杂的职责和重复分支，提取的方法要有真实职责；不为凑数字制造只转发的方法，也不把逻辑挪到检查不到的地方。

**正例**：`RedisLoginProtection.reserve` 超限后，把事务内锁定与代际核对提取为 `policyAllows(generation)`，行为不变。

**检查**：自动（Checkstyle `CyclomaticComplexity`、`ExecutableStatementCount`）。

### C-14 例外须人工批准且范围精确

**规则**：确需保留超限实现或跳过某项检查时，在 PR 中写明对象、指标、理由、影响和替代验证，由人工批准；批准只对该对象生效。不使用 `@SuppressWarnings`、抑制配置或排除路径自行放行。

**检查**：评审。

## 生成代码

### C-15 生成代码的豁免

**规则**：只有外部工具重复生成、不手工维护的输出，才能在人工批准后豁免注释、格式或复杂度检查，豁免不包括编译、架构、安全和行为验证。登记生成器版本、输入、输出范围和豁免的规则；输出必须能从输入重新生成。AI 生成后由项目维护的代码不属于生成代码；只加 `@Generated` 或放进生成目录不能获得豁免。

**检查**：评审（目前没有生成代码）。
