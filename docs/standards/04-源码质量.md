## 已确认的源码职责定位原则

- 业务上下文使用统一的默认职责位置，并明确公开契约的识别方式。新任务沿用工程基线与所属模块声明，不自行发明另一套同义位置或将语言可见性当作跨上下文使用许可。
- 按实际职责创建源码，不要求目录齐全、空领域模型或无职责的转发层；内部细分保持真实职责与既有依赖方向。非标准组织说明实际需要，超出有效规则时取得精确人工例外，不能靠重新登记消除越界事实。
- 新增源码的所属上下文、职责及公开范围须可核对，真实依赖仍执行[逻辑模块与依赖门禁](02-系统设计.md#逻辑模块与依赖门禁)。仅放入正确目录或标识为公开，不能证明实现的业务归属、职责与依赖正确。
- 本项针对业务上下文。通用技术组件按自身真实职责组织，不强套业务分层或领域模型；不要求每个用例增加 `port.in` 接口，也不增加固定 Maven 模块数量。入口与出口继续遵守[按需入口接口](02-系统设计.md#入口端口与用例契约)和[业务出口及通用契约复用](02-系统设计.md#出口端口与平台能力复用)。
- 具体约定名称、公开标识、依赖声明及检查机制按以下细化稿与后续基线落实；实际上下文、包路径、制品拆分和产品代码仍在整套控制面确认后的设计研发阶段形成。

## 职责位置与公开范围细化

下列默认职责位置约定沿用已有规范；总体结构已批准的 context.bootstrap 及查询短路径见[总体架构](../architecture/01-总体架构.md#ddd-边界与代码映射)，阶段 2a 定向适配真实检查后才进入相应产品实现。

每个业务上下文有明确的包根及代码范围。默认在该根下按以下职责位置组织，必要时在其内部按实际功能细分；没有相应职责便不创建源码或空目录。

| 默认职责位置 | 归属与使用要求 |
|---|---|
| `interfaces` | HTTP、消息及任务等入口适配和必要的协议数据；调用已公布的应用用例，不直接执行持久化或客户端操作 |
| `application` | 应用用例、编排及用例合同；不因目录名称而将其中全部类型或方法对其他上下文开放 |
| `domain` | 实际需要的领域模型和业务规则；简单用例不为满足目录形状制造领域类型 |
| `bootstrap` | 已批准的 context 内启动、接线与生命周期职责；其他职责不得反向引用，本次尚不实现规则适配 |
| `infrastructure` | 持久化、技术客户端及适配器；框架通用基类、Mapper、PO 与 SQL 遵守[持久化职责](05-持久化.md#工程职责与类型边界) |

`port.in` 与 `port.out` 表达合同职责而非强制增加的层次。公开应用方法可以直接承载用例契约；需要显式入口接口时在应用合同的范围内组织。业务出口按实际使用者及依赖方向定位，已满足要求的平台公开通用契约直接复用；不为了统一路径重复创建接口。具体端口子位置随工程基线固定，不在每个任务中临时约定。

模块声明集中表达上下文包根、实际职责范围、对外契约和允许依赖，默认约定与该声明共同供检查使用；声明语法及工具在门禁基线固定。新增文件须落在有效范围，未识别源码不能作为漏检后的通过。装配入口、通用组件等非业务上下文源码也有明确归属及相应依赖要求，不能把未登记业务代码改称通用组件来避开边界。

公开契约标识能确定实际允许调用的用例及其必要数据、结果和失败类型。按实际合同核对可达类型与声明的公开范围，不能仅凭 `public`、包名含 `api` 或目录位置把整包内部实现开放；也不要求为了标识公开范围另建一套接口、镜像 DTO 或额外构建模块。公开机制不改变[注释合同责任](#已确认的方法注释)及既有技术隔离要求。

## 职责定位验证

结构及依赖检查负责可判定约束，业务职责准确性仍须源码与场景证据评审。

| 情形 | 正例与必须识别的反例 |
|---|---|
| 按需采用默认位置 | 只包含实际入口、用例及适配的轻量上下文允许通过，不要求空领域层或成对接口 |
| 位置与实际依赖不符 | 应用在正确包中仍访问 Mapper，或将 SDK 包装成领域类型，不能因路径正确而通过 |
| 公开契约与内部实现 | 已公布且允许依赖的调用可以通过；引用未公布应用方法、框架技术类型或另一上下文内部模型须识别 |
| 声明与扫描覆盖 | 新增源码未被归属、归属冲突或缺失必要扫描必须识别，不把未知范围视为合法技术组件 |
| 合法通用组件或精确例外 | 按实际职责及有效范围检查，不误要求业务四层；无依据扩大公开范围或例外不能放行 |

门禁实现还须复用[模块边界反例](02-系统设计.md#逻辑模块与依赖门禁)，不能只检查目录存在。运行装配、动态调用与数据访问继续由相应真实场景验证。第五层已有[真实编译、模块归属及直接合同的子集校准](../workflow/04-工程检查设计.md#真实编译与模块合同绑定)；完整职责、技术类型隔离、合同闭包及语义结果仍未证明，不将子集检查视为本节整体验证通过。

## 已确认的格式基线

- 选择与项目基线兼容的现成格式方案，固定执行工具、版本及配置；文档引用唯一配置，不再逐条维护同一套排版细则。
- 本地与 CI 使用同一格式基线，适用源码的格式偏离须整改。已确认的注释位置、复杂度及架构要求继续有效，工具输出不能覆盖这些规则。
- 本项决定格式规则的形成方式，不等于采纳所选方案的全部编码规则；命名语义、职责、合同与业务质量仍需相应规范及评审。
- 工具、版本及配置统一维护于[工程机制](../workflow/04-工程检查设计.md#工具选择与支持边界)；产品采用前验证实际组合，不能用隔离格式校准替代产品门禁。

## 格式执行与验证

项目维护的 Java 生产与测试源码采用统一格式基线；外部生成输出仅按[有效人工登记](#已确认的生成源码治理)处理，不能凭生成标记或目录默认排除。其他文件类型的适用格式范围单独明确，不由本项自动选定工具或规则。

工具与配置在[受支持技术基线](03-技术与构建.md#版本与兼容)中固定，源码检查及编辑器接入引用同一来源。选择时验证所用 Java 声明形式、简体中文 Javadoc、全部注解之前的注释位置及多次格式化结果，避免两套工具反复改写或覆盖必要内容。格式检查通过不能证明注释准确、命名恰当或实现正确。

开发时可以对当前任务范围应用格式，再核对差异及受影响检查；不能顺带重排无关维护源码。交付检查采用不修改源码的检查方式，发现偏离后整改并复验，不由 CI 悄悄改写输入后宣称提交通过。导入整理等处理须明确纳入的步骤；会改变行为或结构的重构不能混入排版操作而免除相应评审与测试。

复杂度计量以统一格式基线下的实际实现为依据，校准方法长度时同时固定格式方案。更换格式方案或配置时核对数值及其他门禁的影响，不能临时改变换行方式使某个超限实现通过。

| 情形 | 对应验证要求 |
|---|---|
| 合法维护源码按基线格式化 | 格式检查通过；重复应用不继续产生排版差异，其他适用检查仍须执行 |
| 适用源码偏离格式、未扫描到或未执行必需检查 | 相应交付检查必须失败，不能以只处理部分文件作为完整通过证据 |
| 本地与 CI 使用不同工具、版本或配置 | 基线核对必须识别不一致，不能依赖编辑器默认设置 |
| 错位 Javadoc 被格式工具接受 | 对应注释位置检查仍须失败，不能以格式通过代替注释规则验证 |
| 格式处理改变合同、必要说明或行为 | 核对差异与相应合同、注释及行为证据，不能将变化认定为纯排版而放行 |

技术依据：[google-java-format 官方说明](https://github.com/google/google-java-format)说明固定布局及 Java 运行前提；[Spotless Maven 文档](https://github.com/diffplug/spotless/tree/main/plugin-maven)区分检查与应用格式。固定工具及限定执行见[校准支持边界](../workflow/04-工程检查设计.md#工具选择与支持边界)，不由工具能力推导产品组合已通过。

## 源码表达与状态保护

本节依据已确认的领域与职责原则规定源码表达与状态保护。

- 类型、方法及字段按[统一语言与所属上下文](01-需求与领域建模.md#领域与上下文识别)命名，表达真实业务含义或技术职责；缩写、常量及辅助步骤应有可理解的依据。不用统一后缀、类型数量或模式名称代替职责判断，格式化也不能证明名称恰当。
- 只暴露实际合同与框架接入所需的访问范围。Java 可见性不是[跨模块公开合同](02-系统设计.md#逻辑模块与依赖门禁)，必要的 public 声明不自动授权其他模块使用内部实现；也不能降低可见性来省略合同、注释或架构检查。
- 领域状态按[模型与不变量](01-需求与领域建模.md#上下文模型与战术设计)维护。核对构造、属性写入、集合返回及重建等实际入口，不能通过通用访问器、可变引用或生成方法绕过规则。数据传输及持久化对象按实际职责处理，不因存在属性读写就一律判定违规，亦不将其与领域模型合并以规避状态保护。
- 按实际合同明确空值、默认值、单位、精度及状态含义，不靠名称或语言默认值隐含决定。领域与持久化转换引用[对象分离要求](02-系统设计.md#领域与持久化对象分离)，不在源码规范重定义模型或存储语义。
- 分支、循环、辅助方法及复用按可读性、真实职责和变化需要选择。不统一要求所有类型不可变、所有用例增加接口，或每个步骤套用设计模式；也不能以实现简单为由绕过已确定的规则。复杂度指标与必要抽象的质量分别核对。

验证先核对源码的合同、状态入口及调用路径：允许职责清楚的轻量实现、简单数据属性和必要框架访问；拒绝有证据的越界访问、规则旁路或语义失实。自动检查负责已声明的依赖和可判定结构，命名准确性、公开必要性及状态规则是否完整由源码、合法非法场景和变更依据评审。不凭存在 setter 或缺少某个模式机械判定质量，也不将语义判断包装成脚本证明。

## 已确认的类型注释

- 每个生产命名类型都须有自己的简体中文 Javadoc，包括类、接口、枚举、record、注解类型及命名嵌套类型；抽象类、内部类和命名局部类不因形式而豁免。
- 不区分 public、protected、包可见或 private。降低可见性、调整目录、类型改名或改变生成来源，不能免除适用规则；AI 生成的项目代码仍是项目生产代码。
- 注释放在所属类型声明之前；存在注解时放在全部声明注解之前，不能夹在注解与类型名之间或注解之间。文件说明、外层类型注释不能替代本类型注释。
- 正文说明真实职责及适用的关键约束，不以空注释、只有标签或机械复述类名满足要求。必要的 API 名称与技术标识可保留原文，职责说明使用简体中文。
- 方法、测试与外部生成物分别执行[方法注释](#已确认的方法注释)、[测试注释](#已确认的测试注释)及[生成源码治理](#已确认的生成源码治理)。

## 注释内容与位置细化

首句用简短、完整的说明回答“这个类型承担什么职责”。确有使用前提、数据含义、生命周期、线程安全或其他容易误用的约束时，补充相应说明；简单类型不机械填写不存在的复杂性清单。注释与当前代码、公开合同和场景保持一致，代码改变职责或约束时同步更新。

普通行注释或普通块注释不能替代 Javadoc。采用的文档注释形式必须被所选 JDK 和检查工具识别；以下仅用传统 `/** ... */` 表示位置，不选定项目 JDK 或具体装配方案。

正确位置：

```java
/** 装配当前模块的关系持久化组件。 */
@Configuration
class PersistenceConfiguration {
}
```

不符合位置要求：

```java
@Configuration
/** 装配当前模块的关系持久化组件。 */
class PersistenceConfiguration {
}
```

示例只演示注释，不是已经存在的源码，也不证明任何组件已经实现。类型有多行注解、多个注解或非 public 修饰符时仍遵守同一位置要求。

## 已确认的方法注释

- 生产代码中，公开合同的方法与构造器须有简体中文 Javadoc 合同说明；包含业务规则、副作用、失败或其他易误用语义的内部方法同样必须说明，不因 private 或包可见而豁免。
- 仅无额外语义的内部简单访问器或纯委托允许省略重复注释。方法名、可见性、代码行数或覆盖注解不能自动证明满足省略条件。
- 公开合同按实际用例、业务协议及能力接口判断，不等同于搜索 public 关键字；降低可见性不能消除原有合同或关键行为的说明责任。
- 不要求所有方法机械填写重复注释，也不免除生产类型全覆盖。测试及外部生成物分别遵守[测试注释](#已确认的测试注释)与[生成源码治理](#已确认的生成源码治理)。

## 方法内容与省略条件

必须说明的方法先回答“完成什么操作，以及调用方需要知道什么”。根据真实合同说明必要的参数含义与前提、结果及空值语义、副作用、拒绝与失败行为；适用时补充权限、事务、并发、重试或资源责任，不机械列出所有不存在的事项。参数、结果及异常说明与签名和行为一致，不用空标签、名称复述或“出错时抛异常”替代真实合同。

文档注释位于所属声明的全部注解及修饰符之前。引用已有完整合同可以减少重复，但引用须可定位且适用于本方法；新增前置条件、结果转换、异常映射或其他行为仍须补足。文档继承须满足所选基线的真实处理条件，不能凭 `@Override` 或 `{@inheritDoc}` 推定合同已经完整。

省略重复注释须同时满足：属于内部实现而非新的公开合同；访问器或委托的相关字段、目标和有效合同可明确识别；没有额外的业务校验、权限、状态变化、转换、默认值、异常处理或其他容易误用的语义。无法确认时写出必要说明，不以“看起来简单”直接跳过。

以下只说明判断方法，不预定实际产品代码：

| 情形 | 注释处理 |
|---|---|
| 内部方法直接读取已有合同明确的字段，没有新增语义 | 可以成为省略候选；仍须核对实际字段与调用合同 |
| 内部方法完全按已有合同纯委托，没有新增语义 | 可以成为省略候选；不能只因方法体是一行就认定成立 |
| getter 名称的方法新增权限过滤、默认值或结果转换 | 必须说明，即使只有一行或采用非 public 可见性 |
| 私有校验、状态变更、异常映射或失败恢复步骤 | 必须说明关键行为，不能通过分解为私有辅助方法隐藏合同 |

按规则允许的省略不是违规例外，不逐个要求额外人工审批；在正常任务评审中验证实际依据。确需超出本规则的豁免，仍按[覆盖范围与例外](#覆盖范围与例外)处理。行为变化后重新判断，原先可省略的方法新增关键语义时须补充注释。

## 已确认的匿名实现原则

- 简单局部回调、适配等可以采用匿名类，不机械要求其拥有独立的类型 Javadoc；具有独立职责时提取命名类型，并遵守[命名类型注释要求](#已确认的类型注释)。不能将独立业务职责改写成匿名体来逃避说明与检查。
- 匿名方法的公开合同与关键行为继续遵守[方法注释要求](#已确认的方法注释)，符合条件的文档引用、继承及内部纯委托按同一规则处理；不凭匿名形式或 `@Override` 自动豁免。初始化及所属操作的关键行为也须有必要说明。
- 匿名方法、初始化及真实依赖纳入适用格式、复杂度、架构和行为检查，不能因没有类型名而漏检。实际生产用途不因移至测试目录而改变；生成输出只按有效登记处理。
- lambda 不被一律禁止，也不要求每个表达式补 Javadoc；命名嵌套或局部类型须有自己的类型注释。其他隐式类型与语言形式按[源码覆盖范围](#覆盖范围与例外)核对。

## 匿名实现说明与验证

说明与实际合同对应：需要方法 Javadoc 时仍位于该方法的全部注解与修饰符之前；初始化或局部操作的必要解释可以在所属操作说明或恰当的局部注释中补足，不为没有命名声明的表达式制造虚假类型说明。选择匿名形式不改变权限、事务、资源、失败或重试责任。

| 情形 | 对应检查或评审要求 |
|---|---|
| 简单局部回调或适配，必要合同及关键行为已说明 | 不因缺少独立类型 Javadoc 而误拒绝；其他适用门禁继续执行 |
| 匿名方法含关键行为但缺少说明，或引用合同与新增行为不符 | 用源码及场景核对方法说明责任，不能按匿名形式或覆盖注解统一放行 |
| 匿名体访问禁止依赖、超出适用复杂度阈值或遗漏扫描 | 相应门禁须失败，不能只检查外层命名声明后报告完整通过 |
| 独立职责被藏入匿名体以规避类型说明 | 有证据的职责评审要求整改；不能用表达式长度或目录位置代替职责判断 |
| 命名局部或嵌套类型缺少自身注释 | 仍须被类型检查识别，不能套用匿名实现的说明方式 |

结构、位置、依赖、计量及执行覆盖按相应门禁验证；职责是否独立、说明是否充分由源码、合同与场景证据评审。当前[隔离校准](../workflow/04-工程检查设计.md#注释与格式的限定校准)已涉及匿名体内命名类型、方法及部分计量，不代表匿名实现全部责任、真实依赖和语义已通过。

## 已确认的测试注释

- 测试源码以清晰的场景名称和必要说明为主，不统一要求每个测试类型或测试方法重复填写 Javadoc。
- 名称或场景说明须让读者识别所验证的条件与预期；非直观的前提、夹具、断言依据及辅助行为须有必要说明，不能因不强制 Javadoc 而不解释实际复杂性。
- 本项减少重复说明，不降低场景、断言及证据要求；写有完整注释不能替代有效测试。
- 测试注释不改变生产类型与方法要求；复杂度执行[独立测试基线](#已确认的测试复杂度基线)。

## 测试说明与验证

说明以实际条件、动作与预期为依据，不机械重复方法名或断言语句。可以用明确的测试名称或测试框架支持的场景说明承载易识别的内容，不要求两者重复；只有必要信息尚不清楚时才补充注释。自然语言说明使用简体中文，技术标识可保留原文，不强制采用中文 Java 标识符或某个框架注解。

复杂夹具、时间与并发控制、故障注入及关键测试辅助工具说明必要前提、作用和恢复责任；断言依赖特殊业务依据时解释其来源。测试或合同变化时同步更新，不能保留与实际断言不符的旧说明。采用类型或方法 Javadoc 时仍放在所属声明的全部注解与修饰符之前；本规则不强制将所有必要说明都改写为 Javadoc。

范围按真实用途判断：被产品或消费工程用作生产实现的代码，即使位于测试目录或由测试工具生成，仍遵守生产规则。不能移动路径或更名来取得测试注释待遇；只有测试用途的源码按本节处理，具体识别范围在工程与门禁中固化。

| 情形 | 验证要求 |
|---|---|
| 场景名称或说明已清楚表达条件与预期，没有额外前提 | 允许没有重复 Javadoc，不得因统一套用生产注释检查而误拒绝 |
| 名称笼统、复杂夹具无说明或注释与断言不符 | 用源码、合同与断言证据整改，不能只补空注释或名称复述 |
| 项目生产实现移入测试目录后不再受生产检查 | 必须识别其真实用途与扫描遗漏，不得将目录变化作为豁免依据 |
| 测试使用 Javadoc 但放在声明注解之后 | 对采用的 Javadoc 执行相应位置检查，不能因属于测试而放行错位 |

自动检查负责可识别的执行范围和所采用文档形式的结构、位置；场景描述是否准确、前提是否充分及断言是否有效，需要有源码与场景证据的评审。没有 Javadoc 本身不是测试违规。

## 已确认的复杂度门禁

- 最终纳入硬门禁基线的指标采用固定阈值；适用实现超过阈值时阻断交付，须整改后复验。
- 确需保留超限实现时，取得精确、有依据的人工例外。普通质量评审、工具抑制配置或 Agent 自行解释不能代替人工决定；例外按[覆盖范围与例外](#覆盖范围与例外)处理。
- 指标达标不替代职责、合同、业务语义及真实场景验证。不得以无职责的拆分、压缩排版、删减测试或降低规则规避门禁。
- 工具默认值不是项目阈值；初始基线和计量范围按下文唯一配置执行。

圈复杂度和可执行语句数执行硬门禁；固定排版后的方法行数仅辅助可读性评审，不单独阻断。生产与测试分别校准，计量口径见[机制设计](../workflow/04-工程检查设计.md#方法规模计量决策)。

已批准的初始上限唯一维护于[复杂度配置](../../tools/engineering_gate/complexity.json)，不复制到规范或索引；支持边界见[初始上限](../workflow/04-工程检查设计.md#初始上限与校准边界)。修改有效基线须有对应人工决定；已有版本化配置不能代为批准。

## 已确认的测试复杂度基线

- 测试源码纳入固定阈值复杂度硬门禁，采用与生产分开校准的测试基线；不自动照搬生产数值，也不默认提高全部测试上限。
- 校准覆盖测试主体、夹具及测试辅助逻辑的真实用途。测试范围、适用指标、计数口径及阈值有明确依据，不能仅按名称、可见性或目录漏检。
- 超限须整改并复验；确需保留时取得精确、有依据的人工例外，沿用[复杂度门禁](#已确认的复杂度门禁)及[例外边界](#覆盖范围与例外)，不增加自动放行方式。
- 不能为数值达标无意义拆散场景、隐藏断言或降低测试有效性；生产用途的实现即使位于测试目录，也按生产基线处理。
- 本项确认测试基线的组织方式与覆盖责任，不选定工具、指标或数值，也不证明测试或门禁已经执行。

## 复杂度计量与整改

阈值基线须同时声明指标定义、计数对象、上限、检查范围和工具配置。方法长度说明注释、空行及声明如何计入；圈复杂度说明哪些决定点计入及分支处理方式。构造器、初始化块和所选 Java 基线的新声明形式按各指标明确覆盖，不能借工具未支持或漏配声明形式转为通过。测试按[独立校准原则](#已确认的测试复杂度基线)处理；外部生成物仅按[已确认的治理原则](#已确认的生成源码治理)及实际获批登记处理，不能由工具默认排除隐式代替。

门禁阶段用有明确预期的代表性实现和边界反例校准工具、口径及数值，形成版本化的唯一配置；后续引用配置，不在多份规范中复制阈值。本地与 CI 使用同一基线，交付证据可核对实际执行版本、扫描对象及超限项。校准与例外须说明理由和影响，不能以让当前实现通过作为调整基线的唯一依据。

测试校准保留完整场景与断言，覆盖测试主体、数据夹具、并发或故障控制及辅助逻辑；区分表驱动数据长度与控制复杂度，不自动豁免某一类方法。生产与测试使用同一[数值基线](#已确认的复杂度门禁)，不同范围在共同配置中声明，不另建平行门禁。显式文件的数值通过不等于全量源码及其他门禁通过。

整改优先消除混杂职责、重复分支及难以验证的行为；提取的步骤须具有真实职责与清晰合同，并保持行为及测试有效。不为数值达标制造只有转发作用的层次、无意义的方法碎片，或将控制逻辑迁到未受检查的位置。合理拆分会损害可读性或边界时，提交带源码、替代方案和测试证据的例外申请，而非自行放行。

获批例外只对决定中明确的对象、指标与范围生效；记录超限结果、保留理由、风险及替代验证。相关实现或前提变化时重新核对适用性，不能将单次例外推广为全目录、同名方法或后续功能的豁免。例外记录须有真实决定来源，未获批准不得配置放行。

技术依据：[Checkstyle 圈复杂度](https://checkstyle.org/checks/metrics/cyclomaticcomplexity.html)的决定点及 switch 处理配置会影响结果；[方法长度](https://checkstyle.org/checks/sizes/methodlength.html)可配置空行、注释和声明形式的计数。这些资料只说明计量需明确口径，不选定工具或默认数值，也不证明指标能独自判断代码质量。

## 覆盖范围与例外

检查以实际生产源码和声明、表达式的适用责任为依据，不能只搜索 `public class`，也不能只检查文件名对应的外层类型。测试说明及其与生产用途的边界见[测试说明与验证](#测试说明与验证)。命名局部类型仍执行自己的类型注释要求，匿名实现按[已确认原则](#已确认的匿名实现原则)处理；允许匿名形式不是对其方法、依赖及关键行为的整体豁免。

所选 Java 基线的适用源码形式须能核对实际归属、注释与其他检查覆盖；工具不能识别时报告缺口，不能因扫描不到声明就通过。紧凑编译单元的隐式顶层类与匿名回调不同：它位于未命名包，不能作为业务上下文包内职责的默认组织方式。脚本、片段与验证夹具按实际用途及相应基线管理，不能借名称或文件形式把实际生产代码排除；不由本节自动批准某种语言形式或项目 JDK。

资料依据：2026-10-06 经 Exa 读取的 [Oracle 匿名类说明](https://docs.oracle.com/javase/tutorial/java/javaOO/anonymousclasses.html)说明其为没有类型名的表达式；该教程面向 JDK 8，本节只引用形式定义，不采用旧版本成员限制。[JEP 512](https://openjdk.org/jeps/512)说明紧凑编译单元及未命名包中的隐式类；引用该资料不选择 JDK 25，也不把隐式类与匿名类合并处理。项目准入、检查范围及真实验证仍分别确定。

项目维护的生成实现仍按同一规则检查；仅添加 `@Generated`、改为工具目录或把 AI 输出称为生成代码不能自行豁免。外部工具重复生成且不手工维护的输出按[生成源码治理](#已确认的生成源码治理)登记，实际豁免仅限获批链路、对象和规则。未获明确批准时，不得配置跳过注解或广泛排除路径。

确需例外时明确精确对象、来源、理由、影响及替代验证方式，按[人工例外边界](../product/01-产品定义.md#已确认的产品边界)取得决定。检查配置与获确认范围保持一致，不能先跳过再将通过结果当作追认依据。

## 已确认的生成源码治理

- 仅确有接入需要、由外部工具重复生成且不手工维护的输出，可以按人工批准的生成链路和精确范围获得有限豁免。
- 明确生成器、输入范围、输出范围、重复生成验证及可豁免的具体规则。符合有效登记的链路内更新按获批范围处理，不逐个为新增生成类型申请同一豁免；超出范围不能自行放行。
- 豁免仅限获批输出的指定注释、格式或复杂度检查，不一并关闭编译、架构边界、安全、接口合同及行为验证。
- 生成输入、项目维护的模板及适配代码仍遵守各自适用规则；AI 生成后由项目维护的代码不属于这类豁免，不能仅凭 `@Generated`、路径或生成来源跳过检查。
- 具体生成链路、范围和规则豁免须独立登记批准；治理规则不自动批准工具、目录或新产品功能。

## 生成链路登记与验证

引入外部生成输出时，说明实际用途、生成来源、维护责任及为何需要指定豁免。登记固定生成器及版本、输入约定与范围、输出识别方式、豁免规则、保留门禁和人工批准来源。目录或注解可以辅助识别，但不能独自证明来源；检查配置不建立与人工记录并行的审批事实。

用声明的输入、工具和环境从干净输出重建并核对本次产物，保留输入与输出的版本或摘要、执行范围及结果。若生成器包含时间戳等非语义差异，说明核对口径，不忽略实现或合同变化。手工修改输出、无法重建或混入项目维护代码时不能继续按原登记豁免；应修正生成输入或撤销不适用的排除，再执行对应检查。

有效登记内的正常输入及输出更新仍须重新生成与验证；生成器、输入约定、输出识别方式、维护责任或豁免需求变化时重新核对登记。超出获批范围时先取得新的人工决定，不能把批准某条链路变成批准整个生成目录或所有将来组件。

| 情形 | 对应验证要求 |
|---|---|
| 获批链路产生范围内的新输出，重复生成验证有效 | 允许按已批准规则处理，不因未逐个审批类型而误拒绝；保留门禁继续执行 |
| 仅添加生成标记或把项目代码移动到生成目录 | 不得得到豁免；检查实际来源及执行范围 |
| 没有人工批准、豁免规则不匹配或扩大排除范围 | 范围检查必须失败，不能用插件成功替代有效批准 |
| 输出被手工修改、混入维护代码或无法从声明输入重建 | 生成验证或范围核对必须识别失败，不能沿用旧结果 |
| 生成输入、模板或项目适配代码受错误排除 | 对应适用检查必须识别漏检；不能只检查输出目录的存在 |
| 获批输出出现编译、架构、安全、合同或行为缺陷 | 对应门禁或带证据的评审仍须拒绝，有限豁免不能变成整体质量放行 |

自动检查核对可判定的来源匹配、输出、配置范围及重复生成结果；真实用途、维护责任、豁免必要性和人工批准事实按流程评审核对。校验器以隔离失败反例和获批范围内的允许场景验证。

技术依据：[JDK Generated](https://docs.oracle.com/en/java/javase/25/docs/api/java.compiler/javax/annotation/processing/Generated.html)定义生成标记及生成器名称；[Protocol Buffers Java 文档](https://protobuf.dev/getting-started/javatutorial/)说明从输入定义生成 Java 类型。由此采用的治理判断是区分维护输入与可重建输出，不把注解或路径当作来源验证。这些资料不选定生成工具或将 Protocol Buffers 纳入首版，也不证明任何项目链路已验证。

## 类型注释验证

检查须识别真实声明、注释及源码位置，并覆盖所选 Java 基线中的类型形式；自动检查与语义评审分别给出证据。

| 验证对象 | 必须识别的失败反例或审阅问题 |
|---|---|
| 注释缺失 | public、包可见和 private 类型缺失注释；将 public 改为包可见后仍缺失，不得因可见性变化转为通过 |
| 类型覆盖 | 外层有注释而内部或局部命名类型缺失；接口、枚举、record 或注解类型漏检 |
| 声明位置 | 注释放在首个注解之后、多个注解之间或声明修饰符之后；不能以工具碰巧关联到类型作为位置通过依据 |
| 正文存在 | 空 Javadoc、仅有标签，或普通注释被误认为满足文档注释要求 |
| 范围与豁免 | 添加跳过注解、改变目录或生成标记后，未经批准的项目生产类型逃过检查 |
| 执行覆盖 | 未扫描到本次适用源码、遗漏支持的类型形式或关闭必需检查却报告通过；实际扫描及排除对象须可核对 |
| 语义质量 | 注释只有名称改写、职责失实、仍描述已删除行为或遗漏实际关键约束；需源码、合同及场景证据评审 |

允许反例也须验证：简短而准确的职责说明、非 public 的正确注释、多行及多个注解、嵌套类型各自的正确注释均应通过相应结构检查。不以强制冗长注释或扩大所有类型职责来消除误报。

自动检查可以判断缺失、正文结构、位置及声明覆盖，并辅助筛查语言；不能仅凭存在汉字就宣称简体中文、职责准确性和约束完整性已验证。这些语义要求按[任务责任](../workflow/02-任务执行.md#责任与人工决定)评审，检查通过不替代评审。

技术依据：[Javadoc 注释规范](https://docs.oracle.com/en/java/javase/25/docs/specs/javadoc/doc-comment-spec.html)说明注释与声明的位置关系和正文；读取 JDK 25 文档不选定项目 JDK。[Checkstyle JavadocType](https://checkstyle.org/checks/javadoc/javadoctype.html)不负责缺失检查；[MissingJavadocType](https://checkstyle.org/checks/javadoc/missingjavadoctype.html)默认只覆盖 public，并支持跳过注解。后续工具须明确启用的规则、范围、类型与豁免设置，以隔离反例验证，不凭插件名称认定要求已经受保护。

当前[工具与隔离正反例](../workflow/04-工程检查设计.md#注释与格式的限定校准)已验证部分声明覆盖、位置及正文结构，[联合入口](../workflow/04-工程检查设计.md#真实编译范围与源码检查绑定)已绑定真实编译范围。语义用途、全部声明与合法文档形式仍须补齐；不存在完整生产源码门禁、产品构建或整套通过结论。

## 方法注释验证

结构检查覆盖已确定的合同与关键方法；方法职责及允许省略条件需要源码和场景证据，不能伪称全部由脚本判断。

| 验证对象 | 结构反例及检查责任 | 语义审阅责任 |
|---|---|---|
| 合同与关键方法 | 已确定适用的方法或构造器缺少有效说明；不得按可见性漏检关键私有方法 | 确认实际合同边界及关键行为，不能用 public 范围作为全部覆盖结论 |
| 位置与文档内容 | 注释错位、正文及必要签名说明缺失或不匹配；引用或继承的文档来源须可核对 | 判断输入、结果及失败说明准确，实际新增行为没有被继承或引用掩盖 |
| 省略条件 | 不得以全局跳过 Override、getter 名称或短方法阈值放行所有匹配方法；结构分析只提供候选 | 验证省略对象确属内部简单访问器或纯委托且无额外语义，关键行为不得误判 |
| 行为变化 | 本次新增关键行为而仍使用旧的范围或排除结果，需要重新检查 | 判断先前省略或已有注释是否仍有效，并核对更新后的源码和场景 |

隔离验证同时包含允许场景：符合条件的内部简单访问器及纯委托不因缺少重复注释被统一拒绝；含权限、转换或失败处理的同名短方法则不能因外形相近得到豁免。语义案例用带证据的评审验证，结构案例由对应自动检查验证，不能把人工判断包装成机器已证明。

技术依据：[MissingJavadocMethod](https://checkstyle.org/checks/javadoc/missingjavadocmethod.html)的默认范围及跳过设置不能直接充当项目覆盖规则；[Javadoc 方法文档](https://docs.oracle.com/en/java/javase/25/docs/specs/javadoc/doc-comment-spec.html#method-documentation)说明参数、结果、异常和文档继承的条件。原[方法缺失探针](../workflow/04-工程检查设计.md#注释与格式的限定校准)只验证明确选中对象；后续已接通[真实声明合同方法的源码关联及说明结构](../workflow/04-工程检查设计.md#实际合同方法与源码说明)，仍未完成全部实际合同、关键方法、省略及继承的完整生产识别，不由限定结果产生语义或整体通过。

## 复杂度验证

每项已选指标同时验证阻断能力与合法实现，不以单个超限样例代替覆盖检查。

| 验证对象 | 检查或评审要求 |
|---|---|
| 阈值边界 | 低于、等于上限的实现通过对应指标检查；超过上限且无有效人工例外的实现必须失败 |
| 计数与声明覆盖 | 用可核对结果验证已声明的分支、行数及适用声明形式；漏配决定点或目标形式不能仍报告完整通过 |
| 执行范围 | 关闭检查、未扫描适用实现、使用不同基线或未经批准的排除时，交付检查必须失败 |
| 测试基线 | 测试主体、夹具及辅助逻辑用对应基线验证上限边界；遗漏测试范围或用测试分类放行生产实现时，范围检查及相应评审必须识别问题 |
| 例外匹配 | 有依据且范围匹配的人工例外才允许对应超限；自行抑制、范围外对象及失效例外不能放行 |
| 整改质量 | 带源码与行为测试评审职责及合同；数值降低不能掩盖无意义拆分、行为缺失或测试被削弱 |

自动检查负责固定计数、阈值及可判定的范围与例外匹配；语义评审负责职责、可读性和整改合理性，超限例外仍须人工批准。计量与支持范围见[机制设计](../workflow/04-工程检查设计.md#方法规模计量决策)，初始数值只维护于[唯一配置](../../tools/engineering_gate/complexity.json)；实际完成状态见任务记录，候选试验不产生批准或例外。
