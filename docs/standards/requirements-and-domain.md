# 需求分析与领域设计规范

规范来源与固定输入见[第二层确认记录](../../REBUILD.md#第二层确认记录)；实际实现、验证及未完成项见[当前任务](../tasks/control-plane-verification.md#唯一任务记录)。

## 适用范围与阅读入口

本规范用于平台能力建设和消费项目的业务需求研发。按任务触发读取：

- 新需求、行为修改或需求不明确：[需求与场景分析](#需求与场景分析)。
- 新增或调整业务边界、同名术语含义冲突：[领域与上下文识别](#领域与上下文识别)。
- 选择轻量实现或领域模型：[建模深度](#建模深度)。
- 设计身份、业务状态、不变量、聚合或事件：[上下文模型与战术设计](#上下文模型与战术设计)。
- 复核需求到设计的完整性：[设计审阅与变更](#设计审阅与变更)。

代码依赖、服务映射、端口、查询、事务与持久化规则见[系统设计规范](system-design.md)。任务恢复与本层审阅入口见[重建路径](../../REBUILD.md#第二层审阅入口)。

## 需求与场景分析

先明确需求解决的问题及可验证结果，再确定模型、接口与实现。已有需求只记录受影响的变化，并引用有效基线；不为普通变更复制完整设计。

| 分析对象 | 必要输入或产物 | 检查方法 |
|---|---|---|
| 目标与范围 | 需求来源、预期使用者、业务目的、交付结果及本次不承担的内容 | 核对与平台或消费项目目标一致，能说明为何需要本次工作 |
| 场景与验收 | 成功、失败、非法输入及实际适用的并发、重复、恢复场景 | 预先明确观察什么结果才能通过，区分受理、完成与部分成功 |
| 规则与语言 | 关键术语、规则、状态及其业务所有者 | 同一上下文内含义一致，规则能回指具体场景 |
| 数据与协作 | 数据归属、权限、读写范围、参与能力及外部依赖 | 不以表、接口或技术组件名称替代业务责任 |
| 运行约束 | 适用的时效、一致性、安全、性能及恢复前提 | 明确测量条件与门槛；未知条件保持未知 |

区分可调查事实、设计建议和需要人工决定的业务选择。可调查事实自行查明；会改变范围、合同或风险且无法查明的问题，进入聚焦访谈。只暂停依赖该问题的设计，其他已明确部分继续推进。

分析可以保存在任务设计记录中；格式、索引与状态流转由后续研发流程规范确定。低影响任务仍说明目标、变化和验证，复杂或跨边界任务补足模型、合同及一致性设计，文档长度按所需证据控制。

## 领域与上下文识别

### 概念与判断对象

| 概念 | 本规范中的含义 |
|---|---|
| 领域 | 软件需要理解和解决的业务问题范围 |
| 子域 | 领域内围绕业务目标、规则和专业语言形成的问题分区 |
| 限界上下文 | 一套术语与模型能够保持一致的明确适用范围 |
| 领域模型 | 对该上下文内业务概念、关系、规则和行为的表达 |
| 代码模块 | 组织及检查源码依赖的单位 |
| 部署单元 | 一起启动、发布和运行的应用单位 |

业务语义、代码组织、存储及部署分别说明，再建立映射；映射方法遵守[上下文与部署规则](system-design.md#上下文与部署映射)。

### 边界识别方法

1. 从业务参与者、目标、流程及规则开始，比较已有上下文能否自然承担需求。
2. 核对同名概念的含义、生命周期、规则所有者与变化原因。存在真实语义或责任冲突时，再比较拆分与维持边界的方案。
3. 每个候选上下文说明业务目的、主要术语、规则和数据责任、公开协作以及不承担的内容。
4. 用成功、失败和协作场景检查边界；再评估模块与部署映射。技术或团队约束参与可行性判断，不单独决定业务划分。

核心、支撑和通用子域用于解释业务价值与投入。核心子域说明竞争差异；支撑子域说明业务必要性；通用子域比较复用、采购或自行建设的成本。分类来自消费项目的目标，不把平台全部通用组件自动等同于业务领域，也不因分类而降低其已承诺的交付质量。

仅因为新增页面、数据库表、目录、团队或服务就新增上下文，不构成充分理由。若两个场景的同名概念存在不同含义或规则，不应靠万能对象和大量场景标志强行统一。

### 上下文关系记录

每项跨上下文关系说明调用或数据流向、业务意图、公开合同、数据所有者、模型翻译位置、版本兼容及失败责任。按需要采用公开服务、已发布交换语言、模型适配等方式，不为每次协作固定增加一套模式结构。

各上下文维护自己的规范模型。确需共享模型子集时，说明共同语义、范围、共同维护责任与兼容约束；未说明这些条件时，按公开合同交换所需数据，不直接共享内部可变对象。平台复用的是已公布的通用能力，消费项目的业务模型仍由各项目维护。

技术依据：[Fowler 的限界上下文说明](https://martinfowler.com/bliki/BoundedContext.html)解释模型与语言的一致性范围；[Microsoft 的领域分析指南](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis)说明先分析业务与上下文，再识别服务。这里的具体判断方法属于已确认的项目规范，不直接确定业务系统的实际划分。

## 建模深度

### 已确认原则

- 所有业务均须明确业务规则、归属及依赖边界。简单维护允许轻量实现；复杂业务使用承载规则的领域模型。
- Agent 必须提供建模选择依据，不能仅以“只是 CRUD”为由跳过业务分析。
- 统一规范规定适用条件和必要边界，不要求所有业务生成同样数量的对象、抽象或技术层次。在适用条件内选择实现方式不属于规范例外。

### 判断与审阅方法

以下细化上述原则；具体依赖边界及代码组织见[系统设计规范](system-design.md)。

先从成功、失败和非法场景中列出规则，再决定模型深度。不能仅依据接口数量、表数量或页面看起来是否简单作出判断。

| 情形 | 设计要求 | 审阅依据 |
|---|---|---|
| 规则局限于简单维护，未识别出复杂生命周期或多个操作共同维护的业务约束 | 使用直接、清晰的用例实现；不为结构整齐额外创建没有职责的领域对象 | 列明实际规则及其实现归属，说明轻量实现为何足以维护这些规则 |
| 业务规则相互制约，涉及多阶段生命周期、复杂计算或多个操作共同维护的约束 | 明确规则所属模型及合法行为，使规则在相关业务操作中一致地得到维护；只采用有场景依据的领域模式 | 用成功、失败和非法场景检验模型行为，核对规则是否遗漏、重复或散落 |
| 需求不足，无法判断规则与生命周期 | 标明未知项及其影响，通过业务访谈查明，暂不把猜测固化为模型 | 核对未知项是否会改变范围、规则或一致性要求；只阻塞依赖它的设计 |

两种实现都要处理各自适用的授权、事务、失败和测试要求；模型深度不是降低工程质量的理由。发现新增规则使原先判断失效时，在该需求的设计中重新评估，并同步受影响的模型与验证场景。

### 对照示例

以下仅用于说明判断方法，不是新零售产品的已确认需求或系统划分。

- 假设字典项仅维护名称、启停和排序，规则只有已确认的输入及重复约束，可采用轻量用例实现。若它还承担审批、版本生效或关联业务限制，须依据这些实际规则重新判断。
- 假设订单有金额计算、允许取消的状态与条件，以及多个操作必须共同维护的约束，应在模型中表达这些行为和约束；不能仅生成数据字段，再让不同操作各自重复判断。

技术依据：Fowler 区分[事务脚本](https://martinfowler.com/eaaCatalog/transactionScript.html)与领域模型，并在[贫血领域模型讨论](https://martinfowler.com/bliki/AnemicDomainModel.html)中说明领域模型应组织业务行为，且并非适合所有场景。这些资料支持判断方法，不替代本项目的人工决定，也不直接确定持久化访问方式。

## 上下文模型与战术设计

只在明确的上下文中采用所需模式。模型记录术语、主要规则、合法及非法行为、数据与协作边界；代码、接口和存储设计引用这一有效模型，变化以增量更新。

| 模式 | 采用依据 | 审阅重点 |
|---|---|---|
| 实体 | 业务需要跨时间追踪同一身份 | 身份含义与生命周期明确，业务行为维护自身规则 |
| 值对象 | 概念由值定义，不需要独立身份 | 等值语义清晰，优先不可变，相关计算遵守领域规则 |
| 聚合 | 有需要原子维护的业务约束 | 根负责合法修改，边界由不变量与生命周期解释，范围保持内聚 |
| 领域服务 | 业务规则无法自然归属单一实体或值对象 | 说明规则归属，不充当堆放所有业务逻辑的通用服务 |
| 领域事件 | 已发生且业务关心的事实 | 名称、触发条件和业务意义明确，区分内部事实与对外集成合同 |
| 仓储协议 | 用例需要读取或保存聚合的业务状态 | 按业务需要表达读写，具体持久化和对象转换遵守系统设计规范 |

聚合不由数据库外键、接口请求结构或对象数量机械推导。跨聚合或跨上下文约束按[事务与一致性规则](system-design.md#本地事务与跨上下文一致性)分析；不为避免协调创建巨型聚合，也不机械要求所有跨聚合操作异步化。

每个重要生命周期列出操作、前置条件、合法与非法状态转换、维护的约束及必要的业务事件。每项约束说明谁维护、何时验证以及失败结果。领域事件转换为集成事件时，明确发布数据、版本、权限和恢复合同。

工厂、规格、策略等模式只在创建过程、组合规则或真实算法变化需要时采用，说明它解决的问题和调用方。单一构造、单一判断或未知未来变化不自动产生这些抽象。

持久化分离规则见[领域与持久化对象分离](system-design.md#领域与持久化对象分离)。领域模型、持久化对象、公开输入输出与集成事件各有职责，不因字段相似就自动合并角色。

技术依据：[Microsoft 的战术 DDD 说明](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/tactical-ddd)提供实体、值对象、聚合、服务及事件的基本含义。本项目的部署、查询及共享本地事务策略以已确认选择为准，并不整体采用资料中的微服务或异步协作建议。

## 设计审阅与变更

| 审阅对象 | 需要的证据 | 验证边界 |
|---|---|---|
| 目标与场景完整性 | 需求来源、交付结果及成功失败场景 | 索引或字段检查核对引用；目标匹配及遗漏场景由语义评审核对，新业务取舍仍须人工决定 |
| 领域与上下文边界 | 术语、规则所有权、数据和协作责任及边界理由 | 依赖检查能识别部分越界引用，业务语义不能只由脚本判定 |
| 模型深度与行为 | 采用模式的依据、规则归属及合法非法行为测试 | 核对模型实际维护规则，不能以类数量或命名代替评审 |
| 变更影响 | 受影响模型、合同、数据、一致性与消费方 | 只更新有效来源和受影响内容，重新验证变化涉及的场景 |

模型或边界无法解释实际场景时，回到需求与业务责任分析，修正设计并复验。检查、评审和人工确认分别记录，不能以自动检查通过产生业务确认或本层整体验收结论。
